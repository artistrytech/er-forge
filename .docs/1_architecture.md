# ER図管理ツール 設計書

## 1. スコープ

### 1.1 動作モード

| モード | 起動方法 | 必要な環境 | 提供機能 |
|---|---|---|---|
| **静的モード** | `erd/index.html` をブラウザで開く（`file://`） | **なし**（ブラウザのみ） | ER図の閲覧（ノードはテーブル名のみ）、ページ切替、パン / ズーム、検索、リレーション追跡、テーブル / リレーションの詳細ダイアログ、テーブルカタログ（一覧・詳細）の閲覧。**ER図の配置編集も可能だが保存はできず、エクスポート（生の JS コードを表示・コピー）で持ち出す** |
| **サーバーモード** | `java -jar erd-server.jar` | Java 17+ | 静的モードの全機能 + DBからのスキーマ逆生成、スキーマ / 論理名 / 論理制約の編集、カラム論理名の横断一括編集、ドラッグによるER図更新とファイル保存、ページ管理、自動レイアウト |

**「動作モード」と「編集セッション」は直交する別概念である。** 動作モードは起動方法で決まる（上表）。編集セッション（閲覧中 / 編集中）はユーザーが明示的に切り替えるもので、**静的モードでも編集セッションを開始できる**（§9.7）。

**このツールはローカルで単独利用する前提とする。** 複数人による同時編集は考慮しない（サーバーは `127.0.0.1` にのみ bind される）。競合は「稀な例外」として扱い、**保存時に検出して中止し、人が再操作して復旧する**設計とする（§8.6）。

### 1.2 非スコープ

- CLI サブコマンド（全操作を GUI で提供する）
- ネイティブバイナリの配布、および実行ファイルの Git 管理
- npm / npx によるツール配布
- サーブレットコンテナ（Tomcat 等）へのデプロイ
- クラウド / 共有サーバーでのホスティング
- **複数人による同時編集**（差分マージ・OT・CRDT の類は導入しない）
- **複数スキーマ（ネームスペース）の同時管理**。**1プロジェクト = 1スキーマ**とし、対象スキーマは逆生成の設定で指定する。GUI にスキーマ名は表示しない（全テーブルで同じ値であり、ノイズにしかならない）。ただしテーブルID は `schema.table` の形式を維持する（将来の拡張余地と ID 衝突の回避のため）
- **画像・文書のエクスポート**（PNG / SVG / 印刷 / Mermaid / Markdown 定義書）。ブラウザのスクリーンショット・印刷で代替する
  - **例外**: 静的モードで編集した配置を持ち出すための「配置のエクスポート」（`ERD.diagram({...})` の生コードをダイアログに表示・コピー）は提供する。静的モードにおける唯一の保存手段であるため（§9.7）
- **DDL ファイル（`CREATE TABLE`）からの取り込み**。スキーマの入力元は JDBC 接続と GUI の手動編集に限定する
- **逆生成の実行履歴の保持**
- **`.gitignore` の自動検査 / 自動追記**（利用者が手動で設定する）

### 1.3 対応DB

**JDBC ドライバがあれば原則すべての DB に対応する。**

| DB | 対応レベル |
|---|---|
| PostgreSQL | 同梱ドライバ + Dialect Enhancer（DB固有情報の追加取得） |
| MySQL | 同梱ドライバ + Dialect Enhancer |
| その他（SQL Server, Oracle, SQLite, H2 …） | **ユーザーが JDBC ドライバの jar を追加するだけで、JDBC 標準メタデータの範囲で動作する**。必要に応じて Enhancer を後から追加 |

### 1.4 横断機能要件

全機能に共通してかかる要件。個別機能の設計はこれに従う。

#### 1.4.1 言語対応（i18n）

- **日本語 / 英語**の2言語に対応する。
- 初期言語は**ユーザーの環境設定に従う**（ブラウザの `navigator.languages` を評価し、`ja` で始まるなら日本語、それ以外は英語）。GUI から明示的に切り替えることもでき、選択は個人設定として保持する（静的モードではメモリ、サーバーモードでは `.erd/`）。
- UI 文字列はすべて翻訳リソース化し、コード中に直接記述しない。**翻訳リソースはバンドルに内包する**（`file://` では `fetch` による遅延ロードができないため）。
- **翻訳対象は UI 文字列のみ。** DB 由来の識別子・コメント、ユーザーが入力した論理名・注記は翻訳しない（データそのものであり、言語切替で見た目が変わってはならない）。
- 日時・数値の書式は選択言語のロケールに従う。

#### 1.4.2 リンクのブラウザ標準準拠

**画面遷移を伴う要素はすべて実体のあるリンク（`<a href="...">`）として実装する。** `onClick` のみで遷移する疑似リンクを作らない。これにより以下がブラウザ標準の挙動として成立する。

| 操作 | 期待される挙動 |
|---|---|
| Ctrl / ⌘ + クリック、中クリック | 新しいタブで開く |
| Shift + クリック | 新しいウィンドウで開く |
| 右クリック | 「新しいタブで開く」「リンクをコピー」等のコンテキストメニュー |
| ホバー | ステータスバーに URL が表示される |
| ブラウザの戻る / 進む | 履歴を辿れる |

- 実装上、修飾キーなしの左クリックのみ `preventDefault()` してクライアントサイド遷移に置き換える。修飾キー付き・中クリックはブラウザに委ねる。
- 対象となる遷移: ER図ページの切替、テーブル一覧 / 詳細 / 編集画面、ER図上のノード・詳細ダイアログからテーブル詳細画面へのリンク、テーブル詳細画面から ER図 へのリンク、検索結果、リレーションの参照先。
- **URL は `#` ハッシュで表現する**（`file://` では History API による pushState が使えないため）。ルーティング体系は §4.4 を参照。

## 2. 技術選定

### 2.1 バックエンド（サーバーモード）

| レイヤ | 選定 | 備考 |
|---|---|---|
| 言語 | **Java 17 LTS** | Javalin 6 の最低要件。Java 21 でも動作 |
| Webフレームワーク | **Javalin 6**（Jetty 組み込み） | 軽量。Spring は使用しない |
| ビルド | **Gradle + Shadow プラグイン** | 実行可能 fat JAR を生成 |
| データ入出力 | **Jackson**（JSON5 相当の緩和フラグ付き） | §5.12 参照 |
| DB内省 | **JDBC `DatabaseMetaData`**（標準層）+ `DialectEnhancer`（拡張層） | §7 参照 |
| ドライバ管理 | `drivers/*.jar` の自動スキャン + `DriverShim` / クラスパス指定 | §7.2 参照 |
| ファイル監視 | `java.nio.file.WatchService` → Javalin の SSE | |
| 自動レイアウト | **Eclipse ELK（`org.eclipse.elk`, Java実装）** | 新規テーブルの初期配置に使用 |
| テスト | JUnit 5 + **Testcontainers**（PostgreSQL / MySQL の実DBで内省を検証） | |

**WAR ではなく実行可能 fat JAR とする。** `java -jar` 実行時は `-cp` が無視されるため、WAR / `-jar` 形式では「実行時のクラスパス追加によるドライバ拡張」が成立しない。Javalin は Jetty 組み込み型であり、サーブレットコンテナを前提としない。

### 2.2 フロントエンド（ビューア / エディタ）

| レイヤ | 選定 | 備考 |
|---|---|---|
| 言語 | TypeScript（strict） | |
| UI | React 19 | |
| ER図キャンバス | **`@xyflow/react`（React Flow, MIT）** | パン / ズーム / ドラッグ / MiniMap / Controls を標準搭載。Canvas / WebGL 方式は採用しない |
| 状態管理 | zustand | Undo / Redo を実装 |
| ルーティング | **ハッシュルーティング（自前の軽量実装）** | `file://` では History API が使えない。§1.4.2 / §4.4 参照 |
| 国際化 | **自前の軽量 i18n**（`ja` / `en` の辞書をバンドルに内包） | `file://` では翻訳リソースを `fetch` できない。ライブラリを入れるほどの規模ではない |
| ビルド | **Vite + `vite-plugin-singlefile`** | 単一 `index.html` を出力 |
| スキーマ検証 | zod | データファイル ⇔ モデルの境界で型を保証 |
| テスト | Vitest + Playwright | |

### 2.3 フロントエンドのビルド制約（静的モードのための必須設定）

`file://` ではクラシックスクリプトしかロードできない。以下を厳守する。

- `build.rollupOptions.output.format: 'iife'`
- コード分割禁止（`inlineDynamicImports: true`）
- `build.target: 'es2019'`
- ビューア本体から **Web Worker / 動的 `import()` / `fetch` を使用しない**
- `localStorage` に依存しない（`file://` の opaque origin で不安定。個人設定（言語・表示設定）は静的モードではメモリ保持、サーバーモードでは `.erd/` に保存する）
- **翻訳リソース（ja / en）はバンドルに内包する**（遅延ロード禁止）
- **画面遷移は `#` ハッシュ URL のみで表現する**（`history.pushState` は `file://` で使用不可）。すべての遷移要素を `<a href="#/...">` として実装し、ブラウザ標準のリンク挙動を保つ（§1.4.2）

## 3. 配布 / 運用

### 3.1 配布物

`npm run build`（フロント）と `./gradlew shadowJar`（バック）の成果物を手動で ZIP 化し、**GitHub Releases に手動アップロード**する。

```
erd.zip
├── erd-server.jar          fat JAR（Javalin + Jetty + Jackson + ELK + core）
├── drivers/                空（README のみ）。JDBC ドライバは各自が取得する
│   └── README.txt
├── index.html              単一HTML（スキーマ情報は含まない）
├── erd.sh / erd.bat        起動スクリプト
└── README.md
```

**ZIP 名にバージョンは入れない**（`erd.zip` 固定）。展開先の `erd/` を差し替える運用のため、
ダウンロードしたファイル名が毎回同じであるほうが手順を書きやすい。リリースのバージョンは
GitHub Releases のタグで示す。

**JDBC ドライバは配布物に同梱しない。** 代わりに逆生成画面から Maven 経由でダウンロードする
（§7.2）。同梱しないのは意図的で、(1) 再配布に伴うライセンス問題（MySQL は GPLv2 + FOSS 例外、
Oracle は proprietary な OFUTC）を避け、(2) 配布 ZIP を小さく保つため。既定バージョンは
`DriverCatalog`、チーム共有の設定は `data/config.js` の `drivers` に置く。

### 3.2 起動方法

| 方式 | コマンド | 用途 |
|---|---|---|
| **A. `drivers/` 自動スキャン（既定・推奨）** | `java -jar erd-server.jar` | 追加したいドライバ jar を `drivers/` に置くだけ。OS 差（パス区切り文字）の影響を受けない |
| B. クラスパス指定 | `java -cp "erd-server.jar:drivers/*:/path/to/extra.jar" com.erd.Main`<br>（Windows は `;` 区切り） | 任意の場所の jar を使う場合 |

### 3.4 運用フロー

**アーキテクト / 編集者**

1. Release の ZIP をダウンロードし、`erd/` に展開する
2. `java -jar erd-server.jar` を実行（ブラウザが自動で開く）
3. GUI から DB 接続 → 逆生成 → 差分確認 → 適用
4. GUI 上でテーブルをページに配置（ドラッグ）
5. `erd/index.html` と `erd/data/**` を `git commit` / `push`

**プロジェクトメンバー（閲覧のみ）**

1. `git pull`
2. `erd/index.html` をブラウザで開く（**Java・Node・npm・サーバーのいずれも不要**）

### 3.5 バージョン整合性と自動移行

`index.html` と `data/**` の形式バージョンが食い違う可能性に備える。**サーバーが起動時に自動で移行し、ユーザーに手作業を求めない。**

- `manifest.js` に `schemaVersion`（データ形式のバージョン）を持たせる
- サーバーは `CURRENT_VERSION` と、`v1→v2`, `v2→v3` … の**移行関数の列**を持つ

| 状態 | 挙動 |
|---|---|
| データ == サーバー | そのまま起動 |
| データ **<** サーバー | **自動移行**（バックアップ → 全ファイルを新形式で再生成 → アトミック置換）。完了後、GUI に「データ形式を v1 → v2 に移行しました。差分をコミットしてください」と通知する |
| データ **>** サーバー | **起動を中止**し、データに一切触れない。「`erd-server.jar` を更新してください」（古いツールが新しいデータを壊さない） |

- **静的モード（ビューア）は移行しない。** バージョンが一致しない場合、**描画せずバナーを表示する**（中途半端に読んで誤ったER図を見せるより、明確に止まる方が安全）。`index.html` と `data/**` は同じコミットで更新されるため、メンバーがこの状態に遭遇するのは移行の過渡期のみである。
- `schemaVersion` は**後方互換を破る変更時のみ**インクリメントする。**キーの追加では上げない**（未知キーは読み書きで保持されるため。§5.12）。
- 移行は全ファイルを書き換えるため、大きな Git 差分になる。GUI で「単独のコミットにすることを推奨します」と明示する。

詳細は [詳細設計: フェーズ0](function-details/Phase0_model-printer-index.md) §6 を参照。

### 3.6 初回起動（`data/**` が空のとき）

`erd/data/manifest.js` が存在しない、またはテーブルが0件の状態でサーバーを起動したら、**ブートストラップ画面**を表示する。

| 選択肢 | 内容 |
|---|---|
| **既存のスキーマから生成する** | DB に接続して逆生成する（§7 のフローへ）。実運用の入口 |
| **サンプルデータを取り込む** | ツールに同梱したサンプル（約30テーブルの `data/**` 一式）を書き出す。DB を用意せずに機能を試せる |
| （将来）**空のプロジェクトを作成する** | テーブルの手動作成（J-01）が実装された時点で選択肢に追加する |

- サンプルデータは `.docs/sample-schema.sql`（約30テーブルの PostgreSQL DDL。日本語コメント付き）を元に、**実装時に生成して同梱する**（論理名・論理制約・ER図ページの配置例を含んだ、完成状態のサンプルとする）。
- 既存の `data/**` がある状態では、サンプルの取り込みを**実行できない**（上書き事故を防ぐ）。
- **静的モードで `data/**` が空の場合**は、「データがありません。サーバーモードで起動して初期化してください」と表示する（静的モードには初期化手段がない）。

## 4. アーキテクチャ

### 4.1 モジュール構成

```
erd-tool/                       （ツール本体のリポジトリ）
├── server/                     Java / Gradle
│   ├── core/                   モデル、決定論的プリンタ、Jackson パーサ、差分検出、リネーム検出、論理名辞書
│   ├── introspect/             JDBC 標準内省 + DialectEnhancer（postgres / mysql）
│   ├── layout/                 Eclipse ELK による自動レイアウト
│   └── web/                    Javalin ルーティング、SSE、ファイルI/O、ドライバローダ
└── viewer/                     TypeScript / Vite
    ├── model/                  モデル型定義（zod）、データローダ、論理名の解決
    ├── canvas/                 React Flow ノード（テーブル名のみ）/ エッジ（物理FK・論理FK）
    ├── catalog/                テーブル一覧 / 詳細 / 編集画面、カラム論理名の一括編集画面
    ├── i18n/                   ja / en 辞書、言語判定・切替
    └── ui/                     ルーター（ハッシュ）、ページ、検索、詳細ダイアログ、編集UI（サーバーモード時のみ有効）
```

### 4.2 責務分界

**サーバーは「I/O とメタデータ取得」に責務を限定する。** 差分の解釈・リネームの承認・レイアウトの決定といった判断は GUI 側に置く。

| 責務 | 配置 |
|---|---|
| DB 接続、JDBC メタデータ取得、正規化 | サーバー |
| `data/**` の読み書き、決定論的プリント | サーバー |
| ファイル監視 → SSE 配信 | サーバー |
| 自動レイアウト計算（ELK） | サーバー |
| スキーマ差分の表示・リネームの承認・適用範囲の選択 | ビューア（GUI） |
| ER図の描画・ドラッグ・ページ管理 | ビューア |
| 論理名の解決（個別 → 辞書 → 物理名）、多言語化 | ビューア |

### 4.3 モード判定と編集セッション

ビューアは起動時に `GET /__erd/health` を1回試行する。

- 成功 → **サーバーモード**（保存が可能）
- 失敗（`file://` では即座に失敗）→ **静的モード**（保存不可）

#### データの読み込み経路は1本にする

**モードにかかわらず、データの読み込みは常に `<script>` タグによる `data/**.js` の動的注入で行う。API はデータ取得に使わない。**

| | 読み込み | 書き込み |
|---|---|---|
| 静的モード | `<script>` タグ | なし（エクスポートで持ち出す） |
| サーバーモード | **`<script>` タグ（同じ経路）** | REST API |

**API を読み込みにも使うと、ローダーが2系統になる。** データ形式のパース・キャッシュ・進捗表示・欠損時のエラー処理をすべて二重に持つことになり、「静的モードでだけ壊れる」バグが構造的に生まれる。読み込みを1本化すれば、ビューアのデータ層はモードを一切意識しない。

- サーバーは `data/**` を**静的ファイルとして配信する**（`GET /data/schema/public/users.js` がそのまま返る）。
- **書き込み後の再読込**は、SSE で受け取ったリビジョンをクエリに付けて `<script>` を再注入する（`data/diagrams/core.js?v=<revision>`）。キャッシュを確実に回避でき、グローバル API（`ERD.diagram(...)`）が再度呼ばれてローダーが上書きする。
- API の `GET` 系は、**データ本体ではなくメタ情報のためだけに使う**（`baseHash` の取得、ドライバ一覧、逆生成のプレビュー）。

**動作モードにかかわらず、起動直後は必ず「閲覧中」である。** ユーザーが明示的に「編集」を開始するまで、ノードは動かせない（誤操作で配置が変わらない）。

| | 静的モード | サーバーモード |
|---|---|---|
| 編集セッションの開始 | 可能。「保存されません」の警告を出す | 可能。**閲覧ルートと編集ルートを分ける**（§4.4）。ロックは取得しない（別タブ / 外部の変更は §8.7 のバナーで検知する） |
| 保存 | **不可**。エクスポート（§9.7）で持ち出す | 可能（**明示保存のみ**。自動保存はしない） |
| 自動レイアウト（ELK） | 不可（サーバー API に依存） | 可能 |
| スキーマ・論理名の編集 | 不可 | 可能 |

### 4.4 ルーティング（ハッシュ URL）

**ER図とテーブルカタログは対等な2つのビューであり、いずれも URL で直接指せる。** すべての画面遷移はこのハッシュ URL への `<a href>` リンクとして実装する（§1.4.2）。

**閲覧と編集は別ルートとする。** 各画面は既定で**閲覧ルート**に着地し、編集は必ず画面内の [編集開始] から**編集ルート**へ遷移して初めて始まる（画面へ遷移しただけでは編集モードにならない）。

| ルート | 画面 | モード |
|---|---|---|
| `#/erd/<diagramId>` | ER図（指定ページ・閲覧） | 静・編 |
| `#/erd/<diagramId>/<tableId>` | ER図。該当ノードを中央表示・選択状態にする | 静・編 |
| `#/erd/<diagramId>/edit` | **ER図の配置編集**（閲覧ルートから [編集開始] で遷移） | 静・編（静的モードは保存不可。エクスポートで持ち出す。§9.7） |
| `#/tables` | テーブル一覧 | 静・編 |
| `#/tables/<tableId>` | テーブル詳細（閲覧） | 静・編 |
| `#/tables/<tableId>/edit` | テーブル編集 | 編（静的モードでは詳細へリダイレクトし、閲覧モードである旨を表示） |
| `#/columns` | カラム論理名の一括編集（テーブル横断・閲覧） | 静・編 |
| `#/columns/edit` | カラム論理名の一括編集（編集） | 編（静的モードでは `#/columns` へリダイレクト） |
| `#/introspect` | DB からの逆生成（接続 → 内省 → 差分 → 適用のフロー） | 編 |

- ER図上のノード / エッジのダブルクリックで開く詳細ダイアログは、一時的な UI であり URL を持たない。ダイアログ内から `#/tables/<tableId>` への**実リンク**を提供する。
- テーブル詳細画面からは、そのテーブルが配置されている各ページへの `#/erd/<diagramId>/<tableId>` リンクを提供する。配置ページが複数ある場合はページを選択させる（リンクを列挙する）。
- **編集ルート滞在中に別ルートへ遷移しようとしたら、未保存の変更があれば確認する**（破棄 / キャンセル）。ブラウザの戻る / 進むも同様に捕捉する（`popstate`。[X-05](2_functions.md) の「ブラウザ標準の戻る / 進む」は、編集中に限りこのガードが優先する）。修飾キー付きクリック（Ctrl / 中クリック）による別タブ表示は妨げない（別タブは閲覧として開く）。
- 編集ルートへ直接着地した場合（ブックマーク・リロード・戻る）はその画面の編集モードで開く（下書きは空から）。ただし静的モードで編集不可の画面（テーブル編集・カラム論理名編集）は上表のとおり閲覧ルートへリダイレクトする。
- 未知のルート・存在しない ID は「見つかりません」を表示し、`#/tables` への導線を出す（白画面にしない）。

## 5. データ形式

### 5.1 決定事項

- **形式は JavaScript（クラシックスクリプト）。** `file://` では `fetch` / ES Modules が使用できないため、JSON / YAML を外部ファイルとして読み込むことはできない。
- 各ファイルは **「グローバル API への関数呼び出し1つ」** に限定する。制御構文・変数・演算・関数定義は禁止（実質「JSON5 のオブジェクトリテラル1つ」）。
- **スキーマ情報（`data/schema/`）と ER視覚情報（`data/diagrams/`）は完全に分離する。** 逆生成は `data/diagrams/` を一切書き換えない。
- **ファイル内の自由コメントはサポートしない。** 書き込みは全文を決定論的プリンタで再生成する。人が書く注記はすべて `meta` の構造化フィールドに格納し、逆生成はそこを読み書きしない（＝注記は完全に保持される）。
- **プロジェクト設定（`data/config.js`）とカラム論理名辞書（`data/dictionary.js`）は human-owned。** 逆生成はこれらを**読む**が（無視リストは内省の入力になる）、**書き換えない**。
- **論理名（テーブル / カラム）と論理制約（論理一意制約 / 論理外部制約）は人が持つ情報であり、`meta` に格納する。** DB のスキーマには存在しない情報であり、逆生成で失われてはならない。
  - **唯一の例外**として、逆生成の適用時に `meta.displayName` が**未設定の場合に限り**、DB のコメント（`REMARKS`）を論理名の初期値として書き込む（§5.8.2）。既存値は決して上書きしない。

### 5.2 グローバル API

`index.html` は起動時に以下のグローバル関数を定義する。

| API | 用途 |
|---|---|
| `ERD.manifest({...})` | ファイル一覧 / バージョン |
| `ERD.config({...})` | プロジェクト設定（テーブル無視リスト） |
| `ERD.index({...})` | 全テーブルの軽量サマリ + リレーション一覧（ER図描画・検索・一覧用） |
| `ERD.dictionary({...})` | カラム論理名の横断辞書 |
| `ERD.table({...})` | テーブル1件のスキーマ定義 |
| `ERD.diagram({...})` | ER図ページ1件の視覚情報 |

### 5.3 `data/manifest.js`

```js
ERD.manifest({
  schemaVersion: 1,
  generatedAt: "2026-07-11T09:00:00Z",
  source: { product: "PostgreSQL", version: "16.2" },
  config: "config.js",
  dictionary: "dictionary.js",
  tables: {
    "public.users": "schema/public/users.js",
    "public.orders": "schema/public/orders.js",
  },
  diagrams: [
    { id: "core",    file: "diagrams/core.js",    title: "コアドメイン", order: 1 },
    { id: "billing", file: "diagrams/billing.js", title: "課金",         order: 2 },
  ],
});
```

### 5.4 `data/config.js`（プロジェクト設定 / テーブル無視リスト）

**human-owned のプロジェクト設定。** チーム全員で共有すべき設定であり、Git 管理する（個人設定は `.erd/` へ）。サーバーは逆生成でこのファイルを書き換えない（GUI からの明示的な編集でのみ更新する）。

```js
ERD.config({
  ignoreTables: [
    "public.flyway_schema_history",   // 完全一致
    "public.tmp_*",                   // glob（* と ? が使える）
    "/^staging\\..*_bak$/",           // 正規表現（前後を / で囲む）
  ],
});
```

#### テーブル無視リスト（`ignoreTables`）

**マッチしたテーブルは「このプロジェクトには存在しない」ものとして扱う。** 逆生成の入力からも、既存定義の側からも、双方向に無視する。

| 局面 | 挙動 |
|---|---|
| 逆生成（内省） | DB から取得しない（取得しても差分計算前に捨てる）。**追加候補にならない** |
| 逆生成（差分計算） | `data/schema/**` に定義が存在していても比較対象にしない。**削除候補にならない・変更も検出しない** |
| 既存のスキーマファイル | **削除しない**。ファイルはそのまま残り、ER図・テーブルカタログ・検索には通常どおり表示される |
| 差分プレビュー | 「無視 (N)」として件数のみ表示し、どのパターンにマッチしたかを確認できる |

- マッチ対象は**完全修飾テーブルID**（`schema.table`）。
- 記法は3つ。前後を `/` で囲めば**正規表現**、`*` / `?` を含めば **glob**、それ以外は**完全一致**。
- 用途は主に2つ。
  1. **DB 側の管理テーブルを除外する**（マイグレーション履歴、一時テーブル、バックアップテーブル）
  2. **手動定義テーブル（J-01）を保護する。** DB に存在しないテーブルを手で定義した場合、無視リストに入れないと逆生成のたびに削除候補として現れる
- 無視リストから外すと、次回の逆生成で通常の対象に戻る（DB に存在しなければ削除候補になる）。
- 「今回の内省だけ対象から外したい」場合は、接続設定側のフィルタ（§7.5 の包含 / 除外パターン）を使う。**無視リストはプロジェクトに永続する設定であり、既存定義にも作用する**という点が決定的に異なる。

### 5.5 `data/index.js`（一覧・検索・ER図描画用の軽量インデックス）

全テーブルのスキーマファイルを読み込まずに、テーブル一覧・検索・未配置テーブルの表示、**および ER図の完全な描画**を可能にする。サーバーが `schema/**` から自動生成する派生ファイルであり、手で編集しない。

**ER図のノードはテーブル名のみを描画する（カラムを描かない）ため、ER図の初回描画に必要な情報は「テーブル名 + リレーション」だけになる。** これらを index に集約することで、スキーマファイルは詳細ダイアログ / カタログを開くまで読み込まなくてよい（§6）。

```js
ERD.index({
  tables: [
    { id: "public.users",  name: "users",  schema: "public", displayName: "ユーザー", columns: 8,  tags: ["core", "auth"], diagrams: ["core"] },
    { id: "public.orders", name: "orders", schema: "public", displayName: "注文",     columns: 12, tags: ["core"],         diagrams: ["core", "billing"] },
  ],
  relations: [
    // ER図のエッジ描画に必要な最小情報。kind: "physical"（FK）/ "logical"（meta の論理外部制約）
    { id: "public.users#fk:users_org_id_fkey", kind: "physical",
      from: "public.users", to: "public.organizations", columns: [["org_id", "id"]],
      cardinality: { parent: "0..1", child: "0..N" } },
    { id: "public.orders#lfk:lfk_orders_user", kind: "logical",
      from: "public.orders", to: "public.users", columns: [["user_id", "id"]],
      cardinality: { parent: "1..1", child: "1..N" }, explicit: ["child"] },
  ],
});
```

- **エッジID は `<テーブルID>#<種別>:<制約名>`。** 種別（`fk` / `lfk`）を挟むのは、**物理 FK と論理外部制約で制約名が衝突しうる**ため。`diagrams.edges` のキーもこの形式に一致させる（§5.9）
- `from` は**参照元**（FK を持つ側 = 子）、`to` は**参照先**（親）
- `cardinality`: **解決後**の多重度（§5.7 のカーディナリティ）。ビューアは導出ロジックを持たず、この値をそのまま鳥の足記号にする
- `explicit`: 人が `meta.relations` で明示設定した項目（導出値との区別。詳細ダイアログで「手動設定」と示すため）

### 5.6 `data/dictionary.js`（カラム論理名の横断辞書）

**同名カラムはプロジェクト全体で同じ意味を持つ**という前提のもと、カラム物理名 → 論理名の対応を1箇所で管理する。`created_at` を全テーブルで「作成日時」と表示するために、テーブルごとに設定して回る必要をなくす。

```js
ERD.dictionary({
  columns: {
    id:         "ID",
    created_at: "作成日時",
    updated_at: "更新日時",
    org_id:     "組織ID",
    email:      "メールアドレス",
  },
});
```

- キーはカラムの物理名のみ（テーブル名を含まない）。**テーブル横断の一括編集画面**（`#/columns`）から編集する。
- テーブル個別の事情で異なる論理名を付けたい場合は、そのテーブルの `meta.columns.<name>.displayName` で上書きする（§5.8.1）。
- 逆生成はこのファイルを読み書きしない（human-owned）。

### 5.7 `data/schema/public/users.js`

```js
ERD.table({
  id: "public.users",
  name: "users",
  schema: "public",
  comment: "ユーザーマスタ",
  columns: [
    { name: "id",         type: "bigserial",    logicalType: "int",      nullable: false, autoIncrement: true },
    { name: "email",      type: "varchar(255)", logicalType: "string",   nullable: false },
    { name: "org_id",     type: "int8",         logicalType: "int",      nullable: true },
    { name: "created_at", type: "timestamptz",  logicalType: "datetime", nullable: false, default: "now()" },
  ],
  primaryKey: ["id"],
  uniques: [
    { name: "users_email_key", columns: ["email"] },
  ],
  indexes: [
    { name: "idx_users_created_at", columns: ["created_at"] },
  ],
  foreignKeys: [
    { name: "users_org_id_fkey", columns: ["org_id"], ref: { table: "public.organizations", columns: ["id"] }, onDelete: "set null", onUpdate: "no action" },
  ],
  dialect: {
    // Enhancer が取得した DB 固有情報（CHECK制約、unsigned、ENUM値 など）
  },
  meta: {
    // ↓ human-owned。逆生成は読まず、書き換えない（displayName の初期値補完のみ例外。§5.8.2）
    displayName: "ユーザー",                    // テーブル論理名
    tags: ["core", "auth"],
    notes: "論理削除は deleted_at 運用",
    columns: {
      // カラム単位の論理名（辞書より優先）と注記
      org_id: { displayName: "所属組織ID", notes: "NULL は個人アカウント" },
    },
    logicalUniques: [
      // DB に制約は無いが、運用上一意であることが保証されている組
      { name: "luk_users_org_email", columns: ["org_id", "email"], notes: "組織内でメールは重複しない（アプリ側で担保）" },
    ],
    logicalForeignKeys: [
      // DB に FK は無いが、論理的には参照関係にある（ER図に破線エッジで描画される）
      { name: "lfk_users_last_order", columns: ["last_order_id"], ref: { table: "public.orders", columns: ["id"] }, notes: "性能上 FK を張っていない" },
    ],
    relations: {
      // リレーションのカーディナリティ（物理情報だけでは決まらない多重度を人が設定する。§5.7 のカーディナリティ）
      "fk:users_org_id_fkey": { child: "1..N", notes: "組織には必ず1人以上の利用者がいる" },
    },
  },
});
```

#### キーの所有権

| 区分 | キー | 逆生成の挙動 |
|---|---|---|
| machine-owned | `name` `schema` `comment` `columns` `primaryKey` `uniques` `indexes` `foreignKeys` `dialect` | 上書きする |
| human-owned | `meta.*`（`displayName` / `tags` / `notes` / `columns.*` / `logicalUniques` / `logicalForeignKeys` / `relations`） | **読まない・書かない**。ただし `displayName` が未設定の場合のみ、コメントから初期値を補完する（§5.8.2） |
| 共有 | `id` | リネーム承認時のみ書き換える |

#### 論理制約（`meta.logicalUniques` / `meta.logicalForeignKeys`）

DB に物理的な制約が存在しない一意性・参照関係を、人がメタデータとして宣言し、ER図と詳細画面に表示する。

- 物理制約（`uniques` / `foreignKeys`）とは**フィールドを分けて保持する**。混ぜると逆生成の上書きで消える
- 形式は物理制約と同一のため、詳細画面での表示・カーディナリティ判定・被参照一覧の処理を共通化できる
- **論理外部制約は `onDelete` / `onUpdate` を持たない。** DB に制約が存在しない以上、参照動作も存在しない（持たせると「設定したのに効かない」という誤解を生む）
- ER図では**論理外部制約を破線エッジ**として描画し、物理 FK（実線）と視覚的に区別する
- 参照先テーブル / カラムの存在は保存時に検証する（存在しない場合は警告）

#### カーディナリティ（`meta.relations`）

**多重度は物理情報だけでは決まらない。**

| 多重度 | DB から導出できるか |
|---|---|
| 子から見た**親**が `0..1` か `1..1` か | **できる**（FK カラムが NULL 可か、すべて NOT NULL か） |
| 親から見た**子**が `0..1` か `0..N` か | **できる**（FK カラムに一意制約があるか） |
| 親から見た子の**下限が 0 か 1 か**（`0..N` か `1..N` か） | **できない**。「組織には必ず1人以上の利用者がいる」は**業務ルール**であり、外部キー制約では表現できない |

したがって、**カーディナリティは「物理からの導出値」を既定とし、人が `meta.relations` で上書きする**。

```js
meta: {
  relations: {
    // キー = エッジID の後半（<種別>:<制約名>）。物理 FK・論理外部制約の両方に付けられる
    "fk:users_org_id_fkey": { child: "1..N", notes: "組織には必ず1人以上の利用者がいる" },
  },
}
```

- `parent`（子から見た親）: `"0..1"` / `"1..1"`、`child`（親から見た子）: `"0..1"` / `"1..1"` / `"0..N"` / `"1..N"`
- **部分上書きができる**（`child` だけ設定し、`parent` は導出値のままにする）
- **human-owned。逆生成は読まない・書かない**
- **`meta` は FK を持つ側（参照元テーブル）に置く**。FK の定義と同じ場所で完結する
- サーバーは `index.js` の生成時に「導出値 + 上書き」を解決し、**解決後の値のみを `index.relations[].cardinality` に載せる**（ビューアは導出ロジックを持たない）

#### 型の二重保持

複数DB対応のため、型は2つ持つ。

- `type`: JDBC の `TYPE_NAME` に基づく DB 生の型文字列（忠実性の担保）
- `logicalType`: `java.sql.Types`（`DATA_TYPE`）に基づく正規化型。詳細ダイアログ・カタログの表示・アイコン・比較はこちらを使用する
  - `string` / `int` / `float` / `decimal` / `bool` / `date` / `time` / `datetime` / `json` / `uuid` / `binary` / `enum` / `array` / `other`

### 5.8 論理名

物理名（DB 上の名前）とは別に、人が読むための**論理名**を持つ。設定場所が複数あるため、解決順序を1箇所（ビューアの `model/` 層）に実装し、全画面がそれを使う。

#### 5.8.1 解決順序

| 対象 | 優先順位（上が優先） |
|---|---|
| テーブル論理名 | 1. `meta.displayName` → 2. 物理名 |
| カラム論理名 | 1. そのテーブルの `meta.columns.<name>.displayName`（個別設定）→ 2. `dictionary.columns[<name>]`（横断辞書）→ 3. 物理名 |

- **テーブル論理名はテーブル編集画面から設定する。**
- **カラム論理名は横断辞書（`#/columns`）で一括設定するのが基本**で、テーブル固有の事情がある場合のみテーブル編集画面で個別に上書きする。
- 表示は「論理名 / 物理名 / 併記」を切り替えられる（個人設定）。既定は併記。

#### 5.8.2 コメントからの初期値補完（逆生成時）

逆生成の**適用時**に限り、サーバーは以下を行う。`meta` に対する唯一の書き込みであり、**既存値は決して上書きしない**。

| 対象 | 補完元 | 条件 |
|---|---|---|
| `meta.displayName`（テーブル） | `comment`（`getTables().REMARKS`）の1行目 | `meta.displayName` が未設定で、コメントが空でないとき |
| `meta.columns.<name>.displayName` | そのカラムの `comment`（`getColumns().REMARKS`）の1行目 | 同カラムの `displayName` が未設定で、辞書にも登録が無く、コメントが空でないとき |

- 補完は「初期値の種まき」であり、以後は人の編集が常に勝つ。差分プレビューでは補完される論理名も提示し、承認の対象とする。
- コメントに改行がある場合、1行目のみを論理名とし、全文は `comment` に残る（`comment` は machine-owned のまま）。

### 5.9 `data/diagrams/core.js`（ER視覚情報 = 1ページ）

```js
ERD.diagram({
  id: "core",
  title: "コアドメイン",
  order: 1,
  nodes: {
    "public.users":         { pos: [120, 80],  w: 260 },
    "public.orders":        { pos: [520, 80] },
    "public.organizations": { pos: [120, 400] },
  },
  edges: {
    "public.users#fk:users_org_id_fkey": { waypoints: [[380, 200], [300, 320]] },
  },
});
```

- **ページ = ダイアグラムファイル1枚。** 描画オブジェクト数を抑える単位であり、Git のコンフリクト局所化の単位でもある。
- ノードのキーはテーブルID（`schema.table`）。これがスキーマ情報と視覚情報を結ぶ唯一の接点。
- **エッジのキーは `<テーブルID>#<種別>:<制約名>`**（`fk` = 物理 FK、`lfk` = 論理外部制約）。種別を挟むのは両者で制約名が衝突しうるため（§5.5）。制約名を変更した場合はこのキーも書き換える（waypoints を失わないため）。
- ノードはテーブル名のみを描画するため、**折りたたみ状態（`collapsed`）は持たない**。`w` は名前が長い場合の幅の明示指定にのみ使う（省略時は内容に合わせて自動）。
- 同一テーブルを複数ページに配置してよい。
- **ビューポート / ズーム / 選択状態は保存しない**（個人状態は `.erd/` へ）。

### 5.10 テーブルのリネーム耐性

1. 逆生成の差分検出時、削除候補と追加候補の**カラム構成シグネチャ**（カラム名・型・順序のハッシュ）を照合してリネーム候補を推定する
2. GUI の差分プレビューでリネームとして提示する（人が承認・訂正できる）
3. 承認時、サーバーが `data/schema/**` と `data/diagrams/**` の**両方をアトミックに書き換える**
4. 参照先を失った孤児ノードは自動削除せず、ビューア上で警告表示する。除去は明示操作でのみ行う

### 5.11 書式規約（Git 差分の最適化）

サーバー側の決定論的プリンタで強制する。

- **1カラム = 1行**（compact object 形式）。カラム型の変更が1行差分になる
- キー順は固定。省略可能なキーはデフォルト値と一致する場合に省略する（ただし `nullable` は可読性のため常に出力する）
- **配列**の順序は DB の物理順（`ORDINAL_POSITION` / `KEY_SEQ`）を維持する。アルファベット順にしない
- **マップ**（`nodes` / `edges` / `manifest.tables` / `dictionary.columns` …）は**キーの昇順**（Unicode コードポイント順。ロケール依存のソートを使わない）。座標を変えても行が移動せず、差分が1行に収まる
- インデントは2スペース、末尾カンマあり（末尾要素の追加が1行差分で済む）
- **座標はグリッドスナップ（8px）+ 整数化**。ドラッグ由来の微小差分を発生させない
- 改行コードは LF、末尾に改行1つ、UTF-8（BOM なし）
- **日本語をエスケープしない**（`\uXXXX` にしない）。Git 差分が読めることが、このデータ形式の存在意義である
- **`U+2028` / `U+2029` は必ずエスケープする**（JavaScript の文字列リテラル内で改行として扱われ、ファイル全体が構文エラーになるため）
- **JS の予約語・記号を含むキーはクォートする**（カラム名が `default` のときにファイルが壊れないように）

**エスケープ規則・キー順・省略規則・ソート順の完全な仕様は、[詳細設計: フェーズ0](function-details/Phase0_model-printer-index.md) §2 を参照。** Java（サーバー）と TypeScript（H-13 のエクスポート）の二重実装になるため、同一の golden fixture による出力一致を CI で保証する。

### 5.12 サーバー側の読み書き実装

**読み込み**: ラッパ（`ERD.table(` … `);`）を剥がし、Jackson でオブジェクトリテラルをパースする。JS パーサの自前実装は不要。

```java
ObjectMapper mapper = JsonMapper.builder()
    .enable(JsonReadFeature.ALLOW_UNQUOTED_FIELD_NAMES)
    .enable(JsonReadFeature.ALLOW_SINGLE_QUOTES)
    .enable(JsonReadFeature.ALLOW_TRAILING_COMMA)
    .enable(JsonReadFeature.ALLOW_JAVA_COMMENTS)
    .build();
```

**書き込み**: モデル → 決定論的プリンタ（自前実装）で全文生成 → 一時ファイルへ書き出し → `ATOMIC_MOVE` で置換する。

**未知キーの保持（前方互換）**: パース時に**モデルが知らないキーを捨てない**。`unknown` マップに退避し、プリンタが元の位置に書き戻す。これがないと、新しいバージョンのツールが書いたフィールドを古いツールが黙って消す（「開いて閉じただけで情報が失われる」）。この保持があるからこそ、**キーの追加では `schemaVersion` を上げなくてよい**（§3.5）。

## 6. ロード設計（インクリメンタルロード）

連結バンドルは作らない。ローダーは `<script>` タグを動的注入し、`onload` / `onerror` で完了を待つ。**この経路は静的モード / サーバーモードで共通である**（§4.3）。

### 6.1 ロード順序

**ER図のノードがテーブル名のみになったことで、ER図の描画にスキーマファイルは不要になった**（ノード名・リレーションはいずれも `index.js` に含まれる）。スキーマファイルは詳細ダイアログ / テーブルカタログを開いたときに初めて必要になる。

| 段階 | 読み込むもの | この時点で可能なこと |
|---|---|---|
| 1 | `data/manifest.js` | バージョン検証、ページ一覧の描画 |
| 2 | `data/index.js` + `data/dictionary.js` | テーブル一覧・検索・サイドバーの描画。論理名の解決 |
| 2' | `data/config.js`（**サーバーモードのみ**） | 無視リストの表示・編集。閲覧には不要なため静的モードではロードしない |
| 3 | 表示対象ページの `data/diagrams/<id>.js` | **ER図の初回描画完了**（ノード = テーブル名、エッジ = `index.relations`） |
| 4 | 選択されたテーブルの `data/schema/**.js`（オンデマンド、1件） | 詳細ダイアログ / テーブル詳細画面の表示 |
| 5 | 残りの全テーブル（アイドル時にバックグラウンドで順次） | カタログの全項目表示、カラム単位の全文検索、論理名一括編集画面の即時化 |

### 6.2 実装方針

- 段階3までで ER図は完成する。ここまでに読むファイルは**4本のみ**（manifest / index / dictionary / 対象ページ）で、テーブル数が増えても増えない
- 段階4はオンデマンド。ダイアログを開いた瞬間にロードし、それまではスケルトン表示（数十msで解決するため、ローディング画面は出さない）
- 段階5は `requestIdleCallback`（未対応環境は `setTimeout`）でチャンク実行し、UI をブロックしない。並列度は 8 程度に制限する
- カタログ / 一括編集画面を段階5の完了前に開いた場合は、必要なテーブルの優先度を上げて先行ロードし、到着した行から順次描画する（プログレッシブレンダリング）
- ロード済みテーブルは `Map<tableId, Table>` にキャッシュし、二重ロードしない
- ロード失敗（ファイル欠損）は握りつぶさず、「欠損テーブル一覧」としてビューア上に表示する
- 進捗は上部の細いプログレスバーで表示する（初回描画をブロックするローディング画面は出さない）

### 6.3 性能方針

- 1ページあたりのテーブル数は **100 以下**を推奨とし、超過時は GUI で警告する
- 総テーブル数 1000 規模でも、初回描画に必要なのは「manifest + index + dictionary + 1ページ分」に限定されるため高速に保たれる
- ノードがテーブル名のみになったことで1ノードあたりの DOM 数が大幅に減り、俯瞰時の描画コストも下がる（LOD による描画粒度の切替は不要になった）

## 7. スキーマ逆生成

### 7.1 2層構成

```java
// 層1: JDBC 標準。DatabaseMetaData のみを使用し、すべてのドライバで動作する
public interface Introspector {
    RawSchema introspect(Connection conn, IntrospectOptions opts) throws SQLException;
}

// 層2: 任意。DB固有情報を追加SQLで補完する。ServiceLoader で発見する
public interface DialectEnhancer {
    boolean supports(DatabaseMetaData md);              // getDatabaseProductName() で判定
    void enhance(Connection conn, RawSchema schema) throws SQLException;
}
```

- **層1だけで最低限動作する。** JDBC ドライバの jar を `drivers/` に置くだけで、未知の DB にも対応できる
- 層2は PostgreSQL / MySQL 用を同梱する。新規 DB の対応は「ドライバを置く」だけで済み、Enhancer の追加は任意

### 7.2 ドライバのロード

`DriverManager` は呼び出し元のクラスローダーから見えるドライバしか使わないため、`drivers/*.jar` を動的に読む場合はラッパ経由で登録する。

```java
URLClassLoader cl = new URLClassLoader(driverJarUrls, Main.class.getClassLoader());
for (Driver d : ServiceLoader.load(Driver.class, cl)) {
    DriverManager.registerDriver(new DriverShim(d));  // Driver へ委譲するだけの薄いラッパ
}
```

- ロード済みドライバの一覧（クラス名・バージョン）は `GET /__erd/drivers` で返し、GUI に表示する
- クラスパス指定（起動方式B）で読み込まれたドライバも同様に列挙する

#### 7.2.1 ドライバの取得（Maven ダウンロード）

**ドライバは配布物に同梱せず、逆生成画面から Maven 経由でダウンロードする。** これにより
再配布に伴うライセンス問題（MySQL は GPLv2 + FOSS 例外、Oracle は proprietary な OFUTC）を避け、
配布 ZIP を小さく保つ。狙いは「**設定（何を・どのバージョンで）はチーム共有、jar の実体と接続情報は各自**」。

| 何を | どこに置くか | 共有 |
|---|---|---|
| 使うドライバの座標・バージョン・Maven リポジトリ | `data/config.js` の `drivers`（Git 管理） | ✅ チーム共有 |
| jar の実体 | `drivers/*.jar`（`.gitignore`） | ❌ 各自ダウンロード |
| 接続情報・パスワード | `.erd/`（Git 管理外） | ❌ 個人 |

- 既定で提示するドライバと既定バージョンは `DriverCatalog`（build.gradle.kts の testImplementation と揃える）
- `config.js` の `drivers`:

  ```js
  ERD.config({
    drivers: {
      mavenRepository: "https://repo1.maven.org/maven2",  // 省略時は既定（Maven Central）
      artifacts: [
        "org.postgresql:postgresql:42.7.4",               // group:artifact:version
      ],
    },
  });
  ```

- `GET /__erd/drivers` は「ロード済み・カタログ・config の設定・未取得（`missing`）」を返す。
  逆生成画面の入口で `missing` が空でなければダウンロードの確認を出す（他メンバーの初回導線）。
- `POST /__erd/drivers/download` が Maven からダウンロード → `.sha1` 照合 → `drivers/` へ保存 →
  `DriverShim` 経由で登録（**サーバー再起動なし**）。座標は `group:artifact:version` を厳格な
  文字集合に限定し、パストラバーサルを禁止。リポジトリ URL は http(s) のみ許可。
- カタログに無い DB は、`config.js` に座標を足すか、jar を直接 `drivers/` に置く（従来どおり）。

### 7.3 標準メタデータで取得する情報

| 情報 | API | 使用する列 |
|---|---|---|
| テーブル一覧・コメント | `getTables()` | `TABLE_SCHEM` `TABLE_NAME` `REMARKS` |
| カラム | `getColumns()` | `COLUMN_NAME` `TYPE_NAME` `DATA_TYPE` `COLUMN_SIZE` `DECIMAL_DIGITS` `IS_NULLABLE` `COLUMN_DEF` `ORDINAL_POSITION` `REMARKS` `IS_AUTOINCREMENT` `IS_GENERATEDCOLUMN` |
| 主キー | `getPrimaryKeys()` | `COLUMN_NAME` `KEY_SEQ` |
| 外部キー | `getImportedKeys()` | `FK_NAME` `FKCOLUMN_NAME` `PKTABLE_*` `UPDATE_RULE` `DELETE_RULE` |
| インデックス / ユニーク | `getIndexInfo(approximate=true)` | `INDEX_NAME` `NON_UNIQUE` `COLUMN_NAME` `ORDINAL_POSITION` |
| ネームスペース | `getSchemas()` / `getCatalogs()` | 空の場合は catalog にフォールバック |

**性能**: テーブル単位で `getColumns` を呼ぶと N 回の往復が発生する。`getColumns(catalog, schema, "%", "%")` で**一括取得し、メモリ上でテーブル別に分配**する。`getIndexInfo` は API 仕様上テーブル単位のため、対象テーブルに限定して並列実行する。

### 7.4 DB 差異の吸収

| 項目 | 対応 |
|---|---|
| MySQL は catalog = データベース、PostgreSQL は schema | `Namespace` として抽象化。`getSchemas()` が空なら catalog を使う |
| MySQL のコメント・メタデータ精度 | JDBC URL に `useInformationSchema=true` を推奨（GUI の URL テンプレートに既定で含める） |
| MySQL の `unsigned` | `TYPE_NAME` が `INT UNSIGNED` を返す。パースして `dialect.unsigned` に退避 |
| MySQL の `tinyint(1)` | `logicalType: "bool"` に正規化。`type` は原文を保持 |
| PostgreSQL の配列型 | `TYPE_NAME` の `_` 接頭辞から判定し `logicalType: "array"`、`dialect.elementType` に退避 |
| CHECK 制約 | JDBC 標準に API が存在しない。Enhancer で取得 |
| ユニーク制約とユニークインデックスの区別 | 標準では不可。区別せず扱う |
| 部分インデックス・式インデックス | 標準では不可。Enhancer で取得 |
| PostgreSQL の ENUM 型 | Enhancer で値一覧を取得し `dialect.enumValues` に格納 |

### 7.5 接続 UI

JDBC を採用したことで、DB ごとの接続フォーム定義は不要になる。**共通フォーム1つ**とする。

| 項目 | 内容 |
|---|---|
| JDBC URL | 既知ドライバにはテンプレートを提示（例: `jdbc:postgresql://localhost:5432/mydb`、`jdbc:mysql://localhost:3306/mydb?useInformationSchema=true`） |
| ユーザー / パスワード | パスワードは既定で保存しない |
| 追加プロパティ | key-value の任意追加 |
| 対象ネームスペース | 接続後に取得した一覧から**1つだけ**選択する（1プロジェクト = 1スキーマ。§1.2）。ここが唯一のスキーマ指定箇所であり、以後 GUI にスキーマ名は出ない |
| テーブルのフィルタ | **今回の内省に限った**包含 / 除外パターン |

**テーブルのフィルタと無視リスト（§5.4）は役割が異なる。**

| | テーブルのフィルタ（接続設定） | 無視リスト（`config.js`） |
|---|---|---|
| 有効範囲 | その回の内省のみ | プロジェクトに永続（Git 管理・チームで共有） |
| 既存定義への作用 | **なし**（除外したテーブルの既存定義は「対象外」として差分から除かれるだけ） | **あり**（既存定義があっても比較せず、削除候補にしない） |
| 主な用途 | 一時的に一部スキーマだけ取り込む | 管理テーブルの恒久除外、手動定義テーブル（J-01）の保護 |

### 7.6 GUI フロー

1. 接続情報を入力 → 接続テスト（ドライバ・DB製品名・バージョンを表示）
2. **対象スキーマ（1つ）**とテーブルフィルタを選択（§7.5）
3. 逆生成を実行 → **差分プレビュー**（追加 / 削除 / 変更をツリー表示。リネーム候補を提示し、承認・訂正できる。コメントから補完される論理名の初期値もここに提示する）。**無視リスト（§5.4）にマッチするテーブルは、DB 側・既存定義側の双方から除外され、件数のみ表示される**
4. 「適用」で `data/schema/**` を書き換え、`manifest.js` / `index.js` を更新。あわせて未設定の論理名をコメントから補完する（§5.8.2）
5. 新規テーブルは **「未配置」トレイ**に入る。ページへドラッグするか、自動配置ボタン（ELK）で配置する
6. 削除されたテーブルのノードは自動削除せず、警告表示のうえ明示操作で除去する

**この一連の処理で `data/diagrams/**`・`data/dictionary.js`・`data/config.js` は一切書き換えない。** 配置・論理名辞書・プロジェクト設定は人の操作としてのみ記録される（`meta.displayName` の初期値補完は §5.8.2 の条件下でのみ行われる）。

> 差分検出・リネーム推定・部分適用・適用のアトミック性の詳細は、[詳細設計: K-08〜K-13（逆生成の差分プレビューと適用）](function-details/K08-K13_introspect-diff-apply.md) を参照。

## 8. サーバー API

### 8.1 起動

- ポート `5321`（使用中なら自動インクリメント）、`127.0.0.1` のみに bind
- 起動時にランダムトークンを生成し、`http://127.0.0.1:5321/?t=<token>` をブラウザで自動オープン
- サブコマンド・フラグは持たない。以降の操作はすべて GUI

### 8.2 エンドポイント

**データ本体は API で返さない**（§4.3。`GET /data/**.js` の静的配信を `<script>` で読む）。以下の API は、書き込みと、書き込みに必要なメタ情報のためだけに存在する。

| PATCH | `/__erd/diagrams/:id` | レイアウトの差分保存（変更されたキーのみを送る） |
| POST | `/__erd/layout/auto` | ELK による自動配置の座標を返す（**書き込みしない**。適用は PATCH で行う） |
| GET | `/__erd/events` | SSE。ファイル変更を配信（§8.7） |

- **差分プランはリネーム決定に依存する**（承認すれば1項目の「リネーム」、却下すれば「削除 + 追加」の2項目になる）。決定が変わるたびに `POST /__erd/introspect/:sessionId/plan` でサーバーが再計算し、**差分ロジックをビューアに二重実装しない**。内省結果はセッションのスナップショットであり、この再計算で DB へ再接続することはない。
- **`PUT /__erd/tables/:id` の後は、何が変わったかを判定せず、無条件に `index.js` を再生成する。** 論理名・タグ・論理制約はいずれも `index.js`（`tables[].displayName` / `relations`）に影響し、条件分岐で最適化すると必ず漏れる（論理外部制約を保存したのに ER図に破線エッジが現れない、等）。生成コストは小さい。
- サーバーが停止している状態での書き込み要求はネットワークエラーとなる。ビューアはこれを**保存失敗**として扱い、接続エラーのメッセージと再試行を提示する（モードを勝手に切り替えたりはしない）。

### 8.3 書き込みの共通規約

**すべての書き込み API**（`PATCH /diagrams/:id`、`PUT /tables/:id`、`PUT /dictionary`、`PUT /config`、`POST /introspect/apply`、`POST/DELETE /diagrams`）に、以下を共通で課す。

| 要素 | 内容 | 違反時 |
|---|---|---|
| `baseHash` | **書き込み対象ファイルの、読み込み時点での内容ハッシュ**。必須 | `409 STALE` |
| `force` | `true` のとき `baseHash` の検証をスキップする（ユーザーが「上書き」を明示的に選んだ場合のみ） | — |

**編集ロックは設けない。** ローカル単独利用であり、不整合は「稀な例外」として保存時の `baseHash` 検証（§8.4）で止め、複数タブ / 外部の同時変更は §8.7 のバナー通知で検知する（ロックによる事前排他はしない）。

- 書き込みは常に**1本に直列化**する（クライアント側で保証。飛行中の要求が完了するまで次を送らない）。並行して投げると、後から届いた古い値が新しい値を上書きする。
- サーバーは書き込み時に**リビジョンID**を払い出し、SSE イベントに含める。ブラウザは自分が起点のリビジョンを無視することで、「書き込み → 監視検知 → 再読込」の無限ループを防ぐ。

### 8.4 保存時の競合検出（`baseHash`）

**競合の検出は書き込む瞬間にのみ行う。** 編集中はサーバーへ問い合わせない（ローカル単独利用であり、編集のたびに整合性を確認する必要がない）。

サーバーは書き込み直前に**ディスク上の実ファイルを読み直して内容ハッシュを計算**し、`baseHash` と一致しなければ**1バイトも書かずに `409 STALE` を返す**。これにより、`git pull` / エディタでの直接編集 / 逆生成の適用による外部変更を、黙って踏み潰すことがなくなる。

**判定は最終更新日時（mtime）ではなく内容ハッシュ（SHA-256）で行う。**

| 方式 | 問題 |
|---|---|
| mtime | `git checkout` は**内容が同じでも mtime を更新する**（誤検知 → 保存できない）。逆に、ファイルシステムの時刻解像度により**同一秒内の変更を取りこぼす**（検知漏れ → 外部変更を踏み潰す）。検知漏れは許容できない |
| **内容ハッシュ（採用）** | 誤検知も検知漏れもない。対象ファイルは数 KB であり、計算コストは無視できる |

> 実装上の最適化として、`mtime` と `size` が読み込み時と同一ならハッシュ計算を省略してよい（内容が変われば必ずどちらかが変わるため、検知漏れは生じない）。

`409 STALE` を受けたビューアは、**[再読込して自分の変更を破棄] / [自分の内容で上書き保存]** をユーザーに選ばせる。**自動でどちらかを選ばない。**

### 8.5 セキュリティ

- `127.0.0.1` バインド、トークン必須、`Origin` ヘッダ検証、CORS 無効
- ファイル書き込みは `erd/data/` 配下に限定する（パストラバーサル禁止）
- DB 認証情報は既定でメモリ保持のみ。保存する場合は `.erd/connection.local.json`（Git 管理外）とし、パスワード保存は明示的なオプトインとする

### 8.6 複数ファイルに跨る書き込みのアトミック性

逆生成の適用（K-11）は `schema/**`（複数）+ `manifest.js` + `index.js` + リネーム時は `diagrams/**`（複数）を**同時に**書き換える。1ファイルずつ置換すると「manifest だけ新しく schema は古い」中間状態が生じ、その隙間にファイル監視 → SSE → 再読込が走るとビューアが壊れた状態を読む。

- **適用前に `data/**` の全体を `.erd/backup/<timestamp>/` へコピーする**（Git 管理外。直近3世代をローテーション）
- 完成形を一時ディレクトリに生成 → 検証 → `ATOMIC_MOVE` で順次置換 → 削除対象を削除
- **置換中は SSE の配信を抑止し、完了後に単一のリビジョンとしてまとめて通知する**
- 途中で失敗した場合はバックアップから復元し、**適用前の状態に完全に戻す**（部分適用された壊れた状態を残さない）

詳細は [詳細設計: K-08〜K-13](function-details/K08-K13_introspect-diff-apply.md) §6 を参照。

### 8.7 別タブ・外部変更の検知（バナー通知）

**編集ロックは設けない**（§8.3）。同一ブラウザの複数タブ、`git pull` / エディタでの直接編集、逆生成の適用は、いずれも SSE（`GET /__erd/events`）で検知し、**バナーで再読込を促す**（強制はしない。無視して編集を続けられる）。

- サーバーは書き込み時に**リビジョンID**を払い出し、SSE イベント `{ revision, files }` に含める。各タブは自分の書き込みリビジョンを**リングバッファ（直近20件）**に保持し、SSE の `revision` がそこにあれば**自分起因として無視する**（「書き込み → 監視検知 → 再読込」ループの防止）。**タブごとの ID は持たない**（自分のリビジョン集合で「自分か / 他者（別タブ・外部）か」を判別できる）。
- 未知のリビジョンは「他者の変更」として扱い、ビューアが分岐する（詳細は [H-09](function-details/H01-H13_layout-edit-sync-undo.md) §6）:
  - **閲覧中で未保存がない画面** → 静かに再読込する（バナーを出さない）。
  - **編集ルート滞在中の画面** → **バナー[再読込]/[無視]** を表示する。他の通知より重要度が高いためトーストではなくバナーとする。[再読込] を選び未保存があれば破棄を確認する。
- **バナーは二重に開かない**（既に表示中なら対象ファイルを追記する）。**「このタブ内では通知しない」チェック**を設け、選択は `sessionStorage`（タブを閉じるまで有効）に保持する。
- 最終的な安全網は保存時の `baseHash` 検証（§8.4）である。バナーを無視して古い状態のまま保存を試みても、`409 STALE` で止まり、破棄 / 上書きを選べる（人の変更を黙って消さない）。

## 9. ER図ビューア / エディタ

### 9.1 ER図とテーブルカタログの分離

**ER図は「テーブル間の関係の俯瞰」に責務を限定し、テーブルの中身は別画面（テーブルカタログ）で扱う。**

| | ER図 | テーブルカタログ |
|---|---|---|
| 目的 | 関係の俯瞰・探索 | 定義の閲覧・編集 |
| 描画単位 | **テーブル名のみのノード** + リレーション線 | 表形式の一覧 / 1テーブルの全定義 |
| ルート | `#/erd/<diagramId>` | `#/tables`, `#/tables/<id>`, `#/tables/<id>/edit` |
| 編集 | 配置（座標・ページへの追加 / 除去）のみ | スキーマ・論理名・論理制約・注記 |

- **ER図のノードにカラムを描画しない。** ノードはテーブル名（論理名 / 物理名）とスキーマ名のみを表示する。
- ノードを**ダブルクリック**すると、テーブル詳細を**閲覧専用のダイアログ**で表示する。ダイアログにはテーブル詳細画面（`#/tables/<id>`）への実リンクを置き、編集はそちらで行う。
- リレーション線を**ダブルクリック**すると、リレーション詳細（種別・参照元 / 先・カラム対応・ON DELETE / UPDATE・カーディナリティ）をダイアログで表示する。両テーブルの詳細画面へのリンクを含む。
- テーブル詳細画面からは、そのテーブルが配置されている ER図ページへのリンクを提供する（複数ページに配置されている場合はページを選択させる）。

この分離により、ER図の描画コストとロード依存が大きく下がる（§6.1）。

### 9.2 キャンバス

**React Flow を使用する。Canvas / WebGL 方式は採用しない。**

ノードはテーブル名のみだが、ホバー・テキスト選択・検索ハイライト・リンク（`<a href>`）・キーボード操作・スクリーンリーダー対応を要するため、DOM / SVG 描画が有利である。ページ分割により1ページあたりのノード数を抑えるため、性能上の問題は生じない。

### 9.3 ズーム / パン

React Flow の標準機能（d3-zoom ベース）を使用する。

- ホイールズーム、ピンチズーム、ドラッグパン
- `Controls`（ズームイン / アウト / フィット / ロック）と `MiniMap` を配置
- ズーム範囲は `minZoom: 0.1`, `maxZoom: 2.5`。初期表示は `fitView`

**LOD（ズーム率による描画粒度の切替）は行わない。** ノードは常にテーブル名のみであり、切り替える粒度が存在しない。

### 9.4 ノードとエッジの表現

| 要素 | 表現 |
|---|---|
| ノード | テーブル名（論理名 / 物理名 / 併記を切替可）のみ。**スキーマ名は表示しない**（単一スキーマ前提。§1.2）。タグ / 指定色でヘッダを着色 |
| 物理 FK エッジ | **実線**。鳥の足記号でカーディナリティを表示 |
| 論理 FK エッジ（`meta.logicalForeignKeys`） | **破線**。凡例で物理 FK との違いを明示 |
| 複合キー | 1本のエッジに集約（カラム対応はダブルクリックの詳細ダイアログで確認する） |

### 9.5 性能最適化

- ノードコンポーネントの `React.memo` 化
- `onlyRenderVisibleElements: true`
- ドラッグ中は再レンダリングを抑制し、確定時のみ状態を更新する

|---|---|---|

| DB からの逆生成 | ✗ | ✓ |

### 9.7 静的モードでの編集とエクスポート

静的モードでも編集セッションを開始でき、ドラッグ・整列・Undo はすべて動作する。**保存手段がないため、変更は「配置のエクスポート」で持ち出す。**

- 編集開始時に「変更は保存できません。エクスポートして `data/diagrams/*.js` に貼り付けてください」と警告する
- エクスポートは、現在の配置を **`ERD.diagram({...})` の生の JavaScript コードとしてダイアログに表示**し、全選択・コピーできるようにする（`file://` ではダウンロードの挙動が環境依存のため、貼り付け方式の方が確実）
- 自動レイアウト（ELK）はサーバー API に依存するため静的モードでは使えない
- リロード・離脱で変更は消える（**離脱時の警告は出さない**。保存手段がなく、警告しても行動を変えられないため。代わりにエクスポート導線を常時表示する）

> **実装上の注意**: これはクライアント側にも決定論的プリンタ（§5.11 の書式規約）が必要であることを意味する。サーバー（Java）とクライアント（TS）で**二重実装**になるため、**両者に同一の golden ファイルによるテストを課し、同じ入力から同じ文字列が出ることを CI で保証する**。ズレた場合の実害は「貼り付けたファイルが次回のサーバー保存時に整形し直され、余計な Git 差分が1回出る」程度だが、放置すると差分ノイズの原因になる。

### 11.1 リスクと対策

| リスク | 対策 |
|---|---|
| 書き戻しで人の注記・論理名・論理制約が失われる | それらを `meta` に構造化し、逆生成の対象外とする。フェーズ0の往復テストで保証する。唯一の例外（未設定時の論理名補完）は「既存値を上書きしない」を単体テストで固定する |
| ドラッグ由来の差分ノイズ | 座標のグリッドスナップ + 整数化を初期実装から入れる（後付けすると全ファイルが一度書き換わる） |
| `index.html` とデータ形式の不整合 | `schemaVersion` による検証と警告バナー |
| ドライバごとの `DatabaseMetaData` 実装差異 | Testcontainers で実DBに対する内省を CI で検証する。層1で取得できない情報は Enhancer に隔離する |
| `drivers/*.jar` のドライバが `DriverManager` から見えない | `DriverShim` によるラッパ登録で対応する |
| 1つの巨大ER図への集約による破綻 | ページを一級の概念として初期から設計する |
| 書き込み → 監視 → 再読込のループ | リビジョンIDのエコーバックによる自己起因変更の無視 |
| 論理名の解決順序（個別 / 辞書 / 物理名）が画面ごとにズレる | 解決ロジックをビューアの `model/` 層の単一関数に集約し、全画面がそれを経由する |
| `index.js` の `relations` とスキーマファイルの不整合 | `index.js` はサーバーが `schema/**` から必ず再生成する派生ファイルとし、手編集を許さない。整合性チェック（M-04）で検出する |
| 疑似リンク（`onClick` のみ）の混入で Ctrl+クリックが効かない | 遷移を伴う UI は共通の `<Link>` コンポーネントに限定し、Playwright で修飾キー付きクリックの挙動を検証する |
| 外部変更（`git pull` / エディタ編集）を保存が踏み潰す | すべての書き込みに `baseHash`（読み込み時の内容ハッシュ）を必須とし、不一致なら書かずに中止する（§8.4） |
| 決定論的プリンタの二重実装（Java / TypeScript）による出力のズレ | 同一の golden ファイルによるテストを両実装に課し、CI で出力の一致を保証する（§9.7） |
