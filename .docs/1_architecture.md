# ER図管理ツール 設計書

## 1. スコープ

### 1.1 動作モード

| モード | 起動方法 | 必要な環境 | 提供機能 |
|---|---|---|---|
| **静的モード** | `erd/index.html` をブラウザで開く（`file://`） | **なし**（ブラウザのみ） | ER図の閲覧（ノードはテーブル名のみ）、ページ切替、パン / ズーム、検索、リレーション追跡、テーブル / リレーションの詳細ダイアログ、テーブルカタログ（一覧・詳細）の閲覧。**ER図の配置編集も可能だが保存はできず、エクスポート（生の JS コードを表示・コピー）で持ち出す** |
| **サーバーモード** | `java -jar erd-server.jar` | Java 17+ | 静的モードの全機能 + DBからのスキーマ逆生成、スキーマ / 論理名 / 論理制約の編集、カラム論理名の横断一括編集、ドラッグによるER図更新とファイル保存、ページ管理、自動レイアウト、**MCP による AI クライアント連携**（既定オフ。§8.8） |

**「動作モード」と「編集セッション」は直交する別概念である。** 動作モードは起動方法で決まる（上表）。編集セッション（閲覧中 / 編集中）はユーザーが明示的に切り替えるもので、**静的モードでも編集セッションを開始できる**（§9.7）。

**このツールはローカルで単独利用する前提とする。** 複数人による同時編集は考慮しない（サーバーは `127.0.0.1` にのみ bind される）。競合は「稀な例外」として扱い、**保存時に検出して中止し、人が再操作して復旧する**設計とする（§8.6）。

### 1.2 非スコープ

- CLI による**編集操作**（全操作を GUI で提供する）。サブコマンドは `run` と `export` の 2 つに限る。`export`（閲覧用 ZIP の書き出し）だけは、サーバーを起動せずに成果物を作るという GUI で表現できない操作のため CLI に置く（§3.2）
- ネイティブバイナリの配布
- npm / npx によるツール配布
- **MCP サーバーの別プロセス配布**（stdio トランスポート / npm パッケージ）。MCP は**既存 Web サーバーのエンドポイント**として提供し、ライフサイクルを分けない（§8.8）
- サーブレットコンテナ（Tomcat 等）へのデプロイ
- クラウド / 共有サーバーでのホスティング
- **複数人による同時編集**（差分マージ・OT・CRDT の類は導入しない）
- **複数スキーマ（ネームスペース）の同時管理**。**1プロジェクト = 1スキーマ**とし、対象スキーマは逆生成の設定で指定する。GUI にスキーマ名は表示しない（全テーブルで同じ値であり、ノイズにしかならない）。ただしテーブルID は `schema.table` の形式を維持する（将来の拡張余地と ID 衝突の回避のため）
- **画像・文書のエクスポート**（PNG / SVG / 印刷 / Mermaid / Markdown 定義書）。ブラウザのスクリーンショット・印刷で代替する
  - **例外**: 静的モードで編集した配置を持ち出すための「配置のエクスポート」（`ERD.diagram({...})` の生コードをダイアログに表示・コピー）は提供する。静的モードにおける唯一の保存手段であるため（§9.7）
- **DDL ファイル（`CREATE TABLE`）からの取り込み**。スキーマの入力元は JDBC 接続と GUI の手動編集に限定する
- **逆生成の実行履歴の保持**
- **利用者のリポジトリの `.gitignore` の自動検査 / 自動追記**。代わりに配布 ZIP に `.gitignore` / `.gitattributes` を同梱して `erd/` 直下に配り（§3.1）、**ツールが作るファイルはすべて `erd/` の中に収める**ことで、利用者側の設定作業をゼロにする

### 1.3 対応DB

**JDBC ドライバがあれば原則すべての DB に対応する。**

| DB | 対応レベル |
|---|---|
| PostgreSQL | 同梱ドライバ + Dialect Enhancer（DB固有情報の追加取得） |
| MySQL | 同梱ドライバ + Dialect Enhancer |
| その他（SQL Server, Oracle, SQLite, H2 …） | **ユーザーが JDBC ドライバの jar を追加するだけで、JDBC 標準メタデータの範囲で動作する**。必要に応じて Enhancer を後から追加 |

### 1.4 横断機能要件

全機能に共通してかかる要件。個別機能の設計はこれに従う。

#### 1.4.1 言語対応（i18n）

- **日本語 / 英語**の2言語に対応する。
- 初期言語は**ユーザーの環境設定に従う**（ブラウザの `navigator.languages` を評価し、`ja` で始まるなら日本語、それ以外は英語）。GUI から明示的に切り替えることもでき、選択は個人設定として保持する（静的モードではメモリ、サーバーモードでは `erd/.local/`）。
- UI 文字列はすべて翻訳リソース化し、コード中に直接記述しない。**翻訳リソースはバンドルに内包する**（`file://` では `fetch` による遅延ロードができないため）。
- **翻訳対象は UI 文字列のみ。** DB 由来の識別子・コメント、ユーザーが入力した論理名・注記は翻訳しない（データそのものであり、言語切替で見た目が変わってはならない）。
- 日時・数値の書式は選択言語のロケールに従う。

#### 1.4.2 リンクのブラウザ標準準拠

**画面遷移を伴う要素はすべて実体のあるリンク（`<a href="...">`）として実装する。** `onClick` のみで遷移する疑似リンクを作らない。これにより以下がブラウザ標準の挙動として成立する。

| 操作 | 期待される挙動 |
|---|---|
| Ctrl / ⌘ + クリック、中クリック | 新しいタブで開く |
| Shift + クリック | 新しいウィンドウで開く |
| 右クリック | 「新しいタブで開く」「リンクをコピー」等のコンテキストメニュー |
| ホバー | ステータスバーに URL が表示される |
| ブラウザの戻る / 進む | 履歴を辿れる |

- 実装上、修飾キーなしの左クリックのみ `preventDefault()` してクライアントサイド遷移に置き換える。修飾キー付き・中クリックはブラウザに委ねる。
- 対象となる遷移: ER図ページの切替、テーブル一覧 / 詳細 / 編集画面、ER図上のノード・詳細ダイアログからテーブル詳細画面へのリンク、テーブル詳細画面から ER図 へのリンク、検索結果、リレーションの参照先。
- **URL は `#` ハッシュで表現する**（`file://` では History API による pushState が使えないため）。ルーティング体系は §4.4 を参照。

## 2. 技術選定

### 2.1 バックエンド（サーバーモード）

| レイヤ | 選定 | 備考 |
|---|---|---|
| 言語 | **Java 17 LTS** | Javalin 6 の最低要件。Java 21 でも動作 |
| Webフレームワーク | **Javalin 6**（Jetty 組み込み） | 軽量。Spring は使用しない |
| ビルド | **Gradle + Shadow プラグイン** | 実行可能 fat JAR を生成 |
| データ入出力 | **Jackson**（JSON5 相当の緩和フラグ付き） | §5.12 参照 |
| DB内省 | **JDBC `DatabaseMetaData`**（標準層）+ `DialectEnhancer`（拡張層） | §7 参照 |
| ドライバ管理 | `drivers/*.jar` の自動スキャン + `DriverShim` / クラスパス指定 | §7.2 参照 |
| ファイル監視 | `java.nio.file.WatchService` → Javalin の SSE | |
| 自動レイアウト | **Eclipse ELK（`org.eclipse.elk`, Java実装）** | 新規テーブルの初期配置に使用 |
| MCP 連携 | **自前実装**（JSON-RPC over Streamable HTTP。Javalin に相乗り） | 公式 Java SDK は依存が +3.6 MB（reactor 等）で Jackson の版上げも伴う。§8.8 参照 |
| テスト | JUnit 5 + **Testcontainers**（PostgreSQL / MySQL の実DBで内省を検証） | |

**WAR ではなく実行可能 fat JAR とする。** `java -jar` 実行時は `-cp` が無視されるため、WAR / `-jar` 形式では「実行時のクラスパス追加によるドライバ拡張」が成立しない。Javalin は Jetty 組み込み型であり、サーブレットコンテナを前提としない。

### 2.2 フロントエンド（ビューア / エディタ）

| レイヤ | 選定 | 備考 |
|---|---|---|
| 言語 | TypeScript（strict） | |
| UI | React 19 | |
| ER図キャンバス | **`@xyflow/react`（React Flow, MIT）** | パン / ズーム / ドラッグ / MiniMap / Controls を標準搭載。Canvas / WebGL 方式は採用しない |
| 状態管理 | zustand | Undo / Redo を実装 |
| ルーティング | **ハッシュルーティング（自前の軽量実装）** | `file://` では History API が使えない。§1.4.2 / §4.4 参照 |
| 国際化 | **自前の軽量 i18n**（`ja` / `en` の辞書をバンドルに内包） | `file://` では翻訳リソースを `fetch` できない。ライブラリを入れるほどの規模ではない |
| ビルド | **Vite + `vite-plugin-singlefile`** | 単一 `index.html` を出力 |
| スキーマ検証 | zod | データファイル ⇔ モデルの境界で型を保証 |
| テスト | Vitest + Playwright | |

### 2.3 フロントエンドのビルド制約（静的モードのための必須設定）

`file://` ではクラシックスクリプトしかロードできない。以下を厳守する。

- `build.rollupOptions.output.format: 'iife'`
- コード分割禁止（`inlineDynamicImports: true`）
- `build.target: 'es2019'`
- ビューア本体から **Web Worker / 動的 `import()` / `fetch` を使用しない**
- `localStorage` に依存しない（`file://` の opaque origin で不安定。個人設定（言語・表示設定）は静的モードではメモリ保持、サーバーモードでは `erd/.local/` に保存する）
- **翻訳リソース（ja / en）はバンドルに内包する**（遅延ロード禁止）
- **画面遷移は `#` ハッシュ URL のみで表現する**（`history.pushState` は `file://` で使用不可）。すべての遷移要素を `<a href="#/...">` として実装し、ブラウザ標準のリンク挙動を保つ（§1.4.2）

## 3. 配布 / 運用

### 3.1 配布物

`npm run build`（フロント）と `./gradlew shadowJar`（バック）の成果物を手動で ZIP 化し、**GitHub Releases に手動アップロード**する。

```
ERForge-<version>.zip       例 ERForge-0.3.0.zip（リリースビルド以外は ERForge-0.3.0-dev.zip）
├── erd-server.jar          fat JAR（Javalin + Jetty + Jackson + ELK + core）
├── drivers/                空（README のみ）。JDBC ドライバは各自が取得する
│   └── README.txt
├── index.html              単一HTML（スキーマ情報は含まない）
├── erd.sh / erd.bat        起動スクリプト
├── .gitignore              展開先 erd/ 用。.local/ と drivers/*.jar を除外する（§10）
├── .gitattributes          展開先 erd/ 用。binary 指定と改行コード
├── THIRD-PARTY-NOTICES.txt 同梱 OSS の著作権・ライセンス表示
└── README.md
```

`.gitignore` / `.gitattributes` を **同梱する**のは、利用者に手で書かせると抜けるため。
`erd/` 配下の Git 運用はツール側の都合なので、ツールが持って配る。**この 2 つで設定が完結する
（利用者側のリポジトリの `.gitignore` には一切追記させない）**ことを不変条件とし、そのために
個人データも `erd/.local/` に置く（§3.3）。`erd/` の外に出るファイルを作ってはならない。
なお Gradle（Ant）の Copy / Zip は `.gitignore`・`.gitattributes` を**既定で除外する**ため、
`server/settings.gradle.kts` で `DirectoryScanner.removeDefaultExclude` を呼んで外している。

`THIRD-PARTY-NOTICES.txt` は **`distribution/` に置いた固定ファイル**で、`packageDist` がそのまま
ZIP に入れる。fat JAR と単一 HTML は他者のバイナリを**再配布**しているため（Apache-2.0 の NOTICE
伝播、EPL のソース入手告知）、この同梱が義務を満たす本体になる。information（A-02）の
「Powered by」は謝辞であって、これの代わりにはならない。依存を追加・削除したら手で更新する。

**ZIP 名は `ERForge-<version>.zip`**（アプリ名 + 版）。手元のダウンロードフォルダにも
`build/dist/` にも複数の版が並ぶため、**ファイル名だけでどの版か判別できること**を優先する。
版は `VERSION`（§3.1 の唯一の真実源）から `packageDist` が組み立て、リリースビルド以外は
`-dev` が付くので、開発中の ZIP を誤って配ることも防げる。

> 以前は「展開先を差し替えるだけの運用なのでファイル名は固定（`erd.zip`）」としていたが、
> 取り違えの危険のほうが大きいと判断して改めた。手順書に名前を直書きしたい場合は、
> GitHub Releases の latest へのリンクを使う。

#### リリースバージョンの管理

**リポジトリ直下の `VERSION`（1行）が単一の真実源**。ビルド時に2か所へ焼き込む。

| 対象 | 経路 | 表示 |
|---|---|---|
| `index.html` | `viewer/vite.config.ts` が `VERSION` を読み、`__APP_VERSION__` として define | information（A-02） |
| `erd-server.jar` | `server/build.gradle.kts` が `VERSION` を読み、マニフェストの `Implementation-Version` に入れる | `GET /__erd/health` の `appVersion` |

- **リリースビルド（`build-dist.bat` / `build-dist.sh`）だけが `ERD_RELEASE=1`** を立て、`VERSION` の内容そのものを版にする。それ以外の手元ビルドは `-dev` が付き（例 `0.2.0-dev`）、リリース済みの版と見分けが付く。jar 外実行（`gradlew devServer`）は `dev`
- **`index.html` と `erd-server.jar` は配布 ZIP の中で別ファイル**なので、片方だけ差し替えられて食い違うことがある。ビューアはサーバーモードで両方を表示し、**リリース版どうしで食い違ったときだけ**注意文を出す（開発ビルドは常に食い違うため比較しない）
- **`schemaVersion`（データ形式の版。§3.5）とは独立した軸**。連動させない
- **リリース版をデータファイルに書かない**（`manifest.js` 等）。生成物の差分ノイズになるだけで、データの読み書きには要らない

版の上げ方（`VERSION` の更新）:

| 位 | 上げる場面 |
|---|---|
| MAJOR | `schemaVersion` を上げた（古い `index.html` で読めなくなる）／起動方法・配布構成の非互換変更 |
| MINOR | 機能追加（画面追加、フェーズ機能） |
| PATCH | 不具合修正・表示調整のみ |

リリース手順は README の「リリース」を参照（`VERSION` 更新 → コミット → タグ `vX.Y.Z` → ZIP 生成 → Releases へアップロード）。**タグと `VERSION` は必ず一致させる。**

**JDBC ドライバは配布物に同梱しない。** 代わりに逆生成画面から Maven 経由でダウンロードする
（§7.2）。同梱しないのは意図的で、(1) 再配布に伴うライセンス問題（MySQL は GPLv2 + FOSS 例外、
Oracle は proprietary な OFUTC）を避け、(2) 配布 ZIP を小さく保つため。既定バージョンは
`DriverCatalog`、チーム共有の設定は **全ワークスペース共通**の `erd/config.js` の `drivers` に置く。

### 3.2 起動方法

| 方式 | コマンド | 用途 |
|---|---|---|
| **A. `drivers/` 自動スキャン（既定・推奨）** | `java -jar erd-server.jar` | 追加したいドライバ jar を `drivers/` に置くだけ。OS 差（パス区切り文字）の影響を受けない |
| B. クラスパス指定 | `java -cp "erd-server.jar:drivers/*:/path/to/extra.jar" com.erd.Main`<br>（Windows は `;` 区切り） | 任意の場所の jar を使う場合 |

#### サブコマンド

| コマンド | 動作 |
|---|---|
| `erd.bat` / `./erd.sh`（引数なし）・`run` | サーバーを起動しブラウザを開く。**ダブルクリックの挙動は従来どおり** |
| `erd.bat export [オプション]` | **閲覧用 ZIP** を書き出して終了する（サーバーは起動しない） |
| `help` / `-h` / `--help` | 使い方を表示する |

`export` のオプション（どちらも省略可。`--prefix foo` のような空白区切りも受ける）:

| オプション | 既定 | 意味 |
|---|---|---|
| `--prefix=<名前>` | `ERForge-viewer` | ファイル名の前半。`<prefix>-<timestamp>.zip` になる |
| `--workspaces=<a,b>` | 全部 | 含めるワークスペース。知らない ID を渡したら**何も書かずに**選べる ID を示して終了する |

**サブコマンドはこの 2 つだけとし、編集操作のフラグは足さない**（全操作は GUI。§1.2）。
この線引きを超える要求（例: `erd introspect`）が来たら、CLI ではなく GUI で提供する。

**閲覧用 ZIP**（`<prefix>-<timestamp>.zip`。展開先の直下に作る）は、
**Git も Java も使わない相手に閲覧環境ごと渡す**ためのもの。展開して `index.html` を開けば
静的モード（§9.6）で ER 図・カタログが見られる。中身は閲覧に要るものだけに絞る:

| 入れる | 入れない |
|---|---|
| `index.html`・`workspaces.js`・選んだ `workspace-*/data/**` | `erd-server.jar`・`erd.sh` / `erd.bat`（閲覧に不要） |
| `THIRD-PARTY-NOTICES.txt`（`index.html` の再配布に伴う告知義務。§3.1） | **`.local/`（DB 接続情報。社外に出す ZIP に入れては絶対にならない）** |
| | `drivers/`（再配布のライセンス問題。§7.2）・ルートの `config.js`（ドライバ設定で閲覧に不使用） |
| | `.gitignore` / `.gitattributes`（渡した先で Git 管理しない） |

除外の線引きは**テストで固定する**（`ViewerExportTest`）。ここは「うっかり入った」が
そのまま情報漏洩になる場所なので、実装の副作用で中身が変わらないようにする。

**`workspaces.js` は選択に合わせて作り直す**（ディスク上のものをコピーしない）。静的モードは
ディレクトリを走査できず、このファイル 1 本だけでワークスペースを発見するため、そのまま入れると
**書き出さなかったワークスペースまでプルダウンに並び、選ぶとデータが無くて壊れる**。
表示名はディスク側の値を引き継ぐ。

**GUI（ツールメニュー → 閲覧用 ZIP を書き出す）からも同じことができる**（A-11）。
GUI は `POST /__erd/export/viewer` を呼んでブラウザにダウンロードさせるだけで、
**ZIP を組み立てるのは CLI と同一のコード**（`ViewerExport`）である。名前の規則も除外の線引きも
1 か所にしか無いため、経路によって中身が変わることはない。GUI はサーバーモード専用
（`index.html` 自身を読めるのがサーバーだけであるため）。

GUI では、選択と等価な CLI コマンド（`erd.bat export --prefix="..." --workspaces=...`）を
**常に画面に出してコピーできるようにする**。GUI で 1 回作って終わりにする使い方から、
定期的に作り直す運用へ移りたくなったときに、その場から持ち出せるようにするためである。

ファイル名のプレフィックスは**任意に指定できる**。検査は「実際にファイルを作れない・作ると
事故になるもの」だけを弾く方針で、日本語も空白も通す（`\ / : * ? " < > |`・制御文字・
前後の空白・末尾のドット・Windows の予約デバイス名・64 文字超を拒否）。
**正はサーバー**（`ViewerExport.prefixError`）で、ビューア側（`lib/viewerExport.ts`）の同じ検査は
入力中に赤字を出すための写しである（両者にテストを置き、規則を変えるときは両方を直す）。

### 3.3 プロジェクト側のリポジトリ構成

**データはワークスペース単位**（§3.7）に分かれる。1ワークスペース = 1データベースで、フォルダ名は `workspace-<id>`。

```
<project-repo>/
├── erd/
│   ├── index.html            ← Git 管理する（メンバーは pull するだけで閲覧可能）
│   ├── workspaces.js         ← Git 管理する。ワークスペースの索引（ツール生成物）
│   ├── config.js             ← Git 管理する。全ワークスペース共通の設定（JDBC ドライバ）
│   ├── workspace-sales/      ← Git 管理する（ワークスペース1つ = DB 1つ）
│   │   └── data/
│   │       ├── manifest.js
│   │       ├── config.js     ← このワークスペースの設定（テーブル無視リスト）
│   │       ├── index.js
│   │       ├── dictionary.js ← カラム辞書（同名カラムの共通設定）
│   │       ├── schema/
│   │       │   └── public/
│   │       │       ├── users.js
│   │       │       └── orders.js
│   │       └── diagrams/
│   │           ├── core.js
│   │           └── billing.js
│   ├── workspace-billing/    ← 別の DB（構成は同じ）
│   │   └── data/…
│   ├── erd-server.jar        ← Git 管理する（全員が同じ版を使う）
│   ├── .gitignore            ← Git 管理する（配布 ZIP に同梱。drivers/*.jar のみ除外）
│   ├── .gitattributes        ← Git 管理する（配布 ZIP に同梱）
│   ├── drivers/              ← README.txt は Git 管理する。jar は各自（全ワークスペース共通）
│   │   └── README.txt
│   ├── erd.sh / erd.bat      ← Git 管理する
│   └── .local/               ← Git 管理しない（個人データ。同梱の .gitignore が除外）
│       └── workspace-sales/      ワークスペースごとに分ける
│           ├── connection.local.json  JDBC URL・認証情報
│           └── backup/               逆生成の適用前バックアップ（直近3世代。§8.5）
│               └── 20260711-093012/  data/** の全体コピー
└──（ツールは erd/ の外に一切ファイルを作らない）
```

**`erd/` という名前は規約であって要件ではない。** 利用者は好きな名前・好きな階層に展開できる。
サーバーはカレントディレクトリをルートとして起動し（`Main`。起動スクリプトが自分の置き場所へ `cd` する）、
ビューアの参照はすべて相対で、同梱の `.gitignore` / `.gitattributes` も自分の置かれた
ディレクトリからの相対で効くためである。**この性質を壊さないこと** — 具体的には、
ルートからの絶対パスや、展開先の名前を前提にしたパターン（`erd/index.html binary` のような書き方）を
設定ファイルにも実装にも持ち込まない。以下、本書では展開先を `erd/` と表記する。

**個人データを `erd/` の内側（`.local/`）に置く**のは、同梱の `erd/.gitignore` だけで Git 運用が
完結するようにするため（§3.1）。`erd/` の外に置くと、利用者が自分のリポジトリの `.gitignore` に
追記しない限り認証情報がコミット対象として現れてしまい、事故の入口になる。
`erd/` の内側に置いても HTTP からは取得できない — サーバーは `erd/` を丸ごと静的配信しておらず、
明示的に定義したルート（`/`・`/index.html`・`/workspaces.js`・`/workspace-*/data/**`）しか配信しない（§8.5）。

**接続情報とバックアップをワークスペースごとに分けるのは必須である。** 接続先 DB が違うのに1つの
`connection.local.json` を共有すると取り違えが起きるうえ、バックアップからの復元（INV-5 の最後の砦）は
`data/` を丸ごと置き換えるため、混ざると別のワークスペースを破壊する。

**`erd/` の中身は原則すべて Git 管理する**（`erd-server.jar`・起動スクリプトを含む）。
メンバーが `git pull` するだけで、全員が同じ版のツールとデータを使える状態にするため。
バージョンアップは新しい ZIP で `erd/` を上書きし、その差分をコミットする。

`erd/.gitignore`（**配布 ZIP に同梱**。利用者はそのままコミットする）:

```
.local/
drivers/*.jar
```

`erd/.gitattributes`（**配布 ZIP に同梱**）:

```
index.html binary
erd-server.jar binary
workspace-*/data/** text eol=lf
```

**プロジェクト側の `.gitignore` / `.gitattributes` に追記させることは一切ない。**
ツールが作るファイルはすべて `erd/` の中に収まるため、同梱の 2 ファイルで設定が完結する。

### 3.7 ワークスペース（マルチデータベース構成）

**1ワークスペース = 1データベース。** 実体は `erd/workspace-<id>/data/**` で、ワークスペースをまたぐ参照はしない。

| 事項 | 決定 |
|---|---|
| ID | `[A-Za-z0-9][A-Za-z0-9_-]{0,31}`。省略時は `default`。フォルダ名は `workspace-<id>` |
| 重複判定 | **大文字小文字を区別しない**（Windows のパス仕様に合わせる。`Sales` と `sales` は同一） |
| 表示名 | 必須。`erd/workspaces.js` に持つ（§5.13） |
| ID の変更 | **可能**。フォルダ名と `erd/.local/workspace-<id>/` を移し、URL を張り替える。Git 上は「削除＋追加」の差分になるため GUI で警告する |
| 存在の正 | **フォルダの走査**。`workspaces.js` はその索引であり、走査結果と食い違えばサーバーが再生成する |
| 切り替え | アプリタイトル横のプルダウン。**フルリロード**で切り替える（ローダーのキャッシュ・編集状態・キャンバスの計測値がワークスペースに紐づくため） |
| 削除 | 設定メニューの「ワークスペース削除」。フォルダごと消す。確認に **ID の打ち込み**を求める |
| データリセット | 従来どおり残す。**現在のワークスペースの**スキーマ情報だけを消し、ワークスペース・無視リスト・接続設定は残す |
| 共通のもの | JDBC ドライバの jar（`erd/drivers/`）とその設定（`erd/config.js`）。接続先が違ってもドライバはチームで揃えたいため |
| 対象外 | ワークスペース横断の検索・参照、ワークスペース間のコピー / 複製、旧構成からのデータ移行 |

**静的モード（file://）ではディレクトリを走査できない。** そのため一覧は `workspaces.js` だけが情報源であり、
「今どのワークスペースを見ているか」は URL（§4.4 の `#/w/<id>/…`）で表す。URL に入っていないと、
別の DB の ER図 を人に送れない。

### 3.4 運用フロー

**アーキテクト / 編集者**

1. Release の ZIP をダウンロードし、`erd/` に展開する
2. `java -jar erd-server.jar` を実行（ブラウザが自動で開く）
3. GUI から DB 接続 → 逆生成 → 差分確認 → 適用
4. GUI 上でテーブルをページに配置（ドラッグ）
5. `erd/index.html`・`erd/workspaces.js`・`erd/workspace-*/data/**` を `git commit` / `push`

**プロジェクトメンバー（閲覧のみ）**

1. `git pull`
2. `erd/index.html` をブラウザで開く（**Java・Node・npm・サーバーのいずれも不要**）

### 3.5 バージョン整合性と自動移行

`index.html` と `data/**` の形式バージョンが食い違う可能性に備える。**サーバーが起動時に自動で移行し、ユーザーに手作業を求めない。**

- `manifest.js` に `schemaVersion`（データ形式のバージョン）を持たせる
- サーバーは `CURRENT_VERSION` と、`v1→v2`, `v2→v3` … の**移行関数の列**を持つ

移行は**起動時に全ワークスペースを走査して**行う（§3.7）。

| 状態 | 挙動 |
|---|---|
| データ == サーバー | そのまま起動 |
| データ **<** サーバー | **自動移行**（バックアップ → 全ファイルを新形式で再生成 → アトミック置換）。完了後、GUI に「データ形式を v1 → v2 に移行しました。差分をコミットしてください」と通知する |
| データ **>** サーバー | **そのワークスペースには一切触れず**、サーバーの起動は続ける。ビューア側はバージョン不一致をバナーで示し、そのワークスペースを描画しない（A-04）。「1つだけ新しい」状態で全体が起動しなくなるのは実用上つらいため、起動中止はしない |

- **静的モード（ビューア）は移行しない。** バージョンが一致しない場合、**描画せずバナーを表示する**（中途半端に読んで誤ったER図を見せるより、明確に止まる方が安全）。`index.html` と `data/**` は同じコミットで更新されるため、メンバーがこの状態に遭遇するのは移行の過渡期のみである。
- `schemaVersion` は**後方互換を破る変更時のみ**インクリメントする。**キーの追加では上げない**（未知キーは読み書きで保持されるため。§5.12）。
- 移行は全ファイルを書き換えるため、大きな Git 差分になる。GUI で「単独のコミットにすることを推奨します」と明示する。

詳細は [詳細設計: フェーズ0](function-details/Phase0_model-printer-index.md) §6 を参照。

### 3.6 初回起動（ワークスペースが無い / `data/**` が空のとき）

初回は**2段構成**になる。

1. **ワークスペースが1つも無い** → welcome 画面。ワークスペース ID（省略時 `default`。既に使われていれば `default-2` を提案）と表示名（必須）を入力して作成する。静的モードには作成手段がないため、「サーバーモードで起動してください」と表示する
2. **ワークスペースはあるが `workspace-<id>/data/manifest.js` が無い、またはテーブルが0件** → **ブートストラップ画面**（下表）。この画面からも他のワークスペースへ切り替えられる（切り替えられないと、2つ目を作った直後に元へ戻る導線が URL しかなくなる）

| 選択肢 | 内容 |
|---|---|
| **既存のスキーマから生成する** | DB に接続して逆生成する（§7 のフローへ）。実運用の入口 |
| **サンプルデータを取り込む** | ツールに同梱したサンプル（約30テーブルの `data/**` 一式）を書き出す。DB を用意せずに機能を試せる |
| （将来）**空のプロジェクトを作成する** | テーブルの手動作成（J-01）が実装された時点で選択肢に追加する |

- サンプルデータは `dev-db/postgresql/migrations/000_init.sql`（約30テーブルの PostgreSQL DDL。日本語コメント付き。dev-db の初期スキーマと共用）を元に、**実装時に生成して同梱する**（論理名・論理制約・ER図ページの配置例を含んだ、完成状態のサンプルとする）。
- 既存の `data/**` がある状態では、サンプルの取り込みを**実行できない**（上書き事故を防ぐ）。
- **静的モードで `data/**` が空の場合**は、「データがありません。サーバーモードで起動して初期化してください」と表示する（静的モードには初期化手段がない）。

| 責務 | 配置 |
|---|---|
| DB 接続、JDBC メタデータ取得、正規化 | サーバー |
| `data/**` の読み書き、決定論的プリント | サーバー |

### 4.3 モード判定と編集セッション

ビューアは起動時に `GET /__erd/health` を1回試行する。

- 成功 → **サーバーモード**（保存が可能）
- 失敗（`file://` では即座に失敗）→ **静的モード**（保存不可）

#### データの読み込み経路は1本にする

**モードにかかわらず、データの読み込みは常に `<script>` タグによる `workspace-<id>/data/**.js` の動的注入で行う。API はデータ取得に使わない。**（`erd/workspaces.js` も同じ経路で読む。§6.1 段階0）

| | 読み込み | 書き込み |
|---|---|---|
| 静的モード | `<script>` タグ | なし（エクスポートで持ち出す） |
| サーバーモード | **`<script>` タグ（同じ経路）** | REST API |

**API を読み込みにも使うと、ローダーが2系統になる。** データ形式のパース・キャッシュ・進捗表示・欠損時のエラー処理をすべて二重に持つことになり、「静的モードでだけ壊れる」バグが構造的に生まれる。読み込みを1本化すれば、ビューアのデータ層はモードを一切意識しない。

- サーバーは `workspace-<id>/data/**` を**静的ファイルとして配信する**（`GET /workspace-sales/data/schema/public/users.js` がそのまま返る）。file:// と URL の形を一致させるため、ビューアからは常に相対パスで読む。**サーバーモードではクエリにトークンを付ける**（`?t=<token>`。§8.5。無認証で配ると任意の Web ページが `<script src>` で読み出せるため）。付けるのはクエリだけで、読み込み経路（`<script>` 注入）はモードによらず1本のまま。
- **書き込み後の再読込**は、SSE で受け取ったリビジョンをクエリに付けて `<script>` を再注入する（`data/diagrams/core.js?v=<revision>`）。キャッシュを確実に回避でき、グローバル API（`ERD.diagram(...)`）が再度呼ばれてローダーが上書きする。
- API の `GET` 系は、**データ本体ではなくメタ情報のためだけに使う**（`baseHash` の取得、ドライバ一覧、逆生成のプレビュー）。

**動作モードにかかわらず、起動直後は必ず「閲覧中」である。** ユーザーが明示的に「編集」を開始するまで、ノードは動かせない（誤操作で配置が変わらない）。

| | 静的モード | サーバーモード |
|---|---|---|
| 編集セッションの開始 | 可能。「保存されません」の警告を出す | 可能。**閲覧ルートと編集ルートを分ける**（§4.4）。ロックは取得しない（別タブ / 外部の変更は §8.7 のバナーで検知する） |
| 保存 | **不可**。エクスポート（§9.7）で持ち出す | 可能（**明示保存のみ**。自動保存はしない） |
| 自動レイアウト（ELK） | 不可（サーバー API に依存） | 可能 |
| スキーマ・論理名の編集 | 不可 | 可能 |

### 4.4 ルーティング（ハッシュ URL）

**ER図とテーブルカタログは対等な2つのビューであり、いずれも URL で直接指せる。** すべての画面遷移はこのハッシュ URL への `<a href>` リンクとして実装する（§1.4.2）。

**閲覧と編集は別ルートとする。** 各画面は既定で**閲覧ルート**に着地し、編集は必ず画面内の [編集開始] から**編集ルート**へ遷移して初めて始まる（画面へ遷移しただけでは編集モードにならない）。

**すべてのルートは `#/w/<workspaceId>` で始まる**（§3.7）。ワークスペース部を省いた URL（`#/erd/…`）も解釈できるが、
ローダーが現在のワークスペースを補って `location.replace` で書き換える（履歴は汚さない）。URL が存在しない
ワークスペースを指していた場合は「見つかりません」と一覧への導線を出す（白画面にしない）。

| ルート | 画面 | モード |
|---|---|---|
| `#/w/<ws>/erd/<diagramId>` | ER図（指定ページ・閲覧） | 静・編 |
| `#/w/<ws>/erd/<diagramId>/<tableId>` | ER図。該当ノードを中央表示・選択状態にする | 静・編 |
| `#/w/<ws>/erd/<diagramId>/edit` | **ER図の配置編集**（閲覧ルートから [編集開始] で遷移） | 静・編（静的モードは保存不可。エクスポートで持ち出す。§9.7） |
| `#/w/<ws>/tables` | テーブル一覧 | 静・編 |
| `#/w/<ws>/tables/<tableId>` | テーブル詳細（閲覧。左パネルの範囲を連続表示し、該当テーブルへスクロール。R-01） | 静・編 |
| `#/w/<ws>/tables/<tableId>/edit` | テーブル編集 | 編（静的モードでは詳細へリダイレクトし、閲覧モードである旨を表示） |
| `#/w/<ws>/tables/doc` | ドキュメント（同じ範囲を物理名・論理名・タグ・注記に絞って閲覧。R-01）。最後に見たテーブルの位置へ | 静・編 |
| `#/w/<ws>/tables/doc/<tableId>` | ドキュメント。該当テーブルの見出しへスクロール | 静・編 |
| `#/w/<ws>/columns` | カラム論理名の一括編集（テーブル横断・閲覧） | 静・編 |
| `#/w/<ws>/columns/edit` | カラム論理名の一括編集（編集） | 編（静的モードでは `#/w/<ws>/columns` へリダイレクト） |
| `#/w/<ws>/introspect` | DB からの逆生成（接続 → 内省 → 差分 → 適用のフロー） | 編 |

- ER図上のノード / エッジのダブルクリックで開く詳細ダイアログは、一時的な UI であり URL を持たない。ダイアログ内から `#/tables/<tableId>` への**実リンク**を提供する。
- テーブル詳細画面からは、そのテーブルが配置されている各ページへの `#/erd/<diagramId>/<tableId>` リンクを提供する。配置ページが複数ある場合はページを選択させる（リンクを列挙する）。
- **編集ルート滞在中に別ルートへ遷移しようとしたら、未保存の変更があれば確認する**（破棄 / キャンセル）。ブラウザの戻る / 進むも同様に捕捉する（`popstate`。[X-05](2_functions.md) の「ブラウザ標準の戻る / 進む」は、編集中に限りこのガードが優先する）。修飾キー付きクリック（Ctrl / 中クリック）による別タブ表示は妨げない（別タブは閲覧として開く）。
- 編集ルートへ直接着地した場合（ブックマーク・リロード・戻る）はその画面の編集モードで開く（下書きは空から）。ただし静的モードで編集不可の画面（テーブル編集・カラム論理名編集）は上表のとおり閲覧ルートへリダイレクトする。
- 未知のルート・存在しない ID は「見つかりません」を表示し、`#/tables` への導線を出す（白画面にしない）。

## 5. データ形式

### 5.1 決定事項

- **形式は JavaScript（クラシックスクリプト）。** `file://` では `fetch` / ES Modules が使用できないため、JSON / YAML を外部ファイルとして読み込むことはできない。
- 各ファイルは **「グローバル API への関数呼び出し1つ」** に限定する。制御構文・変数・演算・関数定義は禁止（実質「JSON5 のオブジェクトリテラル1つ」）。
- **スキーマ情報（`data/schema/`）と ER視覚情報（`data/diagrams/`）は完全に分離する。** 逆生成は `data/diagrams/` を一切書き換えない。
- **ファイル内の自由コメントはサポートしない。** 書き込みは全文を決定論的プリンタで再生成する。人が書く注記はすべて `meta` の構造化フィールドに格納し、逆生成はそこを読み書きしない（＝注記は完全に保持される）。
- **ワークスペースの設定（`data/config.js`）とカラム辞書（`data/dictionary.js`）は human-owned。** 逆生成はこれらを**読む**が（無視リストは内省の入力になる）、**書き換えない**。
- **論理名（テーブル / カラム）と論理制約（論理一意制約 / 論理外部制約）は人が持つ情報であり、`meta` に格納する。** DB のスキーマには存在しない情報であり、逆生成で失われてはならない。
  - **唯一の例外**として、逆生成の適用時に `meta.displayName` が**未設定の場合に限り**、DB のコメント（`REMARKS`）を論理名の初期値として書き込む（§5.8.2）。既存値は決して上書きしない。
- **MCP（§8.8）は machine-owned を書き換えない。** 「逆生成が `meta` を書き換えない」の対になる制約であり、
  向きが逆なだけで理由は同じ **「所有者が違う情報を、他方の経路から壊さない」** である。MCP から書けるのは
  `meta`・`diagrams/**`・`dictionary.js`・`config.js` だけで、カラム・型・PK・FK・索引には触れない。
  仮に触れると、次の逆生成が DB を正として上書きするため、**書いた内容が黙って消える**。

### 5.2 グローバル API

`index.html` は起動時に以下のグローバル関数を定義する。

| API | 用途 |
|---|---|
| `ERD.manifest({...})` | ファイル一覧 / バージョン |
| `ERD.config({...})` | プロジェクト設定（テーブル無視リスト） |
| `ERD.index({...})` | 全テーブルの軽量サマリ + リレーション一覧（ER図描画・検索・一覧用） |
| `ERD.dictionary({...})` | カラム辞書（同名カラムの共通設定: 論理名・タグ・色） |
| `ERD.table({...})` | テーブル1件のスキーマ定義 |
| `ERD.diagram({...})` | ER図ページ1件の視覚情報 |

### 5.13 `erd/workspaces.js`（ワークスペースの索引）

**ツール生成物**（machine-owned）。存在の正はフォルダの走査であり、このファイルはその索引 + 表示名の置き場所である。
サーバーは起動時と一覧要求のたびに走査し、内容が食い違えば書き直す（Git で pull されただけのワークスペースは、
名前が分からないので ID を表示名にする）。**静的モードではこれが唯一の一覧の情報源**になる。

```js
ERD.workspaces({
  workspaces: [
    { id: "billing", name: "課金" },
    { id: "sales", name: "販売管理" },
  ],
});
```

1ワークスペース = 1行にし、並びは ID のコードポイント順に固定する（別々の人がワークスペースを追加したときに
Git の競合を解消しやすくするため）。

### 5.4 `config.js`（設定。2か所にある）

**human-owned の設定。** チーム全員で共有すべき設定であり、Git 管理する（個人設定は `erd/.local/` へ）。サーバーは逆生成でこのファイルを書き換えない（GUI からの明示的な編集でのみ更新する）。書式は同じで、置き場所と持つ項目が違う。

| 置き場所 | 持つもの | 理由 |
|---|---|---|
| `workspace-<id>/data/config.js` | `ignoreTables`（テーブル無視リスト） | 対象 DB ごとに違う |
| `erd/config.js` | `drivers`（Maven リポジトリ・ドライバ座標） | **全ワークスペース共通**。接続先が違ってもドライバはチームで揃えたい |

`erd/config.js` は `data/` の外にあるため、ファイル監視・SSE・リビジョンの対象ではない。

```js
// workspace-<id>/data/config.js
ERD.config({
  ignoreTables: [
    "public.flyway_schema_history",   // 完全一致
    "public.tmp_*",                   // glob（* と ? が使える）
    "/^staging\\..*_bak$/",           // 正規表現（前後を / で囲む）
  ],
});
```

```js
// erd/config.js（全ワークスペース共通）
ERD.config({
  drivers: {
    mavenRepository: "https://repo1.maven.org/maven2",
    artifacts: [
      "org.postgresql:postgresql:42.7.4",
    ],
  },
});
```

#### テーブル無視リスト（`ignoreTables`）

**マッチしたテーブルは「このプロジェクトには存在しない」ものとして扱う。** 逆生成の入力からも、既存定義の側からも、双方向に無視する。

| 局面 | 挙動 |
|---|---|
| 逆生成（内省） | DB から取得しない（取得しても差分計算前に捨てる）。**追加候補にならない** |
| 逆生成（差分計算） | `data/schema/**` に定義が存在していても比較対象にしない。**削除候補にならない・変更も検出しない** |
| 既存のスキーマファイル | **削除しない**。ファイルはそのまま残り、ER図・テーブルカタログ・検索には通常どおり表示される |
| 差分プレビュー | 「無視 (N)」として件数のみ表示し、どのパターンにマッチしたかを確認できる |

- マッチ対象は**完全修飾テーブルID**（`schema.table`）。
- 記法は3つ。前後を `/` で囲めば**正規表現**、`*` / `?` を含めば **glob**、それ以外は**完全一致**。
- 用途は主に2つ。
  1. **DB 側の管理テーブルを除外する**（マイグレーション履歴、一時テーブル、バックアップテーブル）
  2. **手動定義テーブル（J-01）を保護する。** DB に存在しないテーブルを手で定義した場合、無視リストに入れないと逆生成のたびに削除候補として現れる
- 無視リストから外すと、次回の逆生成で通常の対象に戻る（DB に存在しなければ削除候補になる）。
- 「今回の内省だけ対象から外したい」場合は、接続設定側のフィルタ（§7.5 の包含 / 除外パターン）を使う。**無視リストはプロジェクトに永続する設定であり、既存定義にも作用する**という点が決定的に異なる。

### 5.5 `data/index.js`（一覧・検索・ER図描画用の軽量インデックス）

全テーブルのスキーマファイルを読み込まずに、テーブル一覧・検索・未配置テーブルの表示、**および ER図の完全な描画**を可能にする。サーバーが `schema/**` から自動生成する派生ファイルであり、手で編集しない。

**ER図のノードはテーブル名のみを描画する（カラムを描かない）ため、ER図の初回描画に必要な情報は「テーブル名 + リレーション」だけになる。** これらを index に集約することで、スキーマファイルは詳細ダイアログ / カタログを開くまで読み込まなくてよい（§6）。

```js
ERD.index({
  tables: [
    { id: "public.users",  name: "users",  schema: "public", displayName: "ユーザー", columns: 8,  tags: ["core", "auth"], color: "blue", diagrams: ["core"] },
    { id: "public.orders", name: "orders", schema: "public", displayName: "注文",     columns: 12, tags: ["core"],                        diagrams: ["core", "billing"] },
  ],
  relations: [
    // ER図のエッジ描画に必要な最小情報。kind: "physical"（FK）/ "logical"（meta の論理外部制約）
    { id: "public.users#fk:users_org_id_fkey", kind: "physical",
      from: "public.users", to: "public.organizations", columns: [["org_id", "id"]],
      cardinality: { parent: "0..1", child: "0..N" } },
    { id: "public.orders#lfk:lfk_orders_user", kind: "logical",
      from: "public.orders", to: "public.users", columns: [["user_id", "id"]],
      cardinality: { parent: "1..1", child: "1..N" }, explicit: ["child"] },
  ],
  // このワークスペースで使われているタグ（テーブル ∪ カラム）。コードポイント順
  tagsUsed: ["auth", "core", "廃止"],
});
```

- **エッジID は `<テーブルID>#<種別>:<制約名>`。** 種別（`fk` / `lfk`）を挟むのは、**物理 FK と論理外部制約で制約名が衝突しうる**ため。`diagrams.edges` のキーもこの形式に一致させる（§5.9）
- `from` は**参照元**（FK を持つ側 = 子）、`to` は**参照先**（親）
- `cardinality`: **解決後**の多重度（§5.7 のカーディナリティ）。ビューアは導出ロジックを持たず、この値をそのまま鳥の足記号にする
- `explicit`: 人が `meta.relations` で明示設定した項目（導出値との区別。詳細ダイアログで「手動設定」と示すため）
- `color`: `meta.color` の生の値（P-13）。**ER図のノードはこの索引だけで描くため、色を載せないと「詳細画面では色が付くのに ER図では付かない」ことになる。** カラムの色は載せない（カラムを描く画面は必ずスキーマファイルを読み込んでいる）
- `tagsUsed`: 使用中タグの集合（P-12）。**全テーブルを読み込まなくてもタグ入力の候補を出せるようにするためだけに存在する。** カラムタグは索引に個別展開しないので、カラムタグによる検索はロード済みのテーブルにのみ当たる（F-04 の段階拡張）

### 5.6 `data/dictionary.js`（カラム辞書 = カラムの共通設定）

**同名カラムはプロジェクト全体で同じ意味を持つ**という前提のもと、カラム物理名ごとの共通設定（論理名・タグ・色）を1箇所で管理する。`created_at` を全テーブルで「作成日時」と表示し、`password` を全テーブルで `pii` タグ付きの赤にするために、テーブルごとに設定して回る必要をなくす。

```js
ERD.dictionary({
  columns: {
    created_at: { displayName: "作成日時", tags: ["監査"], color: "muted" },
    email:      { displayName: "メールアドレス", tags: ["pii"], color: "amber" },
    id:         { displayName: "ID" },
    deleted_at: { tags: ["廃止"], color: "muted" },
  },
});
```

- キーはカラムの物理名のみ（テーブル名を含まない）。**カラム辞書の画面**（`#/columns`）から編集する。
- 値は**すべて省略可能**で、全フィールドが空のエントリは保存時に落ちる（= 削除）。論理名が無くタグ・色だけのエントリは正当（上の `deleted_at`）。
- テーブル個別との合わせ方は属性ごとに違う（§5.8.1）。論理名と色は個別が**上書き**し、タグは**合成**される。
- 逆生成はこのファイルを読み書きしない（human-owned）。
- 辞書のタグは `index.js` の `tagsUsed` に載せない。**辞書はビューアが常に直接読むので候補はそこから引ける**からで、載せると辞書を保存するたびに索引の再生成が要る。

### 5.7 `data/schema/public/users.js`

```js
ERD.table({
  id: "public.users",
  name: "users",
  schema: "public",
  comment: "ユーザーマスタ",
  columns: [
    { name: "id",         type: "bigserial",    logicalType: "int",      nullable: false, autoIncrement: true },
    { name: "email",      type: "varchar(255)", logicalType: "string",   nullable: false },
    { name: "org_id",     type: "int8",         logicalType: "int",      nullable: true },
    { name: "created_at", type: "timestamptz",  logicalType: "datetime", nullable: false, default: "now()" },
  ],
  primaryKey: ["id"],
  uniques: [
    { name: "users_email_key", columns: ["email"] },
  ],
  indexes: [
    { name: "idx_users_created_at", columns: ["created_at"] },
  ],
  foreignKeys: [
    { name: "users_org_id_fkey", columns: ["org_id"], ref: { table: "public.organizations", columns: ["id"] }, onDelete: "set null", onUpdate: "no action" },
  ],
  dialect: {
    // Enhancer が取得した DB 固有情報（CHECK制約、unsigned、ENUM値 など）
  },
  meta: {
    // ↓ human-owned。逆生成は読まず、書き換えない（displayName の初期値補完のみ例外。§5.8.2）
    displayName: "ユーザー",                    // テーブル論理名
    tags: ["core", "auth"],                   // 分類・検索用（P-12）。見た目には影響しない
    color: "blue",                            // 指定色（P-13）。タグとは独立
    notes: "論理削除は deleted_at 運用",
    columns: {
      // カラム単位の論理名（辞書より優先）・タグ・色・注記
      org_id: { displayName: "所属組織ID", tags: ["pii"], notes: "NULL は個人アカウント" },
      last_order_id: { tags: ["廃止"], color: "muted" },
    },
    logicalUniques: [
      // DB に制約は無いが、運用上一意であることが保証されている組
      { name: "luk_users_org_email", columns: ["org_id", "email"], notes: "組織内でメールは重複しない（アプリ側で担保）" },
    ],
    logicalForeignKeys: [
      // DB に FK は無いが、論理的には参照関係にある（ER図に破線エッジで描画される）
      { name: "lfk_users_last_order", columns: ["last_order_id"], ref: { table: "public.orders", columns: ["id"] }, notes: "性能上 FK を張っていない" },
    ],
    relations: {
      // リレーションのカーディナリティ（物理情報だけでは決まらない多重度を人が設定する。§5.7 のカーディナリティ）
      "fk:users_org_id_fkey": { child: "1..N", notes: "組織には必ず1人以上の利用者がいる" },
    },
  },
});
```

#### キーの所有権

| 区分 | キー | 逆生成の挙動 |
|---|---|---|
| machine-owned | `name` `schema` `comment` `columns` `primaryKey` `uniques` `indexes` `foreignKeys` `dialect` | 上書きする |
| human-owned | `meta.*`（`displayName` / `tags` / `color` / `notes` / `columns.*` / `logicalUniques` / `logicalForeignKeys` / `relations`） | **読まない・書かない**。ただし `displayName` が未設定の場合のみ、コメントから初期値を補完する（§5.8.2） |
| 共有 | `id` | リネーム承認時のみ書き換える |

#### タグと色（`meta.tags` / `meta.color`）

**タグと色は独立した属性であり、タグから色を導出しない。** 「廃止」タグを付けても自動でグレーにはならず、グレーにしたければ `color: "muted"` も指定する。**意味はタグで、見た目は色で表す**という切り分けである。

タグに色を割り当てる仕組み（タグ定義のレジストリ）を持たないことには理由がある。色をタグ経由にすると、(1) タグ定義を置くファイルが増え、**閲覧に必要な情報とサーバー専用の設定が混ざる**（`config.js` は静的モードでは読まないため、そこに置くと配布した静的 ZIP でだけ色が消える）、(2) 複数タグが付いたときの優先順位という決着しない設計問題を抱え込む、(3) タグの改名が全テーブルの一括書き換えになる。色を直接持たせれば、これらはすべて発生しない。

| | 置き場所 | 索引 | 用途 |
|---|---|---|---|
| タグ | `meta.tags` / `meta.columns.<name>.tags` / `dictionary.columns.<name>.tags` | 使用中の集合のみ（`tagsUsed`。**辞書のタグは載せない**） | 分類・検索・絞り込み |
| 色 | `meta.color` / `meta.columns.<name>.color` / `dictionary.columns.<name>.color` | テーブルの色のみ（`tables[].color`） | ER図ノード・一覧行・カラム行の着色 |

- タグはテーブルとカラムで**同じ名前空間**（「廃止」はどちらにも付く）。**順序に意味は無い**が、人の書いた順は保つ
- タグ名は空白・区切り文字（`,` `、`）を含めない。**空白でタグを確定する入力 UI に合わせた制約**である。前後空白・空要素・重複（大小無視）はサーバーが保存時に正規化し、それ以外の違反は 422 で拒否する。**この規則はテーブルの `meta` とカラム辞書の両方に同じく掛ける**
- 色は**用意されたトークンのみ**（`gray` `red` `amber` `green` `blue` `purple` `muted`）。任意の hex を許さないのは、配色の一貫性と文字色とのコントラストを人の手で崩させないため。実際の配色はビューアのテーマが持つ
- **テーブルの色はカラムに継承しない。** 継承するのは**カラム辞書 → 同名カラム**の方向だけである（§5.8.1）。未知のトークンはビューアが既定の外観で描画しつつ値は保持する（手で編集したファイルで描画が壊れないように）
- **カラム名からの色の自動割り当ては行わない。** 色は人が辞書で指定した分だけ付く。名前から機械的に配ると、7トークンしかない中で衝突が頻発し、意味と無関係な色が並ぶ

#### 論理制約（`meta.logicalUniques` / `meta.logicalForeignKeys`）

DB に物理的な制約が存在しない一意性・参照関係を、人がメタデータとして宣言し、ER図と詳細画面に表示する。

- 物理制約（`uniques` / `foreignKeys`）とは**フィールドを分けて保持する**。混ぜると逆生成の上書きで消える
- 形式は物理制約と同一のため、詳細画面での表示・カーディナリティ判定・被参照一覧の処理を共通化できる
- **論理外部制約は `onDelete` / `onUpdate` を持たない。** DB に制約が存在しない以上、参照動作も存在しない（持たせると「設定したのに効かない」という誤解を生む）
- ER図では**論理外部制約を破線エッジ**として描画し、物理 FK（実線）と視覚的に区別する
- 参照先テーブル / カラムの存在は保存時に検証する（存在しない場合は警告）

#### カーディナリティ（`meta.relations`）

**多重度は物理情報だけでは決まらない。**

| 多重度 | DB から導出できるか |
|---|---|
| 子から見た**親**が `0..1` か `1..1` か | **できる**（FK カラムが NULL 可か、すべて NOT NULL か） |
| 親から見た**子**が `0..1` か `0..N` か | **できる**（FK カラムに一意制約があるか） |
| 親から見た子の**下限が 0 か 1 か**（`0..N` か `1..N` か） | **できない**。「組織には必ず1人以上の利用者がいる」は**業務ルール**であり、外部キー制約では表現できない |

したがって、**カーディナリティは「物理からの導出値」を既定とし、人が `meta.relations` で上書きする**。

```js
meta: {
  relations: {
    // キー = エッジID の後半（<種別>:<制約名>）。物理 FK・論理外部制約の両方に付けられる
    "fk:users_org_id_fkey": { child: "1..N", notes: "組織には必ず1人以上の利用者がいる" },
  },
}
```

- `parent`（子から見た親）: `"0..1"` / `"1..1"`、`child`（親から見た子）: `"0..1"` / `"1..1"` / `"0..N"` / `"1..N"`
- **部分上書きができる**（`child` だけ設定し、`parent` は導出値のままにする）
- **human-owned。逆生成は読まない・書かない**
- **`meta` は FK を持つ側（参照元テーブル）に置く**。FK の定義と同じ場所で完結する
- **設定 UI は「その制約の詳細ダイアログの中」に置く**（独立した一覧は持たない）。キーが制約名である以上、名前が決まる前は設定できず、リネームすると設定が取り残されるため、編集フォームでは**制約の行そのものに持たせ**、保存時に確定した名前でキーを組み立てる（[P 詳細設計](function-details/P01-P09_logical-names-constraints.md) §4.6）
- サーバーは `index.js` の生成時に「導出値 + 上書き」を解決し、**解決後の値のみを `index.relations[].cardinality` に載せる**（ビューアは導出ロジックを持たない）

#### 型の二重保持

複数DB対応のため、型は2つ持つ。

- `type`: JDBC の `TYPE_NAME` に基づく DB 生の型文字列（忠実性の担保）
- `logicalType`: `java.sql.Types`（`DATA_TYPE`）に基づく正規化型。詳細ダイアログ・カタログの表示・アイコン・比較はこちらを使用する
  - `string` / `int` / `float` / `decimal` / `bool` / `date` / `time` / `datetime` / `json` / `uuid` / `binary` / `enum` / `array` / `other`

### 5.8 論理名

物理名（DB 上の名前）とは別に、人が読むための**論理名**を持つ。設定場所が複数あるため、解決順序を1箇所（ビューアの `model/` 層）に実装し、全画面がそれを使う。

#### 5.8.1 解決順序

| 対象 | 優先順位（上が優先） |
|---|---|
| テーブル論理名 | 1. `meta.displayName` → 2. 物理名 |
| カラム論理名 | 1. そのテーブルの `meta.columns.<name>.displayName`（個別設定）→ 2. `dictionary.columns[<name>].displayName`（カラム辞書）→ 3. 物理名 |
| カラムの色 | 1. `meta.columns.<name>.color` → 2. `dictionary.columns[<name>].color` → 3. 色なし |
| カラムのタグ | `dictionary.columns[<name>].tags` **∪** `meta.columns.<name>.tags`（**合成**。重複は表示時にまとめる） |

- **テーブル論理名はテーブル編集画面から設定する。**
- **カラムの論理名・タグ・色はカラム辞書（`#/columns`）で一括設定するのが基本**で、テーブル固有の事情がある場合のみテーブル編集画面で個別に上書きする。
- **タグだけは合成で、個別設定からは取り消せない。** 共通タグは「同名カラムはプロジェクト全体で同じ意味を持つ」という分類であり、テーブル1件の都合で消せると分類として使えなくなる（個別に外す手段は将来の課題）。テーブル編集画面には共通タグを読み取り専用のチップとして出し、個別タグと区別できるようにする。表示（テーブル詳細・ER図）では出どころを区別しない。
- 表示は「論理名 / 物理名 / 併記」を切り替えられる（個人設定）。既定は併記。

#### 5.8.2 コメントからの初期値補完（逆生成時）

逆生成の**適用時**に限り、サーバーは以下を行う。`meta` に対する唯一の書き込みであり、**既存値は決して上書きしない**。

| 対象 | 補完元 | 条件 |
|---|---|---|
| `meta.displayName`（テーブル） | `comment`（`getTables().REMARKS`）の1行目 | `meta.displayName` が未設定で、コメントが空でないとき |
| `meta.columns.<name>.displayName` | そのカラムの `comment`（`getColumns().REMARKS`）の1行目 | 同カラムの `displayName` が未設定で、辞書にも登録が無く、コメントが空でないとき |

- 補完は「初期値の種まき」であり、以後は人の編集が常に勝つ。差分プレビューでは補完される論理名も提示し、承認の対象とする。
- コメントに改行がある場合、1行目のみを論理名とし、全文は `comment` に残る（`comment` は machine-owned のまま）。

### 5.9 `data/diagrams/core.js`（ER視覚情報 = 1ページ）

```js
ERD.diagram({
  id: "core",
  title: "コアドメイン",
  order: 1,
  nodes: {
    "public.users":         { pos: [120, 80],  w: 260 },
    "public.orders":        { pos: [520, 80] },
    "public.organizations": { pos: [120, 400] },
  },
  edges: {
    "public.users#fk:users_org_id_fkey": { waypoints: [[380, 200], [300, 320]] },
  },
});
```

- **ページ = ダイアグラムファイル1枚。** 描画オブジェクト数を抑える単位であり、Git のコンフリクト局所化の単位でもある。
- ノードのキーはテーブルID（`schema.table`）。これがスキーマ情報と視覚情報を結ぶ唯一の接点。
- **エッジのキーは `<テーブルID>#<種別>:<制約名>`**（`fk` = 物理 FK、`lfk` = 論理外部制約）。種別を挟むのは両者で制約名が衝突しうるため（§5.5）。制約名を変更した場合はこのキーも書き換える（waypoints を失わないため）。
- ノードはテーブル名のみを描画するため、**折りたたみ状態（`collapsed`）は持たない**。`w` は名前が長い場合の幅の明示指定にのみ使う（省略時は内容に合わせて自動）。
- 同一テーブルを複数ページに配置してよい。
- **ビューポート / ズーム / 選択状態は保存しない**（個人状態は `erd/.local/` へ）。

### 5.10 テーブルのリネーム耐性

1. 逆生成の差分検出時、削除候補と追加候補の**カラム構成シグネチャ**（カラム名・型・順序のハッシュ）を照合してリネーム候補を推定する
2. GUI の差分プレビューでリネームとして提示する（人が承認・訂正できる）
3. 承認時、サーバーが `data/schema/**` と `data/diagrams/**` の**両方をアトミックに書き換える**
4. 参照先を失った孤児ノードは自動削除せず、ビューア上で警告表示する。除去は明示操作でのみ行う

### 5.11 書式規約（Git 差分の最適化）

サーバー側の決定論的プリンタで強制する。

- **1カラム = 1行**（compact object 形式）。カラム型の変更が1行差分になる
- キー順は固定。省略可能なキーはデフォルト値と一致する場合に省略する（ただし `nullable` は可読性のため常に出力する）
- **配列**の順序は DB の物理順（`ORDINAL_POSITION` / `KEY_SEQ`）を維持する。アルファベット順にしない
- **マップ**（`nodes` / `edges` / `manifest.tables` / `dictionary.columns` …）は**キーの昇順**（Unicode コードポイント順。ロケール依存のソートを使わない）。座標を変えても行が移動せず、差分が1行に収まる
- インデントは2スペース、末尾カンマあり（末尾要素の追加が1行差分で済む）
- **座標はグリッドスナップ（8px）+ 整数化**。ドラッグ由来の微小差分を発生させない
- 改行コードは LF、末尾に改行1つ、UTF-8（BOM なし）
- **日本語をエスケープしない**（`\uXXXX` にしない）。Git 差分が読めることが、このデータ形式の存在意義である
- **`U+2028` / `U+2029` は必ずエスケープする**（JavaScript の文字列リテラル内で改行として扱われ、ファイル全体が構文エラーになるため）
- **JS の予約語・記号を含むキーはクォートする**（カラム名が `default` のときにファイルが壊れないように）

**エスケープ規則・キー順・省略規則・ソート順の完全な仕様は、[詳細設計: フェーズ0](function-details/Phase0_model-printer-index.md) §2 を参照。** Java（サーバー）と TypeScript（H-13 のエクスポート）の二重実装になるため、同一の golden fixture による出力一致を CI で保証する。

### 5.12 サーバー側の読み書き実装

**読み込み**: ラッパ（`ERD.table(` … `);`）を剥がし、Jackson でオブジェクトリテラルをパースする。JS パーサの自前実装は不要。

```java
ObjectMapper mapper = JsonMapper.builder()
    .enable(JsonReadFeature.ALLOW_UNQUOTED_FIELD_NAMES)
    .enable(JsonReadFeature.ALLOW_SINGLE_QUOTES)
    .enable(JsonReadFeature.ALLOW_TRAILING_COMMA)
    .enable(JsonReadFeature.ALLOW_JAVA_COMMENTS)
    .build();
```

**書き込み**: モデル → 決定論的プリンタ（自前実装）で全文生成 → 一時ファイルへ書き出し → `ATOMIC_MOVE` で置換する。

**未知キーの保持（前方互換）**: パース時に**モデルが知らないキーを捨てない**。`unknown` マップに退避し、プリンタが元の位置に書き戻す。これがないと、新しいバージョンのツールが書いたフィールドを古いツールが黙って消す（「開いて閉じただけで情報が失われる」）。この保持があるからこそ、**キーの追加では `schemaVersion` を上げなくてよい**（§3.5）。

## 6. ロード設計（インクリメンタルロード）

連結バンドルは作らない。ローダーは `<script>` タグを動的注入し、`onload` / `onerror` で完了を待つ。**この経路は静的モード / サーバーモードで共通である**（§4.3）。

### 6.1 ロード順序

**ER図のノードがテーブル名のみになったことで、ER図の描画にスキーマファイルは不要になった**（ノード名・リレーションはいずれも `index.js` に含まれる）。スキーマファイルは詳細ダイアログ / テーブルカタログを開いたときに初めて必要になる。

以下の `data/` は、表示中のワークスペースの `workspace-<id>/data/` を指す。

| 段階 | 読み込むもの | この時点で可能なこと |
|---|---|---|
| 0 | `workspaces.js` | **どのワークスペースを読むかの決定**（URL → 最後に見たもの → 先頭）、プルダウンの描画 |
| 1 | `data/manifest.js` | バージョン検証、ページ一覧の描画 |
| 2 | `data/index.js` + `data/dictionary.js` | テーブル一覧・検索・サイドバーの描画。論理名の解決 |
| 2' | `data/config.js`（**サーバーモードのみ**） | 無視リストの表示・編集。閲覧には不要なため静的モードではロードしない |
| 3 | 表示対象ページの `data/diagrams/<id>.js` | **ER図の初回描画完了**（ノード = テーブル名、エッジ = `index.relations`） |
| 4 | 選択されたテーブルの `data/schema/**.js`（オンデマンド、1件） | 詳細ダイアログ / テーブル詳細画面の表示 |
| 5 | 残りの全テーブル（アイドル時にバックグラウンドで順次） | カタログの全項目表示、カラム単位の全文検索、論理名一括編集画面の即時化 |

- 段階0 が空（`workspaces.js` が無い / 壊れている / 0件）なら welcome 画面へ落とす（§3.6）。
- **読むのは常に1ワークスペース分だけ**。切り替えはフルリロードなので、複数を同時に抱えることはない。

### 6.2 実装方針

- 段階3までで ER図は完成する。ここまでに読むファイルは**4本のみ**（manifest / index / dictionary / 対象ページ）で、テーブル数が増えても増えない
- 段階4はオンデマンド。ダイアログを開いた瞬間にロードし、それまではスケルトン表示（数十msで解決するため、ローディング画面は出さない）
- 段階5は `requestIdleCallback`（未対応環境は `setTimeout`）でチャンク実行し、UI をブロックしない。並列度は 8 程度に制限する
- カタログ / 一括編集画面を段階5の完了前に開いた場合は、必要なテーブルの優先度を上げて先行ロードし、到着した行から順次描画する（プログレッシブレンダリング）
- ロード済みテーブルは `Map<tableId, Table>` にキャッシュし、二重ロードしない
- ロード失敗（ファイル欠損）は握りつぶさず、「欠損テーブル一覧」としてビューア上に表示する
- 進捗は上部の細いプログレスバーで表示する（初回描画をブロックするローディング画面は出さない）

### 6.3 性能方針

- 1ページあたりのテーブル数は **100 以下**を推奨とし、超過時は GUI で警告する
- 総テーブル数 1000 規模でも、初回描画に必要なのは「manifest + index + dictionary + 1ページ分」に限定されるため高速に保たれる
- ノードがテーブル名のみになったことで1ノードあたりの DOM 数が大幅に減り、俯瞰時の描画コストも下がる（LOD による描画粒度の切替は不要になった）

## 7. スキーマ逆生成

### 7.1 2層構成

```java
// 層1: JDBC 標準。DatabaseMetaData のみを使用し、すべてのドライバで動作する
public interface Introspector {
    RawSchema introspect(Connection conn, IntrospectOptions opts) throws SQLException;
}

// 層2: 任意。DB固有情報を追加SQLで補完する。ServiceLoader で発見する
public interface DialectEnhancer {
    boolean supports(DatabaseMetaData md);              // getDatabaseProductName() で判定
    void enhance(Connection conn, RawSchema schema) throws SQLException;
}
```

- **層1だけで最低限動作する。** JDBC ドライバの jar を `drivers/` に置くだけで、未知の DB にも対応できる
- 層2は PostgreSQL / MySQL 用を同梱する。新規 DB の対応は「ドライバを置く」だけで済み、Enhancer の追加は任意

### 7.2 ドライバのロード

`DriverManager` は呼び出し元のクラスローダーから見えるドライバしか使わないため、`drivers/*.jar` を動的に読む場合はラッパ経由で登録する。

```java
URLClassLoader cl = new URLClassLoader(driverJarUrls, Main.class.getClassLoader());
for (Driver d : ServiceLoader.load(Driver.class, cl)) {
    DriverManager.registerDriver(new DriverShim(d));  // Driver へ委譲するだけの薄いラッパ
}
```

- ロード済みドライバの一覧（クラス名・バージョン）は `GET /__erd/drivers` で返し、GUI に表示する
- クラスパス指定（起動方式B）で読み込まれたドライバも同様に列挙する

#### 7.2.1 ドライバの取得（Maven ダウンロード）

**ドライバは配布物に同梱せず、逆生成画面から Maven 経由でダウンロードする。** これにより
再配布に伴うライセンス問題（MySQL は GPLv2 + FOSS 例外、Oracle は proprietary な OFUTC）を避け、
配布 ZIP を小さく保つ。狙いは「**設定（何を・どのバージョンで）はチーム共有、jar の実体と接続情報は各自**」。

| 何を | どこに置くか | 共有 |
|---|---|---|
| 使うドライバの座標・バージョン・Maven リポジトリ | `erd/config.js` の `drivers`（Git 管理・全ワークスペース共通） | ✅ チーム共有 |
| jar の実体 | `drivers/*.jar`（`.gitignore`） | ❌ 各自ダウンロード |
| 接続情報・パスワード | `erd/.local/`（Git 管理外） | ❌ 個人 |

- 既定で提示するドライバと既定バージョンは `DriverCatalog`（build.gradle.kts の testImplementation と揃える）
- `config.js` の `drivers`:

  ```js
  ERD.config({
    drivers: {
      mavenRepository: "https://repo1.maven.org/maven2",  // 省略時は既定（Maven Central）
      artifacts: [
        "org.postgresql:postgresql:42.7.4",               // group:artifact:version
      ],
    },
  });
  ```

- `GET /__erd/drivers` は「ロード済み・カタログ・config の設定・未取得（`missing`）」を返す。
  逆生成画面の入口で `missing` が空でなければダウンロードの確認を出す（他メンバーの初回導線）。
- `POST /__erd/drivers/download` が Maven からダウンロード → `.sha1` 照合 → `drivers/` へ保存 →
  `DriverShim` 経由で登録（**サーバー再起動なし**）。座標は `group:artifact:version` を厳格な
  文字集合に限定し、パストラバーサルを禁止。リポジトリ URL は http(s) のみ許可。
- カタログに無い DB は、`config.js` に座標を足すか、jar を直接 `drivers/` に置く（従来どおり）。

### 7.3 標準メタデータで取得する情報

| 情報 | API | 使用する列 |
|---|---|---|
| テーブル一覧・コメント | `getTables()` | `TABLE_SCHEM` `TABLE_NAME` `REMARKS` |
| カラム | `getColumns()` | `COLUMN_NAME` `TYPE_NAME` `DATA_TYPE` `COLUMN_SIZE` `DECIMAL_DIGITS` `IS_NULLABLE` `COLUMN_DEF` `ORDINAL_POSITION` `REMARKS` `IS_AUTOINCREMENT` `IS_GENERATEDCOLUMN` |
| 主キー | `getPrimaryKeys()` | `COLUMN_NAME` `KEY_SEQ` |
| 外部キー | `getImportedKeys()` | `FK_NAME` `FKCOLUMN_NAME` `PKTABLE_*` `UPDATE_RULE` `DELETE_RULE` |
| インデックス / ユニーク | `getIndexInfo(approximate=true)` | `INDEX_NAME` `NON_UNIQUE` `COLUMN_NAME` `ORDINAL_POSITION` |
| ネームスペース | `getSchemas()` / `getCatalogs()` | 空の場合は catalog にフォールバック |

**性能**: テーブル単位で `getColumns` を呼ぶと N 回の往復が発生する。`getColumns(catalog, schema, "%", "%")` で**一括取得し、メモリ上でテーブル別に分配**する。`getIndexInfo` は API 仕様上テーブル単位のため、対象テーブルに限定して並列実行する。

### 7.4 DB 差異の吸収

| 項目 | 対応 |
|---|---|
| MySQL は catalog = データベース、PostgreSQL は schema | `Namespace` として抽象化。`getSchemas()` が空なら catalog を使う |
| MySQL のコメント・メタデータ精度 | JDBC URL に `useInformationSchema=true` を推奨（GUI の URL テンプレートに既定で含める） |
| MySQL の `unsigned` | `TYPE_NAME` が `INT UNSIGNED` を返す。パースして `dialect.unsigned` に退避 |
| MySQL の `tinyint(1)` | `logicalType: "bool"` に正規化。`type` は原文を保持 |
| PostgreSQL の配列型 | `TYPE_NAME` の `_` 接頭辞から判定し `logicalType: "array"`、`dialect.elementType` に退避 |
| CHECK 制約 | JDBC 標準に API が存在しない。Enhancer で取得 |
| ユニーク制約とユニークインデックスの区別 | 標準では不可。区別せず扱う |
| 部分インデックス・式インデックス | 標準では不可。Enhancer で取得 |
| PostgreSQL の ENUM 型 | Enhancer で値一覧を取得し `dialect.enumValues` に格納 |

### 7.5 接続 UI

JDBC を採用したことで、DB ごとの接続フォーム定義は不要になる。**共通フォーム1つ**とする。

| 項目 | 内容 |
|---|---|
| JDBC URL | 既知ドライバにはテンプレートを提示（例: `jdbc:postgresql://localhost:5432/mydb`、`jdbc:mysql://localhost:3306/mydb?useInformationSchema=true`） |
| ユーザー / パスワード | パスワードは既定で保存しない |
| 追加プロパティ | key-value の任意追加 |
| 対象ネームスペース | 接続後に取得した一覧から**1つだけ**選択する（1プロジェクト = 1スキーマ。§1.2）。ここが唯一のスキーマ指定箇所であり、以後 GUI にスキーマ名は出ない |
| テーブルのフィルタ | **今回の内省に限った**包含 / 除外パターン |

**テーブルのフィルタと無視リスト（§5.4）は役割が異なる。**

| | テーブルのフィルタ（接続設定） | 無視リスト（`config.js`） |
|---|---|---|
| 有効範囲 | その回の内省のみ | プロジェクトに永続（Git 管理・チームで共有） |
| 既存定義への作用 | **なし**（除外したテーブルの既存定義は「対象外」として差分から除かれるだけ） | **あり**（既存定義があっても比較せず、削除候補にしない） |
| 主な用途 | 一時的に一部スキーマだけ取り込む | 管理テーブルの恒久除外、手動定義テーブル（J-01）の保護 |

### 7.6 GUI フロー

1. 接続情報を入力 → 接続テスト（ドライバ・DB製品名・バージョンを表示）
2. **対象スキーマ（1つ）**とテーブルフィルタを選択（§7.5）
3. 逆生成を実行 → **差分プレビュー**（追加 / 削除 / 変更をツリー表示。リネーム候補を提示し、承認・訂正できる。コメントから補完される論理名の初期値もここに提示する）。**無視リスト（§5.4）にマッチするテーブルは、DB 側・既存定義側の双方から除外され、件数のみ表示される**
4. 「適用」で `data/schema/**` を書き換え、`manifest.js` / `index.js` を更新。あわせて未設定の論理名をコメントから補完する（§5.8.2）
5. 新規テーブルは **「未配置」トレイ**に入る。ページへドラッグするか、自動配置ボタン（ELK）で配置する
6. 削除されたテーブルのノードは自動削除せず、警告表示のうえ明示操作で除去する

**この一連の処理で `data/diagrams/**`・`data/dictionary.js`・`data/config.js` は一切書き換えない。** 配置・論理名辞書・プロジェクト設定は人の操作としてのみ記録される（`meta.displayName` の初期値補完は §5.8.2 の条件下でのみ行われる）。

> 差分検出・リネーム推定・部分適用・適用のアトミック性の詳細は、[詳細設計: K-08〜K-13（逆生成の差分プレビューと適用）](function-details/K08-K13_introspect-diff-apply.md) を参照。

## 8. サーバー API

### 8.1 起動

- ポート `5321`（使用中なら自動インクリメント）、`127.0.0.1` のみに bind
- 起動時にランダムトークンを生成し、`http://127.0.0.1:5321/?t=<token>` をブラウザで自動オープン
- サブコマンドは `run`（既定）と `export`（閲覧用 ZIP。§3.2）だけ。サーバーが立ち上がった後の操作はすべて GUI

### 8.2 エンドポイント

**データ本体は API で返さない**（§4.3。`GET /workspace-<id>/data/**.js` の静的配信を `<script>` で読む）。以下の API は、書き込みと、書き込みに必要なメタ情報のためだけに存在する。

**データを触る API はすべて `/__erd/w/<ws>/…` の下にある。** ワークスペースに属さないのは、疎通確認・ワークスペース管理・ドライバ（全ワークスペース共通）・SSE・自動レイアウト（座標計算のみで書き込まない）だけである。

**唯一の例外が `POST /__erd/mcp`（§8.8）である。** MCP のクライアントは URL を設定ファイルに固定して使うため、
ワークスペースをパスに含めると**切り替えるたびに設定を書き換えさせる**ことになる。ワークスペースは
ツールの引数で受け、省略時は「1つならそれ、複数なら明示させる」とする。認証も別（MCP トークン）であり、
既存の `/__erd/**` とは資格情報からして違う経路になっている。

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/__erd/health` | モード判定。`schemaVersion`（データ形式）と `appVersion`（サーバーのリリース版。§3.1）を返す |
| GET / POST | `/__erd/workspaces` | ワークスペース一覧 / 追加（`{ id?, name }`。ID 省略時は `default`、重複は `409 DUPLICATE_ID`） |
| PATCH / DELETE | `/__erd/workspaces/:ws` | ID・表示名の変更（フォルダ名も変わる） / 削除（フォルダごと + `erd/.local/workspace-<id>/`） |
| GET | `/__erd/drivers` | ロード済み JDBC ドライバ・カタログ・共通設定（`erd/config.js`）・未取得の一覧 |
| PUT | `/__erd/drivers/config` | **全ワークスペース共通**のドライバ設定（`erd/config.js`）の更新 |
| POST | `/__erd/drivers/download` | ドライバ座標を Maven から取得し `drivers/` に置いて登録する |
| POST | `/__erd/layout/auto` | ELK による自動配置の座標を返す（**書き込みしない**。適用は PATCH で行う） |
| POST | `/__erd/export/viewer` | 閲覧用 ZIP を `application/zip` で返す（A-11 / §3.2）。ボディは `{prefix, workspaces:[]}`（省略時は既定のプレフィックス・全ワークスペース）。**複数ワークスペースを跨ぐため `/w/{ws}` に属さない**。ファイル名は `Content-Disposition` の `filename*`（RFC 5987。日本語可）で返し、サーバー側にはファイルを残さない |
| GET | `/__erd/events` | SSE。ファイル変更を配信（§8.7。`workspaceId` を含む） |
| GET / PUT | `/__erd/mcp/settings` | MCP の設定（有効 / 無効・書き込み許可・トークンの有無・最終アクセス）の取得 / 更新（Q-01）。**トークンの発行 / 再発行 / 削除もここ**。全ワークスペース共通 |
| POST | `/__erd/mcp` | **MCP 本体**（JSON-RPC 2.0 / Streamable HTTP。§8.8）。**認証はセッショントークンではなく MCP トークン**。無効時は 404。ワークスペースは引数で受けるため `/w/{ws}` に属さない |
| GET | `/__erd/w/:ws/project` | リビジョン、各ファイルの `baseHash`、`schemaVersion`、ブートストラップの要否 |
| POST | `/__erd/w/:ws/bootstrap` | 空ワークスペースの初期化（`{ mode: "sample" }` でサンプルデータを書き出す。§3.6） |
| POST | `/__erd/w/:ws/reset` | データリセット（そのワークスペースのスキーマ情報のみを削除。`config.js` は残す） |
| GET / PUT | `/__erd/w/:ws/connection` | 接続設定（`erd/.local/workspace-<ws>/connection.local.json`）の取得 / 保存（K-05。パスワードは明示的オプトイン） |
| POST | `/__erd/w/:ws/connection/test` | 接続テスト（製品名・バージョン・ネームスペース一覧を返す） |
| POST | `/__erd/w/:ws/introspect` | 逆生成を実行し、**差分プレビューを返すのみ**（書き込みしない）。プレビューセッションを発行する |
| GET | `/__erd/w/:ws/introspect/:sessionId` | 発行済みプレビューの再取得（ブラウザのリロード対策）。TTL 30分、失効時は `410`。**他のワークスペースのセッションは失効扱い** |
| POST | `/__erd/w/:ws/introspect/:sessionId/plan` | **リネーム決定を反映した差分プランの再計算**（DB へは再接続しない。書き込みしない） |
| POST | `/__erd/w/:ws/introspect/apply` | 差分（適用範囲の選択とリネーム承認結果を含む）を適用しファイルへ書き込む |
| GET / PUT | `/__erd/w/:ws/tables/:id` | スキーマ + `meta`（論理名・論理制約・注記）の `baseHash` 取得 / 編集 |
| GET / PUT | `/__erd/w/:ws/dictionary` | カラム辞書（同名カラムの共通設定）の取得 / 一括更新 |
| GET / PUT | `/__erd/w/:ws/config` | ワークスペースの設定（テーブル無視リスト）の取得 / 更新 |
| GET / POST / DELETE | `/__erd/w/:ws/diagrams[/:id]` | ページの取得 / 追加 / 削除 |
| PATCH | `/__erd/w/:ws/diagrams/:id` | レイアウトの差分保存（変更されたキーのみを送る） |

- **差分プランはリネーム決定に依存する**（承認すれば1項目の「リネーム」、却下すれば「削除 + 追加」の2項目になる）。決定が変わるたびに `POST /__erd/introspect/:sessionId/plan` でサーバーが再計算し、**差分ロジックをビューアに二重実装しない**。内省結果はセッションのスナップショットであり、この再計算で DB へ再接続することはない。
- **`PUT /__erd/tables/:id` の後は、何が変わったかを判定せず、無条件に `index.js` を再生成する。** 論理名・タグ・論理制約はいずれも `index.js`（`tables[].displayName` / `relations`）に影響し、条件分岐で最適化すると必ず漏れる（論理外部制約を保存したのに ER図に破線エッジが現れない、等）。生成コストは小さい。
- サーバーが停止している状態での書き込み要求はネットワークエラーとなる。ビューアはこれを**保存失敗**として扱い、接続エラーのメッセージと再試行を提示する（モードを勝手に切り替えたりはしない）。

### 8.3 書き込みの共通規約

**すべての書き込み API**（`PATCH /diagrams/:id`、`PUT /tables/:id`、`PUT /dictionary`、`PUT /config`、`POST /introspect/apply`、`POST/DELETE /diagrams`）に、以下を共通で課す。

| 要素 | 内容 | 違反時 |
|---|---|---|
| `baseHash` | **書き込み対象ファイルの、読み込み時点での内容ハッシュ**。必須 | `409 STALE` |
| `force` | `true` のとき `baseHash` の検証をスキップする（ユーザーが「上書き」を明示的に選んだ場合のみ） | — |

**編集ロックは設けない。** ローカル単独利用であり、不整合は「稀な例外」として保存時の `baseHash` 検証（§8.4）で止め、複数タブ / 外部の同時変更は §8.7 のバナー通知で検知する（ロックによる事前排他はしない）。

- 書き込みは常に**1本に直列化**する（クライアント側で保証。飛行中の要求が完了するまで次を送らない）。並行して投げると、後から届いた古い値が新しい値を上書きする。
- サーバーは書き込み時に**リビジョンID**を払い出し、SSE イベントに含める。ブラウザは自分が起点のリビジョンを無視することで、「書き込み → 監視検知 → 再読込」の無限ループを防ぐ。

### 8.4 保存時の競合検出（`baseHash`）

**競合の検出は書き込む瞬間にのみ行う。** 編集中はサーバーへ問い合わせない（ローカル単独利用であり、編集のたびに整合性を確認する必要がない）。

サーバーは書き込み直前に**ディスク上の実ファイルを読み直して内容ハッシュを計算**し、`baseHash` と一致しなければ**1バイトも書かずに `409 STALE` を返す**。これにより、`git pull` / エディタでの直接編集 / 逆生成の適用による外部変更を、黙って踏み潰すことがなくなる。

**判定は最終更新日時（mtime）ではなく内容ハッシュ（SHA-256）で行う。**

| 方式 | 問題 |
|---|---|
| mtime | `git checkout` は**内容が同じでも mtime を更新する**（誤検知 → 保存できない）。逆に、ファイルシステムの時刻解像度により**同一秒内の変更を取りこぼす**（検知漏れ → 外部変更を踏み潰す）。検知漏れは許容できない |
| **内容ハッシュ（採用）** | 誤検知も検知漏れもない。対象ファイルは数 KB であり、計算コストは無視できる |

> 実装上の最適化として、`mtime` と `size` が読み込み時と同一ならハッシュ計算を省略してよい（内容が変われば必ずどちらかが変わるため、検知漏れは生じない）。

`409 STALE` を受けたビューアは、**[再読込して自分の変更を破棄] / [自分の内容で上書き保存]** をユーザーに選ばせる。**自動でどちらかを選ばない。**

### 8.5 セキュリティ

- `127.0.0.1` バインド、トークン必須、`Origin` ヘッダ検証、CORS 無効
- **トークンは書き込み API だけでなくデータ配信にも要求する**（`/workspaces.js`・`/workspace-<id>/data/**`）。トークンを見ないのは `/`・`/index.html`（データを含まない）と `GET /__erd/health`（モード判定 A-01。トークン以前に到達性を確かめるためのもの）だけである
  - **理由:** データファイルは `ERD.table({...})` を呼ぶスクリプトである（§4.3）。無認証で配ると、**利用者が開いた任意の Web ページが `<script src="http://127.0.0.1:5321/workspace-*/data/**.js">` で読み出せてしまう**（`<script>` の読み込みは CORS で止まらないため、同一オリジンポリシーは防壁にならない）。ローカル専用でも、ブラウザからスキーマ全体が抜ける経路は塞ぐ
  - **渡し方:** `<script src>` にヘッダは付けられないため、クエリで渡す（`?t=<token>`。再読込時の `?v=<revision>` と併用）。`file://`（静的モード）にはトークンの概念が無いので何も付けない。**読み込み経路自体は1本のまま**である（§4.3 を壊さない）
  - **トークンがずれたときの見え方:** データが1つも読めないため画面は起動しない。ビューアはこれを「データが無い（welcome / ブートストラップ）」と取り違えないよう、`<script>` の失敗時に同じ URL を XHR で引き直して 403 を判定し、**専用の案内**（起動 URL を開き直す / 分からなければサーバーを再起動する / dev では `ERD_TOKEN=erd-dev`）を出す。編集 API だけが 403 になる場合（起動後にサーバーが再起動された等）も同じ案内を出す
  - 接続情報（`erd/.local/`）は**配信ルート自体が存在しない**。DB のデータ本体はツールが保持しない
- ファイル書き込みは `erd/workspace-<id>/data/` 配下に限定する（パストラバーサル禁止。ワークスペース ID も書式検証する）
- DB 認証情報は既定でメモリ保持のみ。保存する場合は `erd/.local/workspace-<id>/connection.local.json`（Git 管理外）とし、パスワード保存は明示的なオプトインとする
- **静的配信はディレクトリ公開ではなく、明示的に定義したルートだけ**（`/`・`/index.html`・`/workspaces.js`・`/workspace-<id>/data/<path>`）。`erd/` にファイルを置いても、それだけでは HTTP に露出しない。これが個人データ（`erd/.local/`）と JDBC ドライバを `erd/` の内側に置ける根拠であり、**新しい静的ルートを足すときはこの前提を壊していないか確認する**（`erd/` 全体を配信するルートを足してはならない）

#### `Host` ヘッダの検証（全ルート共通）

**`Host` ヘッダのホスト名が `127.0.0.1` / `localhost` / `[::1]` のいずれかであることを、共通ガードで確認する。**
DNS リバインディングは攻撃者のドメインを `127.0.0.1` に解決させる手口であり、そのとき `Host` には
攻撃者のドメインが載る。`Origin` 検証だけでは、`Origin` を送らない経路が素通りになる。

**判定はホスト名だけで行い、ポートは見ない。** 開発時の vite dev サーバーは `changeOrigin: false` で
プロキシしており（`viewer/vite.config.ts`）、Java サーバーに届く `Host` は**元の `localhost:5173` のまま**である。
「自分のポートと完全一致」で判定すると **dev 環境が丸ごと動かなくなる**。この性質はテストで固定する。

#### MCP トークン（§8.8）

MCP の認証は**セッショントークンとは別建て**とし、`erd/.local/mcp.json`（Git 管理外）に永続化する。

| | セッショントークン | MCP トークン |
|---|---|---|
| 寿命 | 起動ごとにランダム | **永続**（画面から発行・再発行・削除） |
| 置き場所 | メモリのみ | `erd/.local/mcp.json` |
| 渡し方 | URL クエリ `?t=`（`<script src>` にヘッダを付けられないため） | **`Authorization: Bearer`** |

- **セッショントークンを流用しない。** 起動のたびに変わるため、AI クライアント側の設定が毎回切れる。
  「画面で発行して貼る」運用は、トークンが再起動をまたいで有効であって初めて成立する。
- **`erd/config.js` に置いてはならない**（Git 管理対象であり、トークンがコミットされる）。`.local/` は同梱の `.gitignore` が除外する（§3.3）。
- **ガードは共用しない。** MCP エンドポイントはセッショントークンを受け付けず、逆に MCP トークンで他の API を叩けてもならない。
- `Origin` は既存ルートより厳しく、**欠落（＝ブラウザ以外のクライアント）か、サーバー自身のオリジンと完全一致**のみ許可する。

### 8.6 複数ファイルに跨る書き込みのアトミック性

逆生成の適用（K-11）は `schema/**`（複数）+ `manifest.js` + `index.js` + リネーム時は `diagrams/**`（複数）を**同時に**書き換える。1ファイルずつ置換すると「manifest だけ新しく schema は古い」中間状態が生じ、その隙間にファイル監視 → SSE → 再読込が走るとビューアが壊れた状態を読む。

- **適用前に `data/**` の全体を `erd/.local/workspace-<id>/backup/<timestamp>/` へコピーする**（Git 管理外。直近3世代をローテーション）
- 完成形を一時ディレクトリに生成 → 検証 → `ATOMIC_MOVE` で順次置換 → 削除対象を削除
- **置換中は SSE の配信を抑止し、完了後に単一のリビジョンとしてまとめて通知する**
- 途中で失敗した場合はバックアップから復元し、**適用前の状態に完全に戻す**（部分適用された壊れた状態を残さない）

詳細は [詳細設計: K-08〜K-13](function-details/K08-K13_introspect-diff-apply.md) §6 を参照。

### 8.7 別タブ・外部変更の検知（バナー通知）

**編集ロックは設けない**（§8.3）。同一ブラウザの複数タブ、`git pull` / エディタでの直接編集、逆生成の適用は、いずれも SSE（`GET /__erd/events`）で検知し、**バナーで再読込を促す**（強制はしない。無視して編集を続けられる）。

- ファイル監視・リビジョンは**ワークスペースごとに独立**している（`index.js` のようにパスが重なるため）。SSE イベントには `workspaceId` を載せ、**別のワークスペースを開いているタブは無視する**。
- サーバーは書き込み時に**リビジョンID**を払い出し、SSE イベント `{ workspaceId, revision, files }` に含める。各タブは自分の書き込みリビジョンを**リングバッファ（直近20件）**に保持し、SSE の `revision` がそこにあれば**自分起因として無視する**（「書き込み → 監視検知 → 再読込」ループの防止）。**タブごとの ID は持たない**（自分のリビジョン集合で「自分か / 他者（別タブ・外部）か」を判別できる）。
- 未知のリビジョンは「他者の変更」として扱い、ビューアが分岐する（詳細は [H-09](function-details/H01-H13_layout-edit-sync-undo.md) §6）:
  - **閲覧中で未保存がない画面** → 静かに再読込する（バナーを出さない）。
  - **編集ルート滞在中の画面** → **バナー[再読込]/[無視]** を表示する。他の通知より重要度が高いためトーストではなくバナーとする。[再読込] を選び未保存があれば破棄を確認する。
- **バナーは二重に開かない**（既に表示中なら対象ファイルを追記する）。**「このタブ内では通知しない」チェック**を設け、選択は `sessionStorage`（タブを閉じるまで有効）に保持する。
- 最終的な安全網は保存時の `baseHash` 検証（§8.4）である。バナーを無視して古い状態のまま保存を試みても、`409 STALE` で止まり、破棄 / 上書きを選べる（人の変更を黙って消さない）。

### 8.8 MCP 連携（AI クライアントからの参照・編集）

**ER図・テーブル定義・論理名・注記を、MCP クライアント（Claude Code 等）から参照・編集できるようにする。**
主用途は「既存のソースコードから業務ドメインを推測し、ページを切って ER図 を起こす」ことである。

詳細は [詳細設計: Q-01〜Q-06](function-details/Q01-Q06_mcp.md) を参照。

#### 配置とライフサイクル

**既存の Javalin サーバーに `POST /__erd/mcp` を1本足すだけとし、別プロセス・別ランタイムは立てない。**
ライフサイクルは Web サーバーと完全に同一で、**MCP を使うにはサーバーモードでの起動が必須**である。

| 採らなかった案 | 理由 |
|---|---|
| Node の別プロセス | 配布物に第2のランタイムが増える。§1.2 の非スコープ（npm / npx 配布）に抵触する |
| Node からデータファイルを直読み | `ERD.table({...})` のパーサと決定論的プリンタを TypeScript で**二重に持つ**ことになる（§5.1 の単一実装が崩れる） |
| jar の `mcp` サブコマンド（stdio） | §3.2 のサブコマンド追加が要る。加えて stdout がプロトコルの通信路になるため `println` 1 行で壊れ、MCP クライアントが任意の cwd で起動するため `--root` も要る。**セッションごとに JVM が常駐**する |

同一プロセスに相乗りする利点は、面倒が消えることだけではない。**`AutoLayout`（ELK）をそのまま呼べる**ため、
「テーブルの集合だけを AI に選ばせ、座標はサーバーが計算する」という分担が成立する（下記）。

代償として、**サーバーを止めると AI からツールが見えなくなる**。またポートは自動インクリメントするため、
再起動でポートが変われば AI 側の設定が切れる（症状は接続失敗であり、トークン不一致により誤接続はしない）。

#### トランスポート（2 世代を同時に喋る）

**Streamable HTTP**。`POST /__erd/mcp` が JSON-RPC 2.0 を受け、`application/json` で返す。

MCP の仕様は改訂 **`2026-07-28`** で大きく変わり、**`initialize` のハンドシェイクが廃止**されて
**リクエストごとにメタ情報を載せるステートレス方式**になった。仕様は前者を legacy、後者を modern と呼ぶ。

| | legacy（`2025-11-25` 以前） | modern（`2026-07-28` 以降） |
|---|---|---|
| 開始 | `initialize` → `notifications/initialized` | **なし**。各リクエストの `params._meta` が版を運ぶ |
| 版の宣言 | initialize で 1 回 | **毎リクエスト**（`MCP-Protocol-Version` ヘッダにも載り、本文と一致しなければ拒否） |
| 能力の照会 | initialize の応答 | **`server/discover`**（サーバーは実装必須） |
| セッション | `Mcp-Session-Id` | 廃止 |
| GET による SSE ストリーム | あり | 廃止 |

**両方を実装する（dual-era）。** 仕様の互換性マトリクスでは「legacy クライアント × modern のみのサーバー」は
**失敗する**とされており、どちらか一方だけでは手元のクライアントか将来のクライアントのどちらかで動かない。
仕様自身が「dual-era サーバーは同一エンドポイントで両方を提供してよい」と認めている。

- **世代の判定はリクエストの形で行う**（仕様どおり）。`params._meta` に
  `io.modelcontextprotocol/protocolVersion` があれば modern、`initialize` が来たら legacy。
- 実装するメソッドは **legacy**: `initialize` / `notifications/initialized` / `tools/list` / `tools/call` / `ping`、
  **modern**: `server/discover` / `tools/list` / `tools/call` / `ping`。
- **`GET` / `DELETE` は 405 を返す。** サーバー起点の通知を送らないため SSE ストリームを開かず、
  セッションも発行しない（いずれも仕様上許容される）。
- 対応版は 1 箇所の定数に置き、テストで固定する。
- **ツールの実体はトランスポートから分離する**（純粋なクラスに置き、JSON-RPC 層から呼ぶだけにする）。

#### 書き込み境界 — 物理情報は書けない

**逆生成が正であるもの（machine-owned）は MCP から書けない。それ以外は書ける**（§5.1）。

| 分類 | 具体 | MCP から |
|---|---|---|
| 物理情報 | `id` / `name` / `schema` / `kind` / `comment`、`columns`、`primaryKey`、`uniques`、`foreignKeys`、`indexes` | **✗** |
| 論理情報 | `meta.displayName` / `notes` / `tags` / `color`（テーブル・カラム）、`meta.logicalUniques` / `logicalForeignKeys` / `relations` | ✓ |
| ER視覚情報 | ページの作成 / 削除 / 改名 / 表示順、ノードの配置と除去（`diagrams/**` + `manifest.diagrams`） | ✓ |
| ワークスペース設定 | `dictionary.js`、`data/config.js` の `ignoreTables` | ✓ |
| 破壊的・波及あり | テーブルの新規作成 / 削除 / リネーム、ワークスペース操作、逆生成、接続設定、データリセット、閲覧用 ZIP | **✗** |

**除外は権限の話ではなく整合性の話である。** 物理情報を MCP から書けるようにすると、次の逆生成で
DB を正として上書きされ、AI が書いた内容が黙って消える。DB に無いテーブルを手で持ちたい場合の入口は
J-01（テーブルの手動作成）であって MCP ではない。

**この非スコープはセキュリティ境界でもある。** DB 接続・ネットワーク送信・任意ファイル読み取りを一切持たないため、
プロンプトインジェクション（DB のコメントや注記に指示文を仕込む攻撃）が成立しても**持ち出す口がない**。

#### 座標を AI に書かせない

LLM は「どのテーブルを同じページに置くか」という意味的判断は得意だが、重なりのない座標を出すのは苦手で、
1 テーブルずつ座標を考えさせるとツール呼び出しを浪費する。**配置ツールはテーブル ID の集合を受け取り、
座標はサーバーが `AutoLayout` で計算する。** 明示座標のツールも置くが、通常は使わせない。

#### 安全網

書き込み範囲が広いため、**「AI に任せて、人が `git diff` で見る」が成立すること**を条件とする。

| 層 | 内容 |
|---|---|
| Git | データはテキストで差分がレビュー可能（§10）。**最後の砦** |
| バックアップ | 既存の `Backups`（§8.6）を再利用し、MCP からの書き込み前に `data/**` をスナップショットする。毎回取ると 3 世代がすぐ埋まるため、サーバー起動後の最初の書き込みと、前回から一定時間経過したときに取る |
| `baseHash` | 人の編集・`git pull` との競合を検出して止める（§8.4）。**MCP からは `force` を使わせない**。`STALE` なら 1 回だけ読み直して再試行し、それでも駄目ならエラーを返す |
| SSE バナー | MCP の書き込みは GUI と同一プロセス・同一サービスを通るため `Revisions` が採番し、開いているタブに**外部変更として通知される**（§8.7）。新しい通知経路は要らない |
| 有効化ゲート | 画面の「書き込みを許可」がオフの間は `tools/list` にも出さず、直接呼んでも拒否する |
| 範囲の制限 | 物理情報とテーブルの作成・削除・リネームを塞いでいるため、**壊せるのは「人が書いた情報」と「図の見た目」だけ**。物理情報は逆生成をやり直せば必ず復元する |

#### 有効化と設定（GUI）

**既定は無効。** 無効時は `POST /__erd/mcp` 自体が 404 を返す。有効化・トークン発行・書き込み許可は
設定画面（Q-01）でのみ行い、**設定は全ワークスペース共通**（`erd/.local/mcp.json`）とする。
書き込み許可のトグルは **1 段**（オンなら書き込みツールがすべて現れる）。

## 9. ER図ビューア / エディタ

### 9.1 ER図とテーブルカタログの分離

**ER図は「テーブル間の関係の俯瞰」に責務を限定し、テーブルの中身は別画面（テーブルカタログ）で扱う。**

| | ER図 | テーブルカタログ |
|---|---|---|
| 目的 | 関係の俯瞰・探索 | 定義の閲覧・編集 |
| 描画単位 | **テーブル名のみのノード** + リレーション線 | 表形式の一覧 / 1テーブルの全定義 |
| ルート | `#/erd/<diagramId>` | `#/tables`, `#/tables/<id>`, `#/tables/<id>/edit`, `#/tables/doc/<id>`（ドキュメントモード。R-01） |
| 編集 | 配置（座標・ページへの追加 / 除去）と、**リレーション**（論理外部制約の作成・編集・削除、カーディナリティ。E-11 / E-12） | スキーマ・論理名・論理制約・注記 |

- **ER図のノードにカラムを描画しない。** ノードはテーブル名（論理名 / 物理名）とスキーマ名のみを表示する。
- ノードを**ダブルクリック**すると、テーブル詳細を**閲覧専用のダイアログ**で表示する。ダイアログにはテーブル詳細画面（`#/tables/<id>`）への実リンクを置き、編集はそちらで行う。
- リレーション線を**ダブルクリック**すると、リレーション詳細（種別・参照元 / 先・カラム対応・ON DELETE / UPDATE・カーディナリティ）をダイアログで表示する。両テーブルの詳細画面へのリンクを含む。**閲覧ルートでは読むだけ**で、編集ルート滞在中だけ編集できるダイアログになる（E-11。物理 FK はカーディナリティと注記のみ、論理外部制約は定義ごと）。この編集は**確定＝即時保存**であり、配置編集の Undo / 明示保存とは別の経路である。
- テーブル詳細画面からは、そのテーブルが配置されている ER図ページへのリンクを提供する（複数ページに配置されている場合はページを選択させる）。

この分離により、ER図の描画コストとロード依存が大きく下がる（§6.1）。

### 9.2 キャンバス

**React Flow を使用する。Canvas / WebGL 方式は採用しない。**

ノードはテーブル名のみだが、ホバー・テキスト選択・検索ハイライト・リンク（`<a href>`）・キーボード操作・スクリーンリーダー対応を要するため、DOM / SVG 描画が有利である。ページ分割により1ページあたりのノード数を抑えるため、性能上の問題は生じない。

### 9.3 ズーム / パン

React Flow の標準機能（d3-zoom ベース）を使用する。

- ホイールズーム、ピンチズーム、ドラッグパン
- `Controls`（ズームイン / アウト / フィット / ロック）と `MiniMap` を配置
- ズーム範囲は `minZoom: 0.1`, `maxZoom: 2.5`。初期表示は `fitView`

**LOD（ズーム率による描画粒度の切替）は行わない。** ノードは常にテーブル名のみであり、切り替える粒度が存在しない。

### 9.4 ノードとエッジの表現

| 要素 | 表現 |
|---|---|
| ノード | テーブル名（論理名 / 物理名 / 併記を切替可）のみ。**スキーマ名は表示しない**（単一スキーマ前提。§1.2）。`meta.color`（指定色）で背景・枠線を着色する（タグとは連動しない。§5.7）。**欠損の警告色と選択枠は指定色より優先**し、関連ハイライトの減光は不透明度で表す（表現の軸を分ける） |
| 物理 FK エッジ | **実線**。鳥の足記号でカーディナリティを表示 |
| 論理 FK エッジ（`meta.logicalForeignKeys`） | **破線**。凡例で物理 FK との違いを明示 |
| 複合キー | 1本のエッジに集約（カラム対応はダブルクリックの詳細ダイアログで確認する） |

### 9.5 性能最適化

- ノードコンポーネントの `React.memo` 化
- `onlyRenderVisibleElements: true`
- ドラッグ中は再レンダリングを抑制し、確定時のみ状態を更新する

### 9.6 機能一覧

| 機能 | 静的モード | サーバーモード |
|---|---|---|
| ページ切替、パン / ズーム、MiniMap | ✓ | ✓ |
| テーブル / カラム検索（全ページ横断） | ✓ | ✓ |
| リレーションのハイライト・追跡（物理 / 論理） | ✓ | ✓ |
| ノードのダブルクリック → テーブル詳細ダイアログ（閲覧専用） | ✓ | ✓ |
| エッジのダブルクリック → リレーション詳細ダイアログ | ✓ | ✓ |
| テーブルカタログ（一覧・詳細）の閲覧 | ✓ | ✓ |
| 言語切替（日本語 / 英語） | ✓ | ✓ |

| ノードのドラッグ移動、整列、Undo / Redo | ✓（**保存されない**） | ✓（保存される） |

| DB からの逆生成 | ✗ | ✓ |
| 自動レイアウト（ELK） | ✗ | ✓ |

### 9.7 静的モードでの編集とエクスポート

静的モードでも編集セッションを開始でき、ドラッグ・整列・Undo はすべて動作する。**保存手段がないため、変更は「配置のエクスポート」で持ち出す。**

- 編集開始時に「変更は保存できません。エクスポートして `workspace-<id>/data/diagrams/*.js` に貼り付けてください」と警告する
- エクスポートは、現在の配置を **`ERD.diagram({...})` の生の JavaScript コードとしてダイアログに表示**し、全選択・コピーできるようにする（`file://` ではダウンロードの挙動が環境依存のため、貼り付け方式の方が確実）
- 自動レイアウト（ELK）はサーバー API に依存するため静的モードでは使えない
- リロード・離脱で変更は消える（**離脱時の警告は出さない**。保存手段がなく、警告しても行動を変えられないため。代わりにエクスポート導線を常時表示する）

> **実装上の注意**: これはクライアント側にも決定論的プリンタ（§5.11 の書式規約）が必要であることを意味する。サーバー（Java）とクライアント（TS）で**二重実装**になるため、**両者に同一の golden ファイルによるテストを課し、同じ入力から同じ文字列が出ることを CI で保証する**。ズレた場合の実害は「貼り付けたファイルが次回のサーバー保存時に整形し直され、余計な Git 差分が1回出る」程度だが、放置すると差分ノイズの原因になる。

## 10. Git 運用規約

**原則: `erd/` の中身はすべて Git 管理する。** 例外は JDBC ドライバの jar だけ。

| 対象 | Git 管理 | 備考 |
|---|---|---|
| `erd/index.html` | ✓ | メンバーが pull だけで閲覧できるようにするため。`.gitattributes` で `binary` 指定し diff ノイズを抑制 |
| `erd/workspace-*/data/**`・`erd/workspaces.js`・`erd/config.js` | ✓ | レビュー対象。差分が読める形式であること（`config.js` / `dictionary.js` を含む） |
| `erd/erd-server.jar`・`erd/erd.sh`・`erd/erd.bat` | ✓ | 全員が同じ版で動かすため。更新は新しい ZIP で上書きしてコミットする |
| `erd/.gitignore`・`erd/.gitattributes`・`erd/drivers/README.txt` | ✓ | 配布 ZIP に同梱している固定ファイル |
| `erd/drivers/*.jar` | ✗ | ライセンスの都合で同梱せず、各自が逆生成画面から取得する（§7.2） |
| `erd/.local/**` | ✗ | 接続設定・個人設定（言語・ビューポート）・適用前バックアップ。同梱の `.gitignore` が除外済み |

- コミット単位の推奨: 「逆生成の適用」「ER図の配置変更」「論理名・論理制約の整備」は別コミットに分ける
- ダイアグラムはページ単位でファイルが分かれるため、複数人が別ページを編集してもコンフリクトしない
- スキーマはテーブル単位でファイルが分かれるため、変更のあったテーブルのみが差分に現れる

### 11.1 リスクと対策

| リスク | 対策 |
|---|---|
| 書き戻しで人の注記・論理名・論理制約が失われる | それらを `meta` に構造化し、逆生成の対象外とする。フェーズ0の往復テストで保証する。唯一の例外（未設定時の論理名補完）は「既存値を上書きしない」を単体テストで固定する |
| ドラッグ由来の差分ノイズ | 座標のグリッドスナップ + 整数化を初期実装から入れる（後付けすると全ファイルが一度書き換わる） |
| `index.html` とデータ形式の不整合 | `schemaVersion` による検証と警告バナー |
| ドライバごとの `DatabaseMetaData` 実装差異 | Testcontainers で実DBに対する内省を CI で検証する。層1で取得できない情報は Enhancer に隔離する |
| `drivers/*.jar` のドライバが `DriverManager` から見えない | `DriverShim` によるラッパ登録で対応する |
| 1つの巨大ER図への集約による破綻 | ページを一級の概念として初期から設計する |
| 書き込み → 監視 → 再読込のループ | リビジョンIDのエコーバックによる自己起因変更の無視 |
| 論理名の解決順序（個別 / 辞書 / 物理名）が画面ごとにズレる | 解決ロジックをビューアの `model/` 層の単一関数に集約し、全画面がそれを経由する |
| `index.js` の `relations` とスキーマファイルの不整合 | `index.js` はサーバーが `schema/**` から必ず再生成する派生ファイルとし、手編集を許さない。整合性チェック（M-04）で検出する |
| 疑似リンク（`onClick` のみ）の混入で Ctrl+クリックが効かない | 遷移を伴う UI は共通の `<Link>` コンポーネントに限定し、Playwright で修飾キー付きクリックの挙動を検証する |
| 外部変更（`git pull` / エディタ編集）を保存が踏み潰す | すべての書き込みに `baseHash`（読み込み時の内容ハッシュ）を必須とし、不一致なら書かずに中止する（§8.4） |
| 決定論的プリンタの二重実装（Java / TypeScript）による出力のズレ | 同一の golden ファイルによるテストを両実装に課し、CI で出力の一致を保証する（§9.7） |
