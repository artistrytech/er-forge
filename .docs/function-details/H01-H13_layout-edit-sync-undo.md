## 0. 前提

### 0.1 利用形態

**このツールはローカルで単独利用する。** サーバーは `127.0.0.1` にのみ bind され、編集者は1人である。この前提が設計を大きく単純化する。

| 前提 | 帰結 |
|---|---|
| **複数人の同時編集を考慮しない** | 差分マージ・OT・CRDT の類は一切導入しない。競合は「滅多に起きない例外」として扱い、**検出して止め、人が再操作すれば復旧できる**設計にする |
| **競合の検出は保存時のみ** | 編集中は競合を気にしない（編集のたびにサーバーへ問い合わせない）。**書き込む瞬間に、書き込み対象ファイルが変わっていないことだけを確認する** |
| **同一ブラウザの複数タブは起こりうる** | 編集開始時に**ロック**を取り、他タブからの編集を禁じる（§2.3） |
| **外部変更は起こりうる** | `git pull` / `git checkout`、エディタでの直接編集、逆生成の適用（K-11）。SSE で検知する（§6） |

### 0.2 用語：動作モード と 編集セッション（区別する）

**「モード」という語が2つの異なる概念に使われていたため、ここで分離する。**

| 概念 | 値 | 決まり方 |
|---|---|---|
| **動作モード** | 静的モード / サーバーモード | 起動方法で決まる（`file://` か `java -jar` か）。ユーザーは切り替えられない |
| **編集セッション** | 閲覧中 / 編集中 | **ユーザーが明示的に切り替える**（「編集」トグル）。**静的モードでも編集できる**（ただし保存はできない。§9） |

- 起動直後は必ず**閲覧中**である。ノードは動かせない（誤操作で配置が変わらない）。
- 「編集」を押して初めて編集中になる。ヘッダに常時明示する。

### 0.3 不変条件

| # | 不変条件 | 破られたときに起きること |
|---|---|---|
| INV-1 | **人の変更が黙って消えない。** 外部変更の取り込みで未保存の変更を自動破棄しない | 数分の作業が無言で消える |
| INV-2 | **保存された座標 = 画面上の座標。** 8px スナップ・整数化はクライアントの状態に入れる時点で適用する | 「送った値 ≠ 保存された値」で画面が飛ぶ。あるいは毎回 Git 差分が出続ける |
| INV-3 | **自分の書き込みで自分が再読込しない**（リビジョンのエコーバック） | 書き込み → 監視 → 再読込の無限ループ |
| INV-4 | **編集操作は必ずコマンドを経由する。** ストアを直接書き換える経路を作らない | Undo できない操作が生まれ、スタックと実体がズレる |
| INV-5 | **書き込みは、対象ファイルが読み込み時から変わっていない場合にのみ成立する** | 外部変更（`git pull` や逆生成）を黙って踏み潰す |
| INV-6 | **書き込み要求は常に1本だけ飛ぶ**（直列化） | 後から届いた古い座標が新しい座標を上書きする |

## 1. 状態モデル

### 1.1 3層に分ける

```
┌─ committed  ─────────────────────────────────────────────────┐
│  サーバー上のファイルと一致していると信じている状態              │
│  { revision, baseHash: { "diagrams/core.js": "sha256:…" },   │
│    diagram: {...} }                                          │
└──────────────────────────────────────────────────────────────┘
              ▲ 保存成功 / 外部変更の取り込みで置き換わる
┌─ pending ────────────────────────────────────────────────────┐
│  まだファイルに書かれていないコマンドの列                       │
│  Command[]     （自動保存: 300ms で自動 flush）                │
│                （手動保存: Ctrl+S / [保存] を押すまで溜まる）    │
└──────────────────────────────────────────────────────────────┘
              ▲ ユーザー操作で追加、保存成功で空になる
┌─ view ───────────────────────────────────────────────────────┐
│  画面に描かれる状態 = committed に pending を適用した結果        │
└──────────────────────────────────────────────────────────────┘
```

- **`view` は導出値**であり、独立した真実の源にしない。
- **保存状態（H-04）は `pending` の有無と飛行中の要求の有無から導出する**（別途フラグを持たない）。

### 1.2 コマンド（INV-4）

すべての編集操作を「適用と反転ができる値」として表現する。これが Undo（H-05）と保存（H-03）の**共通の土台**になる。

```ts
type Command =
  | { type: "moveNodes";    changes: { [tableId]: { from: Pos, to: Pos } } }  // H-01/H-02/H-06/H-07/H-08/N-05
  | { type: "resizeNode";   tableId: string, from: number, to: number }       // D-02
  | { type: "addNodes";     nodes: { [tableId]: NodeVisual } }                // I-04
  | { type: "removeNodes";  nodes: { [tableId]: NodeVisual } }                // I-06/N-04（除去前の値を持つ＝Undo可能）
  | { type: "setWaypoints"; edgeId: string, from: Pos[], to: Pos[] }          // E-07
```

- **すべてのコマンドが `from` と `to` を持つ。** 反転は入れ替えるだけで済み、Undo が1関数に収まる。
- **複数ノードの移動（H-02）・整列（H-06）・自動レイアウト（H-07 / H-08）はすべて `moveNodes` 1個**として記録する。50ノードを一括で動かしても Undo 1回で戻る（ユーザーの「1操作」と Undo の粒度を一致させる）。
- コマンドは**ページ（diagram）に閉じる**。

## 2. 編集セッション（閲覧 ⇄ 編集）

### 2.1 明示的な切り替え

| 遷移 | 挙動 |
|---|---|
| 閲覧中 → 編集中 | サーバーモード: **編集ロックを取得**（§2.3）。失敗したら編集中にならない<br>静的モード: **警告ダイアログ**「変更は保存できません」（§9） |
| 編集中 → 閲覧中 | 未保存の変更があれば確認。破棄 / 保存 / キャンセルを選ばせる。ロックを解放する |

- **閲覧中はノードをドラッグできない**（パン・ズーム・選択・ダイアログは可能）。編集 UI（整列・自動レイアウト）も出さない。
- ブラウザを閉じる / タブを閉じるときに、`navigator.sendBeacon` でロック解放を試みる（失敗しても heartbeat 途絶で自動失効するため実害はない）。

### 2.2 ヘッダの表示（A-02 の改訂）

動作モードと編集セッションは直交するため、**両方を表示する**。

```
[サーバーモード]  [● 編集中]  [自動保存: ON]  保存済み
[サーバーモード]  [　閲覧中 ]                  [編集を開始]
[静的モード]      [● 編集中]  ⚠ 保存されません  [配置をエクスポート]
[静的モード]      [　閲覧中 ]                  [編集を開始]
```

### 2.3 編集ロック（複数タブ対策）

**サーバーモードでのみ有効。** ロックの粒度は**プロジェクト全体で1つ**とする（ページ単位に細分化しない。単独利用のため複雑にする理由がない）。

| 項目 | 仕様 |
|---|---|
| 取得 | `POST /__erd/lock` → `{ lockId, acquiredAt }`。以後、**すべての書き込み API は `lockId` を必須**とする |
| 維持 | 15秒ごとに `PUT /__erd/lock`（heartbeat） |
| 失効 | heartbeat が **60秒**途絶したら自動失効（タブのクラッシュ・スリープ対策） |
| 解放 | `DELETE /__erd/lock`（編集終了・タブ閉じ） |
| 保持 | サーバーのメモリ。**サーバー再起動で消える**（永続化しない） |

**他タブが編集を試みた場合**（`423 Locked`）:

```
このプロジェクトは別のタブ（または別のウィンドウ）で編集中です。
  最終操作: 2分前
  [ そのタブに切り替える ]  [ 強制的に編集を開始する ]
```

- **強制取得を許す。** ローカル単独利用であり、「前に開いたまま忘れたタブ」に締め出される方が実害が大きい。
- 奪われた側は次の heartbeat（最大15秒後）で失効を検知し、**閲覧中に強制降格**する。未保存の変更があれば破棄せずに保持し、**エクスポートダイアログ（§9.2）で取り出せるようにする**（INV-1）。

## 3. H-01 / H-02 ドラッグ移動

### 3.1 ドラッグ中と確定の分離

| 局面 | 挙動 |
|---|---|
| `onNodeDrag`（ドラッグ中） | React Flow の内部状態のみが動く。**コマンドを積まない・保存しない・Undo スタックに触らない** |
| `onNodeDragStop`（確定） | 移動量が 0 でなければ `moveNodes` コマンドを1つ積む。ここで座標が正規化される |

ドラッグ中に毎フレーム コマンドを積むと、Undo スタックがゴミで埋まる。**「手を離したとき」が1操作**である。

### 3.2 座標の正規化（INV-2）

```
normalize(pos) = [ round(x / 8) * 8, round(y / 8) * 8 ]
```

- **コマンドを作る時点で正規化する。** 画面の値・保存する値・ファイルの値がすべて一致する。
- サーバー側でも受信時に再度正規化する（防御的）。
- 正規化の結果、移動前と同一座標になった場合は**コマンドを積まない**（8px 未満のドラッグは「操作なし」）。これがないと、クリックしただけで dirty になる。

### 3.3 複数選択の移動（H-02）

相対位置を保ったまま移動し、**確定時に全ノードを個別に正規化**する。代表ノードだけ正規化して他を相対配置にすると、グリッドから外れたノードが生まれる。

## 4. H-03 保存 / H-04 保存状態

### 4.1 自動保存と手動保存（切替可能）

**個人設定（L-02）として切り替える。既定は自動保存。**

| モード | 挙動 |
|---|---|
| **自動保存** | コマンド追加から **debounce 300ms**（maxWait 2000ms）で自動的に書き込む。`Ctrl+S` で即時 flush もできる |
| **手動保存** | 変更は `pending` に溜まり続ける。**`Ctrl+S` または [保存] ボタン**で初めて書き込む。ヘッダに未保存の件数（「未保存の変更が 12 件」）を表示し、離脱時に警告する |

手動保存は「まとめて整えてから、意図したタイミングで1つの Git 差分にしたい」という使い方に対応する。自動保存のまま作業すると、途中経過が細かくファイルに書かれる（ファイル内容としては同じ結果になるが、外部エディタや Git の watch と噛み合わないことがある）。

### 4.2 保存の状態機械

```
        コマンド追加
   ┌──────────────────────────► dirty ──── 自動: 300ms経過 / 手動: Ctrl+S ───┐
   │                              ▲                                          │
 saved ◄── 成功 & pending空 ──────┤                                          ▼
   ▲                              │                                       saving
   │                    (保存中に新たな変更)                                   │
   │                              └──── 成功 & pending有 ◄────────────────────┤
   │                                                                          │
 failed ◄─── 失敗（接続エラー / 5xx / 409 STALE / 423 ロック喪失）─────────────┘
```

| 状態 | ヘッダ表示（H-04） |
|---|---|
| `saved` | 「保存済み」（控えめ。数秒でフェード） |
| `dirty`（自動保存） | 「保存中…」 |
| `dirty`（手動保存） | **「未保存の変更が N 件」＋ [保存] ボタン** |
| `saving` | 「保存中…」 |
| `failed` | **「保存に失敗しました」＋ 原因 ＋ [再試行]**。目立つ色で常時表示し、消えない |

- **書き込み要求は常に1本だけ**（INV-6）。飛行中に新たなコマンドが積まれたら `pending` に溜め、完了後に次を送る。
- 同一キーへの複数コマンドは**送信時に畳む**（同じノードを3回動かしても送るのは最終座標1つ）。ただし **Undo スタックには3件残す**（保存の粒度と Undo の粒度は別物）。
- 失敗時は自動リトライ（1s → 4s → 10s、最大3回）。以後は手動リトライのみ。**未保存の変更はメモリに保持し続ける**（M-02。INV-1）。

### 4.3 競合検出（保存時のみ・ファイル単位）

**編集中は競合を検出しない。** サーバーへ問い合わせるのは書き込む瞬間だけである。

書き込み要求には、**読み込み時に受け取った対象ファイルの内容ハッシュ（`baseHash`）を必ず添える**。サーバーは書き込み直前に**ディスク上の実ファイルを読み直してハッシュを計算**し、一致しなければ**書き込まずに `409 STALE` を返す**（INV-5）。

#### なぜハッシュか（最終更新日時ではなく）

| 方式 | 問題 |
|---|---|
| **mtime（最終更新日時）** | `git checkout` / `git pull` は**内容が同じでも mtime を更新する**（誤検知 → 保存できないのに理由が分からない）。逆に、ファイルシステムの時刻解像度（環境により1〜2秒）により、**同一秒内の変更を取りこぼす**（検知漏れ → 外部変更を踏み潰す）。検知漏れは INV-5 の破壊であり、許容できない |
| **内容ハッシュ（採用）** | 誤検知も検知漏れもない。「内容が変わったか」を直接見ている。対象ファイルは数 KB であり、SHA-256 の計算コストは無視できる |

> 実装上の最適化として、**mtime + size が読み込み時と同一なら、ハッシュ計算を省略して「変更なし」と判定してよい**（高速な事前フィルタ）。これは検知漏れを生まない（内容が変われば mtime か size のどちらかは必ず変わる）。

#### `409 STALE` を受けたときの UI

```
保存できません。ファイルが外部で変更されています。
  data/diagrams/core.js（git pull、逆生成の適用、またはエディタでの編集）

  [ 再読込する（自分の変更を破棄） ]   [ 自分の内容で上書き保存 ]
```

- **自動でどちらかを選ばない**（INV-1）。
- 「上書き保存」は `force: true` を付けて再送する（`baseHash` の検証をスキップ）。
- 「再読込」を選んだ場合、`pending` を破棄して再ロードし、**Undo スタックも破棄する**（§5.3）。ユーザーは再操作すればよい（ローカル単独利用であり、競合は例外的である）。

### 4.4 書き込みペイロード

```jsonc
PATCH /__erd/diagrams/core
{
  "lockId":   "l-7c2a…",
  "baseHash": "sha256:9f1a…",       // 読み込み時の diagrams/core.js の内容ハッシュ
  "force":    false,
  "nodes": {
    "public.users":  { "pos": [120, 80], "w": 260 },
    "public.legacy": null                            // null = このページから除去（I-06）
  },
  "edges":  { "public.users#fk:users_org_id_fkey": { "waypoints": [[380,200]] } }
}
```

レスポンス: `200 { revision, newHash }` / `409 { code: "STALE", currentHash }` / `423 { code: "LOCK_LOST" }`

**部分更新（変更されたキーのみ送る）は維持する。** 同時編集のためではなく、**外部変更の巻き添えを最小化するため**である。ページ全体を送ると、自分が触っていないノードまで自分の古い値で上書きしてしまう。

## 5. H-05 Undo / Redo

### 5.1 スコープ：**ER図ページ単位のレイアウト操作に限定**

> 機能一覧 H-05 の「レイアウト操作・**スキーマ編集**を対象」から**変更**（§12.1）。

- Undo スタックは **ページ（diagram）ごとに1本**。
- **スキーマ編集（O-03 / J-*）を同じスタックに載せない。** 別画面（`#/erd/…` と `#/tables/…/edit`）であり、単一スタックにすると「テーブル編集画面で Ctrl+Z を押したら別ページのノード移動が戻る」という予測不能な挙動になる。テーブル編集画面の取り消しは、フォーム内のブラウザ標準の取り消しと「変更を破棄」（保存前）で提供する。
- ページを切り替えても各ページのスタックは保持する（戻れば Undo できる）。**リロードで消える**（永続化しない）。
- 上限は各 100 件。
- **閲覧中は Undo できない**（そもそも編集コマンドが積まれない）。編集セッションを終了してもスタックは保持する。

### 5.2 Undo は「新しい編集」である

**サーバーの履歴を巻き戻すのではない。** 逆コマンドを生成し、通常の編集と同じ経路（`pending` → 保存）に流す。

```
undo():
  cmd = undoStack.pop()
  applyToPending(invert(cmd))   // from と to を入れ替えるだけ
  redoStack.push(cmd)
```

- **保存が失敗している最中でも Undo できる**（サーバーの状態に依存しないため）
- サーバーに履歴 API が要らない
- 「Undo したのに保存されない」状態が原理的に生じない

新しい編集が行われたら **Redo スタックは破棄**する（分岐履歴を持たない。エディタの標準挙動）。

### 5.3 スタックを破棄する条件

**`committed` が自分以外の理由で置き換わったとき**、そのページの Undo / Redo スタックを空にする。

- 外部変更を取り込んで再読込したとき（§6）
- `409 STALE` で「再読込する」を選んだとき（§4.3）

理由: 逆コマンドは「その時点の `from`（絶対座標）に戻す」操作である。外部変更でノードが別の場所に移動した後に Undo すると、**外部の変更を意図せず巻き戻す**。これは INV-1 の違反である。

破棄したことはトーストで明示する（「外部の変更を反映したため、取り消し履歴をクリアしました」）。**「上書き保存」を選んだ場合はスタックを維持する**（自分の履歴は依然として有効）。

## 6. H-09 外部変更の反映（SSE）

外部変更の発生源: `git pull` / `git checkout`、エディタでの直接編集、**逆生成の適用（K-11）**、他タブでの編集。

### 6.1 自己起因の変更を無視する（INV-3）

- 書き込みの応答に含まれる `revision` を **`myRevisions`（直近20件のリングバッファ）** に保持する。
- SSE イベント `{ revision, files }` の `revision` が `myRevisions` にあれば**何もしない**（自分の書き込みが監視に引っかかっただけ）。
- 未知のリビジョンなら**外部変更**として §6.2 へ。

### 6.2 分岐

**一律に再読込しない。**

| 自分の状態 | 変更ファイルが**現在のページに無関係**<br>（他ページ / schema / dictionary / config） | 変更ファイルが**現在のページ**（`diagrams/<現在>.js`） |
|---|---|---|
| **ドラッグ中** | 静かに反映（キャンバスに影響しない） | **反映を保留**。ドラッグを中断させない。手を離した直後に下の行の判定を行う |
| **閲覧中**、または編集中で未保存なし | 静かに反映。トースト「外部の変更を反映しました」 | **静かに再読込**し `committed` を差し替える。Undo スタックは破棄（§5.3） |
| **編集中で未保存あり**（`dirty` / `saving` / `failed`） | 静かに反映（`pending` は現在のページのものであり影響しない） | **自動で何もしない。**<br>バナー「このページが外部で更新されました」<br>**[ 自分の変更を保存して上書き ] / [ 破棄して再読込 ]**<br>放置して保存を試みても `409 STALE` で止まる（二重の安全網） |

- スキーマファイル（`schema/**`）の外部変更は、ノード名・リレーションに影響する。**`index.js` を再ロードしてノード・エッジを更新するが、座標は触らない**（座標は `diagrams/**` にしかないため影響を受けない）。
- 参照先を失ったノードは**孤児ノードとして警告表示**する（K-13 と同じ扱い。自動削除しない）。

### 6.3 逆生成の適用中

逆生成の適用（K-11）は複数ファイルを一括で書き換え、**その間 SSE の配信は抑止され、完了後に単一のリビジョンとして通知される**（設計書 §8.5）。ビューアから見れば「1回の外部変更」であり、§6.2 の表がそのまま適用できる。

なお、逆生成の実行には**編集ロックが必要**（書き込み API であるため）。編集中の別タブがある状態では逆生成を開始できない。

## 7. H-06 整列 / H-07・H-08 自動レイアウト

### 7.1 H-06 整列

選択された 2 件以上のノードに対し、左 / 右 / 上 / 下揃え、水平 / 垂直の等間隔配置。**結果は `moveNodes` コマンド1個**（Undo 1回で戻る）。等間隔配置は選択範囲の両端を固定して間を等分する。

### 7.2 H-07 自動レイアウト（ページ全体）

1. `POST /__erd/layout/auto` にノードID・サイズ・エッジを送る
2. サーバーが **Eclipse ELK** で座標を計算して返す（**この API は書き込みをしない**。ロックは不要）
3. クライアントが**プレビュー表示**（現配置を薄く、提案配置を実線で重ねる）
4. [適用] で `moveNodes` コマンド1個として積む → 通常の保存経路へ。[キャンセル] で破棄

**ページ全体の再配置は破壊的である**（手で整えた配置が全部飛ぶ）。プレビューなしに即適用してはならない。Undo 1回で完全に戻せることも安心材料になる。

### 7.3 H-08 自動レイアウト（未配置・選択のみ）— 既存を動かさない

```
1. 既存ノード（配置済み）のバウンディングボックス B を求める
2. 新規ノードとその相互のエッジだけで部分グラフを作る
3. 部分グラフを ELK でレイアウトする（相対座標を得る）
4. 結果を B の右側（またはページの縦横比により下側）にオフセット配置する
5. 8px スナップし、既存ノードとの矩形衝突を検査。衝突すれば、しなくなるまでオフセットを増やす
6. moveNodes / addNodes コマンドとして積む（Undo 可能）
```

**配置の質より「既存を1つも動かさない」ことを優先する。** 関連まで綺麗に見せたければ H-07（全体レイアウト）を使えばよい。配置後は新規ノードが見えるようスクロールし、一時的にハイライトする。

## 8. H-10・H-13 静的モードでの編集とエクスポート

### 8.1 静的モードでも編集できる

`file://` で開いていても、**編集セッションを開始すればノードを動かせる**。ただし保存手段がない。

編集開始時に警告する:

```
このファイルはサーバーなしで開かれています（静的モード）。
配置の変更は保存できません。変更を残すには、編集後に
[配置をエクスポート] から出力し、data/diagrams/*.js に貼り付けてください。

  [ 了解して編集を開始 ]  [ キャンセル ]
```

- 編集中はヘッダに「⚠ 保存されません」を常時表示する。
- Undo / 整列など、書き込みを伴わない編集機能はすべて動作する。
- 自動レイアウト（H-07 / H-08）は**サーバー API（ELK）に依存するため、静的モードでは使えない**（ボタンを無効化し、理由を表示する）。
- リロード・ページ離脱で変更は消える。**離脱時の警告は出さない**（保存手段がなく、警告しても行動を変えられないため。代わりにエクスポート導線を常時表示する）。

### 8.2 配置のエクスポート（H-13）

編集中の `view` を、**`data/diagrams/<id>.js` にそのまま貼り付けられる生の JavaScript コード**としてダイアログに表示する。

```
┌─ 配置をエクスポート ─────────────────────────────┐
│ 以下を data/diagrams/core.js に貼り付けてください  │
│ ┌──────────────────────────────────────────────┐ │
│ │ ERD.diagram({                                │ │
│ │   id: "core",                                │ │
│ │   title: "コアドメイン",                       │ │
│ │   order: 1,                                  │ │
│ │   nodes: {                                   │ │
│ │     "public.users": { pos: [120, 80] },      │ │
│ │     …                                        │ │
│ │ });                                          │ │
│ └──────────────────────────────────────────────┘ │
│                       [ 全選択してコピー ] [ 閉じる ] │
└──────────────────────────────────────────────────┘
```

- ファイルのダウンロードではなく**テキスト表示 + コピー**で足りる（`file://` でのダウンロードは環境差が大きく、貼り付けの方が確実）。
- **サーバーモードでも、未保存の変更を保持したままロックを失った場合の救済手段として使える**（§2.3）。

> **実装上の注意**: これはクライアント側にも決定論的プリンタ（設計書 §5.11 の書式規約）が必要になることを意味する。サーバー（Java）とクライアント（TS）で**二重実装になる**。ズレた場合の実害は「貼り付けたファイルが、次回サーバー保存時に整形し直される（＝余計な Git 差分が1回出る）」程度で済むが、**両実装に同一の golden ファイルを使ったテストを課す**（同じ入力から同じ文字列が出ることを CI で保証する）。

## 9. API 仕様

| メソッド | パス | 用途 |
|---|---|---|
| POST | `/__erd/lock` | 編集ロックの取得 → `{ lockId }` / `423`（保持者情報を返す）。`{ force: true }` で強制取得 |
| PUT | `/__erd/lock` | heartbeat（15秒間隔）→ `200` / `409`（他者に奪われた） |
| DELETE | `/__erd/lock` | 解放 |
| PATCH | `/__erd/diagrams/:id` | レイアウトの保存（§4.4）。`lockId` と `baseHash` が必須 |
| POST | `/__erd/layout/auto` | ELK による座標計算（**書き込みなし・ロック不要**） |
| GET | `/__erd/events` | SSE。`{ revision, files }` |

すべての書き込み API（`PATCH /diagrams`、`PUT /tables/:id`、`PUT /dictionary`、`PUT /config`、`POST /introspect/apply`）に共通で:

- `lockId` 必須（無い / 失効 → `423 LOCK_LOST`）
- `baseHash` 必須（不一致 → `409 STALE`。`force: true` で上書き可）

## 10. テスト観点

| # | 観点 | 期待 |
|---|---|---|
| T-1 | ノードを 3px だけドラッグ | コマンドが積まれず、書き込みも起きない（INV-2 / §3.2） |
| T-2 | ドラッグ → 保存 → ファイルを読む | 座標が 8 の倍数の整数。**同じ操作を繰り返しても Git 差分が増えない** |
| T-3 | 10 ノードを選択して一括移動 → Ctrl+Z | **1回**で全ノードが元に戻る |
| T-4 | 高速に5回連続でノードを動かす | 書き込みは**直列**（同時に2本飛ばない。INV-6）。最終的にファイルが最後の操作と一致 |
| T-5 | 保存失敗（サーバー停止）→ さらに移動 → 復帰 → 再試行 | 失敗中の変更も含めて**すべて**保存される（M-02 / INV-1） |
| T-6 | 自分が保存した直後に SSE が届く | **再読込されない**（INV-3） |
| T-7 | 未保存の変更がある状態で、外部から現在のページを書き換える | **自動再読込されず**、選択バナーが出る。放置しても自分の変更は消えない（INV-1） |
| T-8 | **読み込み後に外部でファイルが変更された状態で保存を試みる** | **`409 STALE` で書き込まれない**（INV-5）。外部の変更がファイル上に保持されている |
| T-9 | `git checkout` で**内容が同じまま mtime だけ**が更新された状態で保存 | **保存できる**（ハッシュが一致するため。mtime 方式なら誤検知するケース） |
| T-10 | 外部変更を取り込んだ直後に Ctrl+Z | **何も起きない**（スタックが空。外部の変更を巻き戻さない。§5.3） |
| T-11 | ドラッグ中に外部変更の SSE が届く | ドラッグが**中断されない**。手を離した後に判定が走る |
| T-12 | タブA で編集中に、タブB で編集を開始 | タブB は `423`。保持者情報が提示される。**強制取得**を選ぶとタブA が15秒以内に閲覧中へ降格し、未保存分をエクスポートできる |
| T-13 | 手動保存モードで20回操作 → Ctrl+S | 書き込みは**1回だけ**。ファイルの内容が最終状態と一致 |
| T-14 | 手動保存モードで未保存のままタブを閉じる | ブラウザの離脱警告が出る |
| T-15 | 静的モードで編集 → エクスポート → 出力を `diagrams/core.js` に貼る → サーバーモードで開く | **同じ配置が再現される**。サーバーが再保存しても内容が変わらない（プリンタ出力の一致。§8.2） |
| T-16 | H-08（未配置のみ自動配置） | 既存ノードの座標が**1つも変わらない**（ファイル差分に既存ノードの行が現れない） |
| T-17 | H-07（全体レイアウト）を適用 → Ctrl+Z | 全ノードが元の座標に**完全に**戻る |

T-2 / T-6 / T-7 / T-8 / T-9 は Git 運用とデータ保全の生命線であり、CI の必須ゲートとする。
