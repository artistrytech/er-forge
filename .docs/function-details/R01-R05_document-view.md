# 詳細設計: R-01〜R-05（テーブル画面の連続表示とドキュメントモード）

対象機能: **R-01 連続表示とドキュメントモード / R-02 表示モードの切替と記憶 / R-03 左パネルとの連動 / R-04 カラム属性のポップアップ / R-05 論理情報の直接編集と論理制約の削除**
関連: B-03〜B-05（左パネル）、O-02（テーブル詳細）、O-03（テーブル編集）、P-01〜P-05（論理名の解決）、E-11（確定＝即時保存の先例）、I-01〜I-03（ページ管理 = 閲覧ルートからの即時書き込みの先例）
設計書: [1_architecture.md](../1_architecture.md) §4.4（ルーティング）/ §6（ロード設計）/ §8.4（`baseHash`）/ §9.1（ER図とカタログの分離）

## 0. この設計が解く問題

テーブル詳細画面（O-02）は「1テーブルの全情報」を出す画面であり、**複数のテーブルを続けて読む**用途には向かない。
テーブルを1つ読むたびに左パネルで次を選ぶ必要があり、カラム表も型・NULL・既定値・コメント・タグ・注記を横に並べるため、
**物理名・論理名・注記だけを追って設計の意図を読む**という「ドキュメントとしての一読」ができない。

この設計は、テーブル画面の右ペインを**左パネルに並んでいるテーブル群を上から順に描く1本のスクロール文書**にし、
1テーブルの中身の密度を「詳細 / ドキュメント」で切り替えられるようにする。

- **詳細**: 1テーブルの全情報（TableInfo）をそのまま縦に連ねる
- **ドキュメント**: 各テーブルのカラム表を「物理名・論理名・タグ・注記」に絞る。型や PK/FK/NULL は消さず、ポップアップに退避する

骨組み（**メタデータ表 → カラム表 → 制約表**）は両モードで同じで、違うのは1テーブルの密度だけにする。
メタデータ（物理名・種別・DB コメント・タグ・注記）は「項目名と値」の表に、制約（主キー・ユニーク・インデックス・
外部キー・論理制約）と被参照は種別を列に持つ1つの表にまとめる（§2.2 / §2.4）。

範囲・スクロール追随・切替・左パネルとの連動は両モードで共通にし、**見た目の骨組み（見出し・タグ・行の色・表）も詳細と同じ部品を使う**。
読んでいて気付いた論理名・タグ・色・注記の不足は、その場でダイアログから直せるようにする（ER図のテーブル詳細ダイアログからも同じ）。要らなくなった論理制約も、その制約の詳細ダイアログから消せるようにする。

### 0.1 不変条件

| # | 不変条件 | 破られたときに起きること |
|---|---|---|
| INV-1 | **範囲は左パネルが決める。** ドキュメントモードは「左パネルに今並んでいるテーブル」を上から順に描くだけで、範囲を選ぶ UI を自前で持たない | 左パネルと右ペインで別々の絞り込みを持ち、「左に無いテーブルが右に出る」食い違いが生まれる（O-02 の直リンク時に起きた問題と同じ） |
| INV-2 | **論理名・注記の解決は詳細（TableInfo）と同じ関数を使い、見出し・メタデータ表・制約表・行の色も同じ部品（`TableMetaTable` / `ConstraintTable` / TableInfo のスタイル）を使う** | 詳細では辞書の論理名が出るのにドキュメントでは未設定になる、といった不一致が起きる。見た目が二系統になると、切り替えたときに別の画面に見える |
| INV-3 | **注記の保存は `saveTableMeta` の経路（読み直し → `baseHash` → `PUT /tables/<id>`）に載せる。専用 API を足さない** | 保存経路が3本目になり、`index.js` 再生成・バックアップ・競合検出の抜けが生まれる。既存の PUT は全文置換だが、直前に読み直したものを1フィールドだけ変えて書くため、部分更新 API と結果は同じ |
| INV-4 | **ドキュメントモードは閲覧ルートであり、編集セッションを開始しない。** 書けるのは論理情報（テーブル / カラムの論理名・タグ・色・注記、制約の注記）と論理制約の削除だけで、確定＝即時保存 | 「編集ルートに入って初めて編集が始まる」（§4.4）の原則が崩れ、フォームの途中状態が残る。ページ管理（I-01〜I-03）と同じく、**1ダイアログ＝1回の書き込み**に限定することでこの原則と両立させる |
| INV-5 | **DOM は範囲の全テーブル分を持つ**（遅延描画で間引かない）。重さは `content-visibility` で吸収する | 途中を描かない仮想化にすると、アンカーへのスクロール・ブラウザの検索（Ctrl+F）が成立しない。「文書として読む」機能でこの2つを失うのは本末転倒 |

## 1. 画面と状態

### 1.1 遷移

```
#/tables/<id>          詳細（連続表示。O-02）  ◄──[詳細 | ドキュメント]──►   #/tables/doc/<id>   ドキュメント（連続表示）
                                                                              │
#/tables               最後の表示モードへ振り替える（R-02）                      └─ 論理情報ダイアログ（R-05。確定＝即時保存）
#/tables/doc           同上（ドキュメント固定。tableId は最後に見たもの）
```

- どちらのルートも同じコンポーネント（`TablesDocument`）で、URL の `<id>` は**スクロール先**を表す。
  右ペイン上部に「詳細 / ドキュメント」のセグメント切替を置く。**両方とも実リンク**（X-04）で、
  切替先の `<id>` は**読んでいる位置のテーブル**（§3.2 のスクロール追随）。
- 左パネルはそのまま（ページ / 全て / 検索の3レーン）。テーブル画面用のインスタンスを共用する。
- 詳細のセクションは従来の詳細画面と同じ（見出し＋TableInfo＋削除の導線）。
- 見出し横の編集ペン（O-03 への入口）は詳細・ドキュメントの両方に出し、**そのセクションのテーブル**を対象にする。
  編集を終えた戻り先は**最後に使っていた表示モード**（`tablesView`）のルート。
- ドキュメントのセクションの見出しの操作は (i) だけ、論理情報のペンは注記の本文の末尾（ホバーで出す）。セクション内にはテーブル編集への
  導線を置かない（見出しのペンと左パネルの行の近道から行ける）。

### 1.2 ルート

| ルート | 画面 | 備考 |
|---|---|---|
| `#/w/<ws>/tables/<tableId>` | 詳細（連続表示）。`<tableId>` の見出しへスクロール | 従来と同じ URL。存在しない ID は「見つかりません」 |
| `#/w/<ws>/tables/doc` | ドキュメント。最後に見たテーブルの位置へ | `#/tables/doc/<lastTableId>` へ `replace` |
| `#/w/<ws>/tables/doc/<tableId>` | ドキュメント。`<tableId>` の見出しへスクロール | 範囲に無ければ、そのテーブルの載っているページを左パネルが選び直し、範囲が変わった時点でそこへ運ぶ（O-02 の直リンクと同じ） |

`doc` はセグメントとして予約する（`#/tables/new` と同じ扱い）。テーブル ID は `schema.name` 形式のため衝突しない。

### 1.3 状態

| 状態 | 置き場所 | 理由 |
|---|---|---|
| 表示モード（`detail` / `doc`） | `localStorage`（`erd-tables-view`。ワークスペースで分けない） | 個人の読み方の好み。`nameDisplay` と同じ扱い |
| 範囲（テーブル ID の配列） | `appStore.tablesPanelList`。左パネル（tables スコープ）の各レーンが `useEffect` で書く | INV-1。パネルは常時マウント（回答2）なので常に最新 |
| 読んでいる位置（スクロール追随のテーブル ID） | `appStore.docActiveTableId` | 左パネルの選択ハイライトと切替リンクの `<id>` に使う。**URL は書き換えない**（履歴を汚さない・スクロールのたびに再描画させない） |
| `lastTableId` | 既存（sessionStorage） | 詳細画面と同じく、ドキュメントで読んでいる位置でも更新する。詳細へ切り替えたときに同じテーブルが開く |
| 注記ダイアログ | コンポーネントのローカル状態 | 1回で完結するため |

## 2. R-01 連続表示とドキュメントモード

### 2.1 範囲の決め方（INV-1）

左パネルのレーンごとに、**一覧に描いている順序のまま**採用する。

| レーン | 範囲 |
|---|---|
| ページ | 選択ページのテーブル（ページ内の並び順）。「未配置」を選んでいれば未配置トレイのテーブル |
| 全て | テーブル名フィルタの結果（名前昇順） |
| 検索 | ヒットしたテーブル（スコア順。同じテーブルはカラム一致が複数あっても1回） |

範囲の見出し（「ページ: 受注」「全て: "order"（12）」「検索: 金額（5）」）を右ペイン上部に出し、**何を読んでいるのかを示す**。
範囲が 0 件なら「左の一覧にテーブルがありません」を出す。

範囲が変わったら（レーン切替・フィルタ入力・ページ選択）文書を描き直す。**読んでいた位置のテーブル**（`docActiveTableId`。まだ無ければ URL の `<tableId>`）が新しい範囲に含まれていればそこへ、無ければ**先頭へ戻す**。着地直後は左パネルの公開より先に描かれるため、URL の `<tableId>` がこの経路で効く（直リンクから左パネルがページを選び直すケース。O-02 と同じ）。

### 2.2 1テーブルの構成（ドキュメント）

```
┌──────────────────────────────────────────────────────────────┐
│ 受注 (orders)   public.orders                                │  ← 詳細と同じ見出し（.catalog-header: 表示形式に従う名前 + ID）
│                                                              │
│ テーブル情報                                                   │
│ ┌────────────┬─────────────────────────────────────────────┐ │  ← 詳細と同じ TableMetaTable（項目名と値。列見出しは無し）
│ │ 物理名      │ public.orders                               │ │

│ │ 外部キー  │ ユーザー (users)                           │ 🔍 ││  ← 外部キーだけ対応カラムを落とす
│ │ 論理外部  │ 在庫 (inventory) 性能上 FK を張っていない     │ 🔍 ││
│ │ 被参照    │ 注文明細 (order_items) (order_id → id)     │ 🔍 ││
│ └──────────┴──────────────────────────────────────────┴────┘│
│                                                              │
│ 配置ページ                                                     │
│ [受注ドメイン] [全体図]                                          │  ← 詳細と同じ PagesSection
└──────────────────────────────────────────────────────────────┘
```

- 見出し・メタデータ表・制約表・カラム表の行の色は**詳細と同じ部品**（`.catalog-header` / `TableMetaTable` / `ConstraintTable` / TableInfo のスタイル）を使う（INV-2）。
  名前は詳細と同じく表示形式（L）に従う。物理名は ID として常に併記されるので、論理名だけの設定でも読み比べられる。
- メタデータ表は**項目名と値の2列**。値の無い項目は行ごと出さない（種別は通常テーブルなら出さない。コメント・タグは空なら出さない）。
  注記だけは空でも「注記なし」を薄く出す（ペンの居場所を作るため）。
  **列見出し（thead）は出さない**。項目名は各行の先頭にあり、その上に「項目 / 値」と書いても何も足さない（制約表も同じ）。
- カラム表は物理名・論理名・タグ・注記の4列。タグは辞書 ∪ 個別（P-12）で、詳細と同じピル。
- 論理名の出どころ（個別 / 辞書 / 未設定）は詳細と同じバッジ・薄字で示す。
- 注記は**本文をそのまま折り返して**出す（詳細画面のようにアイコンに畳まない。読ませるのが目的）。改行は保つ（`white-space: pre-wrap`）。
  テーブル注記が無いときは「注記なし」を薄く出すが、**行では空を「注記なし」と書かない**（毎行に並ぶと読みの邪魔になる。ペンだけ残す）。
- 行の色（P-13）は詳細と同じ `data-color` で左端に出す。
- 制約表は説明に**注記**を出す。対応カラムを落とすのは**外部キー・論理外部制約だけ**で、ほかの種別は構成カラムを出す（§2.4）。`dialect`・ビュー定義は出さない（詳細の責務）。
- **配置ページ（G-05 / O-04）は詳細と同じ `PagesSection` を出す**。読みながら ER図へ渡る導線は、密度を下げる対象ではない。
- PK / FK / NULL 可否 / 型 / 既定値 / DB コメントは行から消さず、**(i) のポップアップに退避**する（R-04）。

### 2.3 ロードと描画の重さ（INV-5）

- 各セクションはマウント時に `loadTable(id)` を呼ぶ（キャッシュ済みなら即時。段階5のバックグラウンドロードで多くは読み込み済み）。
  読み込み中は見出しだけ描き、表の位置に「読み込み中」を出す。読み込み失敗（`tableErrors`）はセクション内にエラーを出し、他のセクションは描く。
- 「全て」で数百テーブルになる場合に備え、**範囲が 30 テーブル以上のときだけ**セクションに `content-visibility: auto` と `contain-intrinsic-size: auto <推定高さ>px` を付ける。
  画面外のセクションが実寸に切り替わる瞬間に境界でかくつくため、普段の範囲（1ページ分）では全部描く。
  推定高さは `index.tables[].columns`（カラム数）から出す（見出し + 行数 × 行高）。画面外のセクションはレイアウト・描画がスキップされ、
  DOM は全件持つのでアンカー・Ctrl+F は成立する。推定高さはメタデータ表・制約表・配置ページの分を両モードに上乗せし、詳細はさらに `dialect`・ビュー定義の分を足す。
- 詳細のセクションでは TableInfo のカラム表の高さ制限（表だけのスクロール）を外す（`fullHeight`）。文書の中に
  もう1つスクロールがあると、読み進める手が止まる。ER図のダイアログでは従来どおり制限する。
- 範囲は 1 配列なので、左パネルのフィルタ入力のたびに全セクションが再マウントされないよう、`key` はテーブル ID とする（React が並び替えとして扱う）。
- 文書の末尾に余白（`padding-bottom: 60vh`）を置く。無いと**最後のテーブルだけ見出しを上端にそろえられず**、左パネルのクリック・選択の追随が末尾で効かなくなる。
- 見出しへ移動した直後は、**その上にあるセクション**の読み込みが済むたびに合わせ直す。上のセクションは読み込みが済むと推定高さから実寸へ変わり、目的の見出しがずれるため（下のセクションは位置に影響しないので待たない）。
- スクロール追随で「読んでいる位置」が変わるたびに App・ヘッダ・左パネルが再描画される。文書本体と各セクションは `memo` にして、テーブル本体の再描画を巻き込まない（境界を越えるたびに全セクションを描き直すと、そこでかくつく）。
- 1回の `scrollIntoView` では決まらない。上のセクションは読み込み中の仮表示や `content-visibility` の推定高さで置かれ、実寸に変わると目的の見出しがずれる。目的のセクション自身が末尾でまだ小さいと、末尾で止まって届かないこともある。移動後しばらく（変化が止まって 1.5 秒）は文書の大きさの変化（`ResizeObserver`）を見張り、**こちらが置いたスクロール位置のまま**で見出しが上端から外れていれば合わせ直す。人がその間にスクロールしていれば手を出さず、ホイール・タッチ・キーの入力があれば打ち切る。
- ドキュメントのカラム表は詳細と同じ `ScrollTable`（枠・角丸・濃色ヘッダ）で描く。高さ制限は付けない。
  メタデータ表・制約表も同じ `ScrollTable` で、どちらも高さ制限を付けない（件数が少なく、畳む意味がない）。

### 2.4 制約表（`ConstraintTable`）

制約は種類ごとに見出し（主キー / ユニーク / インデックス / 外部キー / 論理一意制約 / 論理外部制約 / 被参照）を立てて
「1件 = 1枠」で並べていたが、読むときに知りたいのは**このテーブルにどんな決まりがあるか**であって種類の区切りではない。
種別を1列にして**1つの表**にまとめ、行の並びは上の順序（物理 → 論理 → 被参照）に固定する。
列は**種別と説明の2列だけ**で、メタデータ表と同じく**列見出し（thead）は出さない**。

| 列 | 中身 |
|---|---|
| 種別 | 主キー / ユニーク / インデックス / 外部キー / 論理一意制約 / 論理外部制約 / 被参照。物理は `badge-physical`、論理（論理制約・論理の被参照）は `badge-logical`。インデックスの `unique` 指定だけ補足バッジを添える |
| 説明 | **形を決めない**。相手テーブル（`TableLink`。外部キー・論理外部制約・被参照のみ）→ 対応カラム（相手テーブルがあれば `(col → refCol)`、単体の制約は構成カラムそのもの）→ 注記（ドキュメントのみ）の順に流し込み、末尾（セルの右端）に 🔍 |

モードで変えるのは注記と、**外部キー・論理外部制約の対応カラム**だけ:

| 種別 | 詳細 | ドキュメント |
|---|---|---|
| 主キー / ユニーク / インデックス / 論理一意制約 | 構成カラム | 構成カラム（+ 注記） |
| 外部キー / 論理外部制約 | 相手テーブル + 対応カラム | 相手テーブル（+ 注記）。**対応カラムは落とす** |
| 被参照 | 参照元テーブル + 対応カラム | 参照元テーブル + 対応カラム |

外部キーで対応カラムを落とすのは、`col → refCol` が相手テーブル名と注記の間に挟まると読みの邪魔になるため。
ここで知りたいのは「どこを参照しているか」と「なぜそうしたか」で、どのカラムかは虫眼鏡の中で足りる。
ほかの種別は注記を持たないか短いので、構成カラムを出したほうが行が読める（落とすと 🔍 だけの空の行になる）。
被参照も注記を持てない（注記は参照元テーブルの `meta` にあり、ここでは読み込んでいない）ので対応カラムを出す。

相手テーブルを独立した列にすると、主キー・ユニーク・インデックスの行では常に空になり、
「値の無い列」が表の3割を占める。種別ごとに書くことが違うので、説明は1つのセルに流し込む。
🔍 だけはどの行にもあるのでセルの右端にそろえ、縦に並ぶ押し先として読めるようにする
（詳細ダイアログ: 制約 = `ConstraintInfoDialog` / FK・被参照 = `RelationDialog`）。

- 注記の出どころは種別ごとに違う: 論理一意制約は `meta.logicalUniques[i].notes`、論理外部制約は `meta.logicalForeignKeys[i].notes`、
  物理FK は多重度の補足 `meta.relations["fk:<name>"].notes`（物理FK 自体は machine-owned で注記を持てない）。
  主キー・ユニーク・インデックスは注記を持たないので空。被参照の注記は**参照元テーブル**の `meta` にあり、ここでは読み込んでいないので空にし、虫眼鏡の詳細で読ませる。
- 主キーは `primaryKey: string[]` で持っており制約名が無いため、ダイアログ側（`ConstraintKind = "primaryKey"`）で `{ columns }` の形に均して同じ詳細を出す。
  「いずれの行からも虫眼鏡で詳細へ行ける」を崩さないため、主キーだけ虫眼鏡が無い状態にはしない。
- 制約名は表に出さない（並んだ制約同士を見比べられなくなる）。名前・ON DELETE / UPDATE・カーディナリティ・複合キーの順序は虫眼鏡の詳細に寄せる。
- 1件も無ければ「制約・被参照はありません。」を出す（空の表を残さない）。

## 3. R-02 / R-03 表示モードの切替と左パネルとの連動

### 3.1 切替と記憶（R-02）

- 切替はリンク: 詳細 `#/tables/<id>` ⇄ ドキュメント `#/tables/doc/<id>`。`<id>` は読んでいる位置のテーブルで、切替後も同じ見出しが上端に来る。着地したルートで `localStorage` の表示モードを更新する（ブックマークからの着地も含めて、**最後に使った方**を覚える）。
- `#/tables`（テーブル ID なし）は既存の `restoreTableId` を選んだうえで、記憶した表示モードのルートへ `replace` する。
- ヘッダの「テーブル」ナビも記憶した表示モードで開く（`navHref.tables`）。

### 3.2 左パネルとの連動（R-03）

| 方向 | 挙動 |
|---|---|
| 左 → 右 | 一覧のテーブルをクリック → 表示モードを保ったまま `location.hash` をそのテーブルにし、該当セクションの見出しへ `scrollIntoView`（`block: "start"`） |
| 右 → 左 | 右ペインのスクロール要素の `scroll`（rAF で間引く）で、「貼り付いたバーの下端以下にある最後の見出し」を `docActiveTableId` に書き、左パネルの選択ハイライトを追随させる。`lastTableId` も同じ値で更新する。基準をバーの下端にするのは、見出しが `scroll-margin-top` でバーの下にそろうため |

- 左パネルの `activeTableId` は、テーブル画面のルートでは URL の `<tableId>` ではなく `docActiveTableId` を渡す（App 側で出し分け）。
- **一覧側も追随する**: アクティブになった行は `scrollIntoView({ block: "nearest" })` で見える位置へ出す（`RevealLi`。すでに見えていれば一覧は動かない）。右を読み進めると左の選択が下りていき、一覧も一緒に流れる。
- URL の `<tableId>` へのスクロールは**ルートが変わったときだけ**行う（追随で `docActiveTableId` が変わっても再スクロールしない）。URL が変わったテーブルが範囲に無ければ、読んでいる位置だけをそのテーブルにする（左パネルがページを選び直す → 範囲が変わる → 見出しへ運ぶ）。
- 同じテーブルを続けてクリックしても効くよう、左パネルは URL の書き換えと別に `docScrollTo`（ID + 連番）を store に積む（同じハッシュへの代入は `hashchange` を起こさない）。
- スクロール要素はほかの画面と共用のため、**テーブル画面を離れるとき先頭へ戻す**（途中の位置を持ち越すと、次の画面が途中から開く）。

## 4. R-04 カラム属性のポップアップ

- 各行の物理名の横に (i) を置く。**ホバーでポップアップ、クリックでダイアログ**（`NotePopover` と同じ挙動・同じ見た目）。
  `NotePopover` は本文が文字列前提なので、ポップアップの機構（配置・猶予つきクローズ・フォーカス対応・ダイアログ化）を `InfoPopover` として切り出し、`NotePopover` はその薄いラッパにする。
- 中身は定義リスト:

  | 項目 | 値 |
  |---|---|
  | キー | PK / FK（参照先テーブルへのリンク。詳細画面の `TableLink`）/ ユニーク（単一カラムのユニーク・論理ユニークに含まれる場合） |
  | 型 | `type`（`logicalType` があれば併記）。auto increment / generated のバッジ |
  | NULL | 可 / 不可 |
  | 既定値 | `default` |
  | DB コメント | `comment`（DB 由来。注記とは別物なので混ぜない） |
  | タグ | 辞書 ∪ 個別（P-12） |

- 空の項目は行ごと出さない。全部空でも (i) は出す（型は常にある想定）。
- (i) は**カラムの行だけ**に置く。テーブル単位の情報（DB コメント・制約の構成）はメタデータ表と制約表に常時出るようになったため、
  見出しの (i) は持たない（同じ情報を2か所に置くと、どちらが正かを読む側が判断することになる）。
- (i) はドキュメントだけに出す（詳細は本文にすべて載っている）。

## 5. R-05 論理情報の直接編集と論理制約の削除

### 5.1 導線

- 詳細・ドキュメントの両方、および ER図のテーブル詳細ダイアログ（D-06）に出す。対象と置き場所:

  | 対象 | 書く先 | ペンの場所 |
  |---|---|---|
  | テーブルの論理情報（論理名・タグ・色・注記） | `meta.displayName` / `tags` / `color` / `notes` | メタデータ表の注記の行、本文の末尾（両モード。**その行にホバーしたときだけ出す**） |
  | カラムの論理情報（論理名・タグ・色・注記） | `meta.columns[<col>].displayName` / `tags` / `color` / `notes` | カラム表の**末尾の専用列**（両モード。**行にホバーしたときだけ出す**。キーボードでも到達できるよう `opacity` で隠すだけにし、DOM からは消さない） |
  | 物理FK の多重度の補足 | `meta.relations["fk:<name>"].notes`（物理FK 自体は machine-owned で注記を持てない） | リレーション詳細ダイアログの中（カーディナリティ欄の補足の右） |
  | 論理外部制約の注記 | `meta.logicalForeignKeys[i].notes` | リレーション詳細ダイアログの中（注記の右） |
  | 論理外部制約の多重度の補足 | `meta.relations["lfk:<name>"].notes` | リレーション詳細ダイアログの中（カーディナリティ欄の補足の右） |
  | 論理一意制約の注記 | `meta.logicalUniques[i].notes` | 制約詳細ダイアログの中（注記の右） |

  テーブル・カラムの論理情報は論理情報ダイアログ（`MetaEditDialog`。テーブル編集画面の基本情報・カラム行と同じ項目・部品で、
  カラムではカラム辞書の共通設定も同じ形で見せる）で、リレーション・制約の注記は**詳細ダイアログの中でその場（インライン）**で編集する（`InlineNotes`。
  本文の位置がそのまま入力欄に変わる。Esc は編集だけをやめ、ダイアログは閉じない）。
  どのダイアログも**サーバーモードならどこから開いても**編集できる（テーブル画面・ER図のテーブル詳細ダイアログ・ER図のエッジ）。
  論理情報ダイアログは `appStore.dialogs`（ダイアログの積み重ね）に `{ type: "meta" }` として載せ、App が描く。
  ER図のテーブル詳細ダイアログの上にも重なり、閉じると元のダイアログへ戻る（G-07）。
  対象の読み書きは `model/metaTarget.ts`（`readMetaFields` / `writeMetaFields`。テーブル / カラム）と
  `model/notesTarget.ts`（`writeNotes`。リレーション / 制約）に閉じ込め、TableInfo は `canEdit` のときにペンを出して対象をダイアログへ渡すだけにする。
  論理制約は配列の位置で指すため、保存時に読み直した制約の名前が違えば（他で並びが変わった）中止する。
  保存の読み直しで一瞬テーブルがストアから消えるため、ダイアログは一度読めたテーブルを手元に残す（入力欄ごと消えないように）。
- **サーバーモードのみ**。静的モードではペンを出さない（O-03 と同じ）。
- テーブル編集ルート（`#/tables/<id>/edit`）で同じテーブルを編集中の可能性は考慮しない（同一タブでは遷移で排他になり、別タブは H-09 のバナーで検知する）。

### 5.2 ダイアログ

論理情報ダイアログ（`MetaEditDialog`）は見出しに対象（テーブル ID / カラム名）を出し、論理名（input）・タグ（`TagInput`）・
色（`ColorSelect`）・注記（複数行 textarea）を並べる。初期値は開いた時点のテーブルから取り、確定するまでストアには触らない。
確定で `saveTableMeta(tableId, draft => writeMetaFields(draft, target, fields))` を呼ぶ（インライン注記は `writeNotes`）。

### 5.3 保存（INV-3 / INV-4）

`saveTableMeta` の既存挙動をそのまま使う。

1. `invalidateTable` → `loadTable` で読み直し、`GET /tables/<id>` で `baseHash` を取る
2. 読み直した内容から `MetaDraft` を作り、対象の項目だけ差し替える
3. `PUT /tables/<id>`（`force: false`）
4. 200: `rememberRevision` → `loadTable` → `reloadIndex`。store が更新され、セクションが再描画される。トースト「保存しました」
5. 409: 「他で変更されています。再読み込みしてください」（`save.staleReload`）。ダイアログは閉じ、入力は破棄する（読み直した内容が正）
6. 403 / 422 / ネットワーク: 既存のメッセージをトーストで出し、**ダイアログは開いたまま**（入力を失わせない）

書き込みは配置保存・ページ管理と同じ直列キュー（INV-6 of H）に載るため、ER図の保存と競合しない。
MCP の書き込み前バックアップ（Q-06）は MCP 経由のみの仕組みなので、ここでは取らない（GUI からの保存と同じ扱い）。

### 5.4 空文字

論理名・注記を空にして確定した場合、タグを全部外した場合、色を「色なし」にした場合はそのキーを**落とす**（`draftToMeta` の既存規則。`""` を書かない。Git 差分を汚さない）。

### 5.5 論理制約の削除

注記を書ける場所では、**その制約を消すこともできる**。注記だけ直せて要らなくなった制約は消せない、という片道は使っていて不便であり、
消すために「テーブル編集画面へ行って、同じ制約をもう一度探す」のは、読みながら直すという R-05 の筋から外れる。
**追加はここでは扱わない**（テーブル編集画面 O-03 と ER図 E-12 のまま）。作るときは対象カラム・参照先の入力が要るため、
詳細ダイアログの「1操作＝1保存」に収まらない。

| 対象 | 消す先 | 導線 |
|---|---|---|
| 論理一意制約 | `meta.logicalUniques[i]` | 制約詳細ダイアログの [削除] |
| 論理外部制約 | `meta.logicalForeignKeys[i]`（+ `meta.relations["lfk:<名前>"]`） | リレーション詳細ダイアログの [削除] |

- **物理の制約は消せない**（ユニーク制約・インデックス・物理FK は machine-owned）。[削除] はサーバーモードの論理制約にだけ出す。
- 押すと**確認に切り替わる**（`ConstraintDeleteDialog`）。ダイアログをさらに重ねず**詳細を置き換え**、取消で詳細へ戻る
  （消すか戻るかの二択で、下の内容は読めなくてよい）。確認は ER図のリレーション編集（E-11）の削除と同じ部品で、文言だけ種別で変わる。
- 確定で `saveTableMeta(tableId, draft => removeConstraint(draft, target))`（§5.3 と同じ経路。確定＝即時保存で、配置編集の Undo では戻らない）。
  成功したら詳細ダイアログを閉じてトーストで知らせ、失敗（409 / 403 / 422 / ネットワーク）は確認のまま理由を出す。
- 対象の指し方は `model/constraintTarget.ts` に閉じ込める（注記の `notesTarget.ts`・論理情報の `metaTarget.ts` と同じ役割分担）。
  論理外部制約は**名前**（エッジ ID から決まる）、論理一意制約は**位置 + 名前の突き合わせ**（名前を持たない制約があるため）で指し、
  読み直したドラフトに見当たらなければ `null` を返して中止する（他で消された・並びが変わった）。
- 論理外部制約のカーディナリティはドラフトでは制約の行が持つため（`metaDraft`）、行を落とせば `meta.relations` のエントリも
  一緒に消える（孤児として残らない）。物理FK の設定はそのまま残る。
- 削除後は `index.js` が再生成されるため、ER図の破線エッジ・被参照一覧からも消える（`saveTableMeta` の既存の後処理）。
