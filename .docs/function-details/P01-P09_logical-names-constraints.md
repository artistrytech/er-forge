## 0. この設計が解く問題

論理名は**3箇所に散らばって定義される**（テーブル個別の `meta` / カラム辞書 / 物理名フォールバック）。しかも辞書と個別の合わせ方は属性ごとに違う（論理名・色は上書き、タグは合成）。論理制約は**物理制約と同じ形をしているのに、まったく別のライフサイクルを持つ**（人が書き、逆生成が触らない）。

この2つを場当たりに実装すると、以下が起きる。

- 画面ごとに論理名の解決順序が微妙に違い、ER図のノードとカタログの一覧で違う名前が出る
- 論理制約を追加したのに ER図のエッジが増えない（`index.js` の再生成漏れ）
- 辞書の値とテーブル個別の値のどちらが効いているのか、ユーザーが分からない

**解決順序をコード上の1関数に閉じ込め、そこを全画面が通る**というのが本設計の骨子である。

### 0.1 不変条件

| # | 不変条件 | 破られたときに起きること |
|---|---|---|
| INV-1 | **論理名・色・タグの解決は単一のモジュール（`viewer/model/logicalName.ts`）を通る。** 画面ごとに解決ロジックを書かない | ER図とカタログで違う名前・違う色が表示され、どちらが正しいか誰にも分からなくなる |
| INV-2 | **論理名・論理制約は逆生成で失われない**（K-14 の初期値補完を除き、逆生成は `meta` を書かない） | 人が積み上げた意味情報が DB の更新で消える |
| INV-3 | **カラム辞書（`dictionary.js`）に、テーブル固有の情報を書き込まない** | あるテーブルのカラムコメントが、同名カラムを持つ全テーブルの表示を汚染する |
| INV-5 | **共通タグは合成、共通の論理名・色は上書き。** この非対称を各画面で作り直さない | 「一律に付けたはずのタグ」がテーブルによって消え、分類として使えなくなる |
| INV-4 | **論理制約は物理制約と別のフィールドに保持する**（`meta.logicalUniques` / `meta.logicalForeignKeys`） | 逆生成の上書きで消える |

## 1. 論理名の解決（P-05）

### 1.1 解決順序

```ts
// viewer/model/logicalName.ts —— ここ以外に解決ロジックを書かない（INV-1）

function resolveTableName(table: Table): string {
  return table.meta?.displayName || table.name;          // 個別 → 物理名
}

function resolveColumnName(table: Table, column: string, dict: Dictionary): string {
  return table.meta?.columns?.[column]?.displayName      // ① テーブル個別（P-04）
      || dict.columns[column]?.displayName               // ② カラム辞書（P-03）
      || column;                                         // ③ 物理名
}

function resolveColumnColor(table: Table, column: string, dict: Dictionary): string | undefined {
  return table.meta?.columns?.[column]?.color            // ① テーブル個別（P-13）
      || dict.columns[column]?.color                     // ② カラム辞書
      || undefined;                                      // ③ 色なし
}

// タグだけは上書きではなく合成（INV-5）。共通タグは個別からは取り消せない
function resolveColumnTags(table: Table, column: string, dict: Dictionary): string[] {
  return normalizeTags([
    ...(dict.columns[column]?.tags ?? []),                // 共通タグが先
    ...(table.meta?.columns?.[column]?.tags ?? []),
  ]);                                                    // 重複は大小無視・先勝ちで除く
}
```

**属性ごとに規則が違うのは意図的である。** 論理名と色は「このテーブルではこう見せたい」という個別の事情がありうるが、タグは分類であり、テーブル1件の都合で欠けると集合として意味を失う。個別に外す手段は将来の課題として、いまは持たない（データ形式は増やせる）。

- **空文字は「未設定」として扱う**（`||` でフォールバックする）。UI で空欄にした場合、キー自体を削除して保存する。
- 「論理名が設定されているか」を知りたい場面（未整備ハイライト O-07、カラム辞書の絞り込み）があるため、**解決結果と同時に「どこで解決されたか」を返す版**も用意する。

```ts
type Resolved = { name: string; source: "column" | "dictionary" | "physical" };
```

### 1.2 表示形式（切替可能・個人設定 L-02）

| 設定 | 表示例（テーブル） | 表示例（カラム） |
|---|---|---|
| **併記（既定）** | `ユーザー` / `public.users`（2行、または `ユーザー (users)`） | `メールアドレス (email)` |
| 論理名のみ | `ユーザー` | `メールアドレス` |
| 物理名のみ | `users` | `email` |

- **未解決（物理名フォールバック）は視覚的に区別する**（薄いグレー、または `(未設定)` のヒント）。「論理名が未整備である」ことが一目で分かることが、整備を進める動機になる。
- ER図のノード（D-01）、カタログ一覧（O-01）、詳細（O-02）、詳細ダイアログ（G-01）、検索結果（F-02）のすべてで**同じ設定・同じ解決結果**を使う。

### 1.3 検索との関係（F-01）

検索は**物理名と論理名の両方**にヒットさせる。ユーザーは「ユーザー」でも `users` でも探せる必要がある。

- 検索インデックスには「物理名 + 解決後の論理名」の両方を入れる
- ヒットした側をハイライトする（論理名でヒットしたのに物理名が強調されると混乱する）

## 2. P-03 カラム辞書（`#/columns`）

### 2.1 何のための画面か

`created_at` は全テーブルに現れる。これを 200 テーブル分それぞれの編集画面で「作成日時」と入力させるのは非人間的である。**「同名カラムはプロジェクト全体で同じ意味を持つ」という前提を利用し、1箇所で一括設定する。**

一括で設定するのは論理名だけではない。`password` を全テーブルで `pii` タグ付きの赤にする、`created_at` を全テーブルで淡色にする、といった**分類と見た目も同名カラムに対して一律**であることが多い。そのため辞書は「論理名の対応表」ではなく、**カラム物理名ごとの共通設定**（論理名・タグ・色）を持つ。

| 属性 | テーブル個別との関係 |
|---|---|
| 論理名 | 個別が**上書き**する（P-04） |
| 色 | 個別が**上書き**する（P-13） |
| タグ | 個別と**合成**される。**個別からは取り消せない**（P-12 / INV-5） |

### 2.2 行集合

**全テーブルのカラム物理名を distinct にしたもの ∪ 辞書のキー。**

- **無視リスト（K-15）のテーブルのカラムも含める。** 無視リストは「逆生成の対象外」という意味であり、テーブル自体はカタログに表示され、論理名も必要になるため。
- 辞書に存在するが、どのテーブルにも現れなくなったキー（テーブル削除・カラムリネームの結果）は、**孤立エントリ**として残す。**自動削除はしない**（人が書いた情報だから。INV-2 の精神）。
- **「未設定」は全フィールドが空のときだけ。** 論理名が空でもタグ・色があるエントリは正当であり、保存で消えてはならない（`deleted_at: { tags: ["廃止"] }` のような使い方をする）。

### 2.3 画面

```
カラム辞書                                  [ すべて ▾ ] [ 検索: ______ ] [ 一括貼り付け ]
  ┌──────────────────────────────────────────────────────────────┐ ← ヘッダは固定
  │ カラム物理名     論理名          タグ            色           │
  ├──────────────────────────────────────────────────────────────┤
  │ id              [ID          ]  [            ]  (○)      🔍 │
  │ created_at      [作成日時     ]  [監査 ×      ]  (●)      🔍 │  ← 表だけがスクロールする
  │ password        [パスワード   ]  [pii ×       ]  (●)      🔍 │
  │ code            [            ]  [            ]  (○)      🔍 │
  │ legacy_flag ⚠   [旧フラグ     ]  [            ]  (○)      🔍 │  ← 孤立（押すと理由）
  └──────────────────────────────────────────────────────────────┘
```

| 列 | 内容 |
|---|---|
| カラム物理名 | 辞書のキー。孤立エントリだけ ⚠ を出し、クリックで理由を説明する |
| 論理名 | 行内で編集 |
| タグ | 行内で編集（チップ + 入力欄）。**折り返さず1行**、溢れはセル内で横スクロール |
| 色 | 現在の色の丸を押すとポップアップで選ぶ |
| 🔍 | 詳細ダイアログ（出現テーブル・個別設定の内訳） |

**3つとも行内で編集する。** 1件ずつダイアログを開かせると、この画面の主目的である「数百行を上から順に埋める」作業が成立しない。**「出現」「個別設定」の列は置かない**（数字だけでは「どのテーブルか」が分からず、列幅も食う）。

- **絞り込み**: 「論理名が未設定のみ」「個別設定があるもの」「孤立エントリのみ」。検索はカラム名・論理名・タグに当たる。絞り込みを変えたらスクロール位置を先頭へ戻す。
- **ソート**: カラム物理名の昇順（アルファベット順）。数百行の一覧では、目当てのカラムがどこにあるかを名前から見当付けられることが効く（出現数順は並びの理由が画面から読めず、探し直しになる）。
- **一括貼り付け**: Excel / スプレッドシートからタブ区切りで貼り付けて複数行を一括更新する（`物理名 → 論理名 → タグ → 色`。タグ・色の列は省略でき、省略した項目は据え置き、空欄は削除）。論理名の整備は実務上スプレッドシートで行われがちであり、これがないと画面が使われない。

#### 2.3.1 一覧の仮想化

数百行 × （入力欄 + タグ入力 + 色）を全部描くと、DOM もリスナーも行数に比例して増える。**見えている範囲だけを描き、前後は高さぶんの空行（スペーサー）で埋める**（`viewer/lib/virtualRows.ts`）。

- 表は**ページではなく自前のスクロール器**の中で縦スクロールする（仮想化にはビューポートの高さが要る）。副産物として見出し・絞り込み・表ヘッダが常に見える
- `transform` で持ち上げず**空行**にするのは、`<table>` の列幅計算を壊さないため
- **行の高さは固定**（`ROW_HEIGHT`）。CSS と定数がずれると描画とスクロール量が食い違うので、e2e で実際の行高を検査する
- タグを折り返さないのはこのため。折り返すと行高がタグの数で変わる
- **入力中の行は範囲外でも描き続ける**（`renderPlan` の `pinned`）。スクロールで unmount すると、打鍵と IME 変換中の文字が失われる
- 描いていない行はブラウザの Ctrl+F に当たらない。画面内の絞り込みがその代わりになる

#### 2.3.2 色の選択 UI（P-13）

色は**現在の色を示す丸1つ**を置き、押すとポップアップでトークンを選ぶ。トークン8個を常時並べると、行内ではボタン数が行数×8 になり、横幅も食う。ポップアップは TagInput の候補と同じく **body 直下に固定配置**する（セルの中で絶対配置するとスクロールコンテナに切られる）。テーブル編集画面（O-03）も同じ部品を使う。

#### 2.3.3 詳細ダイアログ（🔍）

1カラム分の内訳を見せる。

| 節 | 内容 |
|---|---|
| 共通設定 | 論理名・タグ・色（行内と同じ値を編集できる） |
| 出現テーブル | このカラム名を持つテーブルの一覧（論理名つき・詳細へリンク）。孤立エントリなら**理由の説明**を出す |
| 個別設定のあるテーブル | 論理名・色・タグをテーブル側で持っているものの一覧と、その値 |

- **編集モード中はテーブルへのリンクを非活性にする**（未保存の編集を抱えたまま遷移させない）。
- 出現テーブルの件数は**ロード済みのテーブルからの集計**なので、全件ロードが済むまでは増え続ける。ダイアログにその旨を出す（§2.5）。

### 2.4 編集モードと保存

**閲覧（`#/columns`）と編集（`#/columns/edit`）を分ける。** 画面に遷移しただけでは辞書を編集できず、**[編集開始] を押して編集ルートへ移って初めて編集可能**になる（画面遷移で誤って書き換えない）。

- **静的モードでは閲覧のみ**（辞書は読み取り表示。[編集開始] は出さない）。`dictionary.js` は設計書 §6.1 の段階2で両モードともロード済みのため、追加ロードなしで表示できる。
- 編集ルート滞在中に別ルートへ遷移しようとしたら、未保存があれば確認する（H-09 の離脱ガードと同じ）。別タブでの並行編集は妨げない（一方の保存はもう一方にバナーで届く）。

**辞書の全体を1回の `PUT /__erd/dictionary` で置換する。**

- 辞書は数百行のフラットなマップであり、部分更新の複雑さに見合う価値がない。
- **タグ・色はテーブル保存（O-08）と同じ規則でサーバーが正規化・検証する**（前後空白・重複は黙って直し、区切り文字の混入・長すぎるタグ・未知の色トークンは 422 で拒否する。P-12 / P-13）。片方の入口だけ緩いと、そこから壊れた値が入る。
- 書き込みの共通規約（`baseHash`。**ロックは無い**）に従う。**自動保存はしない**（明示的な [保存] のみ）。**保存後は閲覧モード（`#/columns`）へ戻る**（テーブル編集画面と同様。ER図が保存後も編集を続けるのと異なる）。
- 保存後、**`index.js` は再生成しない**（`index.js` にカラム情報は含まれないため。§4.2 参照）。**辞書のタグを `tagsUsed` に載せない**のはこの性質を保つためで、タグ入力の候補は辞書を直接読んで足す（辞書はどのモードでも常にロード済み）。

### 2.5 ロードとの関係

**この画面は全テーブルのスキーマを必要とする**（行集合を作るため）。設計書 §6.1 の段階5（アイドル時のバックグラウンドロード）が完了していない場合がある。

- 未ロードのテーブルがあれば、この画面への遷移時に**優先度を上げて先行ロード**する
- 到着したテーブルから順次、行と出現テーブルの一覧を更新する（プログレッシブ表示）。**詳細ダイアログにも読み込み中である旨を出す**（閲覧モードでも開けるため、編集時の警告だけでは足りない）
- 全件ロード完了までは、ヘッダに「読み込み中… (183 / 214)」を表示する。**編集は可能にする**（辞書のキー自体は既にロード済みのテーブルから作れる）が、**保存はロード完了まで待たせる**（孤立エントリの誤判定を防ぐため）

## 3. P-02 コメントからの論理名復元（K-14 の詳細）

### 3.1 補完先は「テーブル個別」であって「辞書」ではない（INV-3）

逆生成の適用時、DB コメントから論理名を補完する先は:

| 対象 | 補完先 |
|---|---|
| テーブル論理名 | `meta.displayName`（そのテーブルの `meta`） |
| カラム論理名 | **`meta.columns.<name>.displayName`（そのテーブルの `meta`）** |

**カラムの補完先をカラム辞書にしてはならない。** DB のカラムコメントはテーブルごとに異なりうる（`users.status` は「会員状態」、`orders.status` は「注文状態」）。これを辞書に書くと、**先に処理されたテーブルのコメントが全テーブルの `status` の表示を汚染する**。

### 3.2 補完の条件

| # | 条件 |
|---|---|
| C-1 | 対象の論理名が**未設定**である（既存値は決して上書きしない。INV-2） |
| C-2 | DB のコメント（`REMARKS`）が空でない |
| C-3 | （カラムのみ）**カラム辞書にも論理名の登録がない**。辞書で既に「作成日時」と決めているものを、DB コメントで上書きしない |

### 3.3 コメントの切り出し規則

DB のコメントは長文であることが多い（「ユーザーマスタ。論理削除は deleted_at で行う。…」）。

- **1行目のみ**を論理名とする（改行 `\n` / `\r\n` で区切る）
- 1行目が 60 文字を超える場合は**補完しない**（論理名ではなく説明文とみなす）
- 前後の空白（全角含む）をトリムする
- `comment` フィールドには**全文がそのまま残る**（machine-owned のまま。切り出しは論理名側の話）

### 3.4 差分プレビューへの提示

補完される論理名は、**逆生成の差分プレビュー（K-08）に「論理名の補完 (47)」として提示し、承認の対象とする。** 黙って `meta` に書き込まない（`meta` への書き込みは逆生成における唯一の例外であり、人の目を通すべきである）。

### 3.5 辞書への昇格提案（優先度 1）

**同名カラムの DB コメントが、出現する全テーブルで一致している場合**（例: `created_at` が全 198 テーブルで「作成日時」）、それはテーブル固有ではなく**プロジェクト共通の意味**である。

カラム辞書の画面（P-03）に「辞書に昇格できる候補が 12 件あります」と提示し、承認すれば:

- 辞書（`dictionary.js`）にそのエントリを追加する
- 各テーブルの `meta.columns.<name>.displayName`（同じ値）を**削除する**（辞書に一本化され、`meta` が軽くなる）

これは「個別設定 → 辞書」への集約であり、差分が読みやすくなる。

## 4. 論理制約（P-06 / P-07）

### 4.1 データ形式

物理制約と**同じ形**にする（表示・カーディナリティ判定・被参照一覧の処理を共通化できる）。ただし**保持する場所は別**である（INV-4）。

```js
meta: {
  logicalUniques: [
    { name: "luk_users_org_email", columns: ["org_id", "email"], notes: "組織内でメールは重複しない（アプリ側で担保）" },
  ],
  logicalForeignKeys: [
    { name: "lfk_users_last_order", columns: ["last_order_id"],
      ref: { table: "public.orders", columns: ["id"] }, notes: "性能上 FK を張っていない" },
  ],
}
```

- `name` は**テーブル内で一意**。未入力なら自動生成する（`lfk_<table>_<col>` / `luk_<table>_<cols>`）。
- `onDelete` / `onUpdate` は**持たない**（DB に制約がない以上、参照動作は存在しない。持たせると「設定したのに効かない」という誤解を生む）。

### 4.2 効果（どこに効くか）

| 機能 | 論理一意制約（P-06） | 論理外部制約（P-07） |
|---|---|---|
| ER図のエッジ | — | **破線エッジとして描画**（E-09） |
| カーディナリティ判定（E-02） | **`toOne` の判定に使う**（参照元カラムに一意性があれば 1対1） | エッジの端点記号 |
| テーブル詳細（O-02 / G-01） | 「論理一意制約」として物理と区別して表示 | 「論理外部制約」として表示 |
| 被参照一覧（G-02） | — | **物理 FK と並べて表示**（種別バッジで区別） |
| リレーション詳細（E-10） | — | 種別「論理」として表示 |
| 整合性チェック（M-04 / P-09） | 参照カラムの存在 | 参照先の存在 |

### 4.3 `index.js` の再生成トリガ（見落としやすい）

**論理制約は `index.relations` に載る**（設計書 §5.5）。ER図はスキーマファイルを読まずに `index.js` だけでエッジを描くため、**論理制約を保存したら `index.js` を再生成しなければエッジが増えない。**

| 保存内容 | `index.js` の再生成 | 理由 |
|---|---|---|
| `meta.logicalForeignKeys` の変更 | **必要** | `relations` が変わる |
| `meta.logicalUniques` の変更 | **必要** | `relations[].toOne`（カーディナリティ）が変わる |
| `meta.displayName`（テーブル論理名） | **必要** | `index.tables[].displayName` が変わる |
| `meta.columns.*.displayName`（カラム論理名） | 不要 | `index` にカラム情報はない |
| `meta.tags` / `meta.notes` | **必要**（tags のみ） | `index.tables[].tags` と `tagsUsed` が変わる |
| `meta.color`（指定色。P-13） | **必要** | `index.tables[].color` が変わる（ER図はこれだけでノードを描く） |
| `meta.columns.*.tags`（カラムタグ。P-12） | **必要** | `tagsUsed` が変わる（カラムタグ自体は索引に展開しない） |
| `meta.columns.*.color` | 不要 | `index` にカラムの色は載せない |
| `dictionary.js` の変更（論理名・タグ・色） | **不要** | 辞書はビューアが直接読む。**辞書のタグは `tagsUsed` に載せない**ため、タグを足しても索引は変わらない |

> サーバーは `PUT /tables/:id` の後、**無条件に `index.js` を再生成する**方針とする（何が変わったかを判定して条件分岐すると、必ず漏れる）。生成コストは小さい。

### 4.4 エッジID の名前空間

ER図のエッジキー（`diagrams.edges` / `index.relations[].id`）は現状 `<tableId>#<制約名>` だが、**物理 FK と論理外部制約で名前が衝突しうる**。種別を挟む。

```
物理: "public.users#fk:users_org_id_fkey"
論理: "public.users#lfk:lfk_users_last_order"
```

> **設計書 §5.5 / §5.9 の修正が必要**（§6.1）。実装前に決めないと、後から全 `diagrams/*.js` が書き換わる。

### 4.5 編集 UI（テーブル編集画面内）

論理制約はテーブル編集画面（O-03）の中で編集する。物理制約のセクションの**直下に、視覚的に区別された別セクション**として置く。

```
─ 制約 ─────────────────────────────────
  主キー        id
  ユニーク      users_email_key (email)
  インデックス   idx_users_created_at (created_at)
  外部キー      users_org_id_fkey (org_id) → public.organizations(id)

─ 論理制約（DB に存在しない、人が定義する制約）───────
  ⓘ ER図には破線で表示されます。DB のスキーマには影響しません。

  論理一意制約   luk_users_org_email (org_id, email)          [編集] [削除]
  論理外部制約   lfk_users_last_order (last_order_id) → public.orders(id)   [編集] [削除]

                                              [ + 論理制約を追加 ]
```

- **「DB のスキーマには影響しない」ことを画面上で明示する。** ここで FK を定義すれば DB に制約が張られると誤解されると、データ不整合の温床になる。
- **一覧の行に注記は出さない**（閲覧側の一覧と同じ扱い。注記の長さで1件の高さが変わると、並んだ制約同士を見比べられなくなる）。注記の読み書きはダイアログの中で行う。
- **注記は複数行で書ける**（`textarea`）。1行では「なぜこの制約があるか」の経緯・例外条件を書き切れず、説明が別の場所へ散る。改行は表示側でもそのまま見せる（`white-space: pre-wrap`）。ファイルには `\n` へエスケープして書き出す（生の改行を書くと `.js` が壊れる）。
- 参照先テーブル・カラムは**選択させる**（自由入力にすると参照切れが増える）。
- 参照先テーブルは**絞り込み → 候補一覧から確定**の 2 段構えにする。テーブル数が増えるとドロップダウンは実用にならないため、名称（論理名・物理名・ID）で絞った結果を一覧で見せ、クリックで確定する（候補が 1 件なら Enter でも確定できる）。
  候補一覧は**入力欄にフォーカスしている間だけ**フローティングで出す（常時展開するとダイアログの他の項目が押し下げられる）。ダイアログ本文は縦スクロールするため、一覧は body 直下へポータルして固定配置し、入力欄の位置を実測して合わせる（下に入りきらないときは上に開く）。
  **確定後は入力不可の表示に切り替え、候補一覧を出さない**（確定済みの参照先が操作の弾みで別のテーブルに変わらないようにする）。選び直しは [×] で解除してから行う。参照先を解除・変更したときは参照先カラムの選択を捨てる（意味を失うため）。

### 4.6 カーディナリティの持ち方（P-11）

**設定は制約の属性であり、独立した一覧ではない。** 以前はテーブル編集画面の末尾に「カーディナリティ」の表を置き、物理FK と論理外部制約を制約名で並べて設定させていたが、これには構造的な欠陥があった。

- **キーが制約名だった。** 保存先は `meta.relations["<種別>:<制約名>"]` である。論理外部制約をリネームすると設定が古い名前に取り残され、**黙って孤児になる**（サーバーは ORPHAN 警告を出すだけ）。
- **名前が決まるまで設定できなかった。** 名前は未入力なら保存時に自動生成されるため、新規に追加した制約は「一度保存するまで多重度を設定できない」状態だった。

現在は次のようにする。

| 対象 | ドラフトでの持ち方 | 保存時のキー |
|---|---|---|
| 物理FK | 制約名で持つ（machine-owned で編集中に変わらない） | `fk:<制約名>` |
| 論理外部制約 | **制約の行そのものに持つ**（名前では持たない） | `lfk:<確定した名前>`（自動生成名も含めて保存時に組み立てる） |
| 現存しない制約への設定 | `orphanRelations` としてそのまま保持 | 元のキーのまま書き戻す（INV-1: 黙って捨てない） |

UI もこれに合わせ、**物理FK・論理外部制約それぞれの詳細ダイアログの中**で設定する（一覧側には「明示設定あり」の印だけを出す）。物理FK は定義を変更できないため、テーブル編集画面に読み取り専用の「外部キー（物理）」セクションを置き、そこを詳細ダイアログへの入口にする（名前の無い物理FK はキーを作れないため対象外）。

**「現在の解決値」は保存済みの `index.js` からしか引かない。** 導出（FK カラムの NULL 可否 → 親側、一意制約との一致 → 子側）は `IndexGenerator` が唯一の実装であり、ビューアには複製しない（Phase0 §5）。そのため未保存の制約・カラム構成を変えた直後は解決値を出せず、「保存後に確定します」と表示する。

### 4.7 ER図からの編集（E-11 / E-12）

ER図の**編集ルート滞在中**は、エッジのダブルクリックで編集できるダイアログを開く（閲覧ルートからは今までどおり読むだけ = E-10）。新規作成は編集モードの中の一時的なモードで、**参照元 → 参照先 → 詳細**の3段階で行う。

- 対象になるのは**そのページに置かれているノードだけ**。両端がページ上にないリレーションはそもそも描かれないため、ページ外のテーブルを選べても描画できない。索引に無い孤児ノード（K-13）も、テーブル定義が読めないため選べない。
- **モード中は配置編集を止める**（移動・除去・Undo / Redo・`Ctrl+S`）。クリックの意味が「選ぶ」に変わるため、同じ操作で違うことが起きないようにする。Esc で中断できる。
- **確定＝即時保存**（`saveTableMeta`）であり、配置編集のコマンド列とは別の経路。したがって **Undo / Redo では戻らない**（削除には確認を挟む）。書き込み自体はレイアウト保存・ページ管理と同じ1本の経路に直列化する（INV-6。並行して投げると `index.js` の再生成が競合する）。
- 保存対象は常に**参照元（子）テーブルのファイル**である。`baseHash` は読み直した内容に対して取り、外部で書き換わっていれば 409 で止める（上書きは提供しない。取り直してやり直す）。失敗してもダイアログは閉じない（入力を失わせない）。

> 保存中はテーブルを読み直すためにストアから一瞬消える。ダイアログが素直に追随すると「読み込み中」に戻って作り直され、入力途中の内容が失われるため、**一度読めたテーブルは保持し続ける**。

> **既知の未対応**: `diagrams/*.js` の `edges` キーも `<テーブルID>#lfk:<制約名>` である。論理外部制約をリネーム・削除しても、このキーは追随せず孤児になる（waypoints が失われて直線に戻るだけで、エラーにはならない）。折れ線の編集 UI（E-07）が未実装で、現状ビューアはこのキーを書かないため実害がない。E-07 を実装するときに、リネーム・削除時の追随とあわせて対応する。

## 5. P-08 バリデーション / P-09 整合性チェック

### 5.1 保存時（P-08）

| # | 検証 | 種別 |
|---|---|---|
| V-1 | 制約名がテーブル内で重複していない | エラー |
| V-2 | 参照元カラムが自テーブルに存在する | エラー |
| V-3 | 参照先テーブルが存在する | エラー |
| V-4 | 参照先カラムが参照先テーブルに存在する | エラー |
| V-5 | 参照元と参照先のカラム数が一致する | エラー |
| V-6 | 参照先カラムが一意である（PK / ユニーク / **論理一意制約**） | 警告（論理制約であり、DB が保証しないため） |
| V-7 | 同一カラム構成の物理制約が既に存在する | 警告（「物理制約 `users_email_key` と重複しています」） |
| V-8 | 参照元と参照先の `logicalType` が異なる | 警告 |

### 5.2 整合性チェック（P-09 / M-04）

保存時には正しくても、**後から参照先が消えることがある**（逆生成でテーブル/カラムが削除された、他のテーブルを手で削除した）。

- **逆生成は論理制約を壊れたまま残す**（勝手に消さない。INV-2）。K 詳細設計 §6.3 の V-3 のとおり、参照切れは**エラーにせず警告**として扱う。
- 整合性チェック画面（M-04）に「参照先を失った論理制約」を一覧表示し、**該当テーブルの編集画面へのリンク**を出す。修正するか削除するかは人が決める。
