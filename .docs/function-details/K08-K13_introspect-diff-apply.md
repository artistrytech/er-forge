# 詳細設計: K-08 〜 K-13（逆生成の差分プレビューと適用）

対象機能: **K-08 差分プレビュー / K-09 リネーム候補の提示 / K-10 適用範囲の選択 / K-11 差分の適用 / K-12 新規テーブルの受け皿 / K-13 削除テーブルの扱い**
関連: K-06（対象の選択）、K-07（逆生成の実行）、K-14（論理名の初期値補完）、**K-15（テーブル無視リスト）**、J-01（テーブルの手動追加）、M-04（整合性チェック）、H-08（自動レイアウト）
設計書: [1_architecture.md](../1_architecture.md) §5.4（`config.js`）/ §7（スキーマ逆生成）/ §8.2・§8.5（API・アトミック性）

## 0. この設計が守るべき不変条件

この一連の機能は「**DB の変更を取り込みながら、人が書いた情報を1文字も失わない**」ことが存在意義である。以下は実装上の交渉不可能な前提とする。

| # | 不変条件 | 破られたときに起きること |
|---|---|---|
| INV-1 | 逆生成は `meta.*`（論理名・論理制約・タグ・注記）を**読まない・書き換えない**。唯一の例外は K-14 の初期値補完（未設定時のみ書き込む） | 人が積み上げた意味情報が DB 由来の情報で消し飛ぶ |
| INV-2 | 逆生成は `data/diagrams/**` の**座標・ページ構成を変更しない**。書き換えるのは**リネーム承認時のキー書換のみ** | ER図の配置が毎回崩れ、レビュー不能な差分が出る |
| INV-3 | 逆生成は `data/dictionary.js` を**一切書き換えない** | カラム論理名の横断辞書が壊れる |
| INV-4 | プレビュー（K-08）は**1バイトも書き込まない** | 「確認しただけ」でリポジトリが汚れる |
| INV-5 | 適用（K-11）は**全ファイルが成功するか、1ファイルも変わらないか**のいずれか | 中途半端な状態でリポジトリが壊れ、手作業の復旧が必要になる |
| INV-6 | 適用対象は**内省スコープ内、かつ無視リストにマッチしないテーブル**に限る | 手動定義テーブル（J-01）や管理テーブル、スコープ外スキーマが「削除」として消える |

INV-6 は **テーブル無視リスト（K-15 / `data/config.js` の `ignoreTables`）** によって成立させる（§2.4）。

## 1. 全体フロー

```
                 ┌──────────────── ブラウザ（GUI） ────────────────┐
[K-07] 実行 ───► POST /__erd/introspect
                 （DB 接続 → 内省 → 差分計算。書き込みなし）
                        │
                        ▼
                 IntrospectSession（サーバーのメモリに保持。TTL 30分）
                   ├ 内省結果のスナップショット（RawSchema）
                   ├ 差分プラン（DiffPlan）
                   ├ リネーム候補（RenameCandidate[]）
                   └ baseFingerprint（現在の data/** のハッシュ）
                        │
                        ▼
[K-08] 差分プレビュー（ツリー表示）
[K-09] リネーム候補の承認 / 訂正 / 却下   ─┐ ユーザーの判断
[K-10] 適用範囲の選択（チェックボックス）  ─┘ （サーバーは何も書かない）
                        │
                        ▼
                 POST /__erd/introspect/apply
                   { sessionId, selection, renameDecisions }
                        │
                        ├─ baseFingerprint 照合（不一致 → 409。再プレビューを促す）
                        ├─ 選択の依存性検証（§5.2）
                        ├─ 一時ディレクトリに data/** の完成形を生成
                        ├─ 検証（決定論的プリンタで往復、参照整合性）
                        └─ ATOMIC_MOVE で一括差し替え + revision 発行
                        │
                        ▼
[K-11] 適用完了 ─┬─► [K-12] 新規テーブル → 未配置トレイへ（配置は人の操作）
                 └─► [K-13] 削除テーブル → 孤児ノードとして警告表示（除去は明示操作）
```

**ポイント: プレビューと適用の間にサーバーの状態は変わらない。** ユーザーがツリーを展開したりリネームを訂正している間、サーバーは `IntrospectSession` を保持しているだけで、DB にも再接続しない（内省結果はスナップショット）。

## 2. データモデル

### 2.1 DiffPlan（差分プラン）

差分は**ツリー**である。ツリーであることが K-10（部分適用）の依存関係をそのまま表現する。

```
DiffPlan
├─ scope           今回の内省スコープ（ネームスペース、フィルタパターン）
├─ stats           { added: 3, removed: 1, modified: 12, renamed: 2, unchanged: 84, outOfScope: 5 }
├─ items: DiffItem[]
└─ guards          危険な差分の警告（§8.3）

DiffItem
├─ id              安定した識別子（下記）
├─ kind            table | column | primaryKey | unique | index | foreignKey | comment | dialect
├─ change          added | removed | modified | renamed
├─ target          対象のテーブルID / カラム名 / 制約名
├─ before / after  変更前後の値（modified のときのみ両方）
├─ children        DiffItem[]（table の下にカラム・制約がぶら下がる）
├─ selectable      false のとき、ユーザーは個別に外せない（§5.2 の強制項目）
└─ requires        この項目を適用するために必要な他項目の id[]
```

**DiffItem の id は決定論的なパス形式**とする。UI の選択状態、リクエスト、ログのすべてでこの id を使う。

```
table:public.users
table:public.users/column:email
table:public.users/fk:users_org_id_fkey
table:public.users/pk
table:public.orders                       ← renamed の場合も「変更後の id」を持つ
```

### 2.2 比較対象（machine-owned のみ）

INV-1 のとおり、差分計算は machine-owned なキーだけを見る。

| 比較する | 比較しない |
|---|---|
| `name` `schema` `comment` `columns[*]`（`name` `type` `logicalType` `nullable` `default` `autoIncrement` `comment`）`primaryKey` `uniques` `indexes` `foreignKeys` `dialect` | `meta.*` の全て、`data/diagrams/**`、`data/dictionary.js`、`id`（リネーム承認の結果としてのみ変わる） |

### 2.3 誤差分（false diff）を出さないための正規化

**同じ DB を2回内省したら差分ゼロ**でなければならない。ドライバやバージョンの表記ゆれで毎回差分が出ると、プレビューが信用されなくなり誰も読まなくなる。比較の前に必ず正規化する。

| 項目 | 正規化ルール |
|---|---|
| 型名 | 前後空白の除去、`VARCHAR (255)` → `varchar(255)`。**大文字小文字は小文字に寄せて比較**するが、保存する `type` は DB が返した原文のまま |
| デフォルト値 | `NOW()` / `now()` の関数名を小文字化。`'foo'::text` のような PostgreSQL のキャストは `dialect` 側に退避し、`default` は `'foo'` に正規化 |
| インデックス | カラム順は `ORDINAL_POSITION` 順を保持（並べ替えない）。インデックス名だけが違う場合は「変更」として出す |
| ユニーク制約 / ユニークインデックス | JDBC 標準では区別できない（設計書 §7.4）。**同一カラム構成のものは1つに畳んで比較する**（片方だけ出て差分になるのを防ぐ） |
| コメント | 改行コードを LF に統一、末尾空白を除去。空文字と `null` は同一視 |
| 真偽値 | `IS_NULLABLE` の `"YES"` / `"NO"` / `""`（不明）を `nullable: true/false` に正規化。不明は `true` 扱いとし、その旨を警告に出す |

> **実装ノート**: 「差分なし」の最終判定は、**正規化後のモデルを決定論的プリンタに通した文字列の一致**で行う。DiffItem の列挙にはモデル比較が必要だが、「結局ファイルは変わらない」ことの確認はプリンタ出力の比較が最も確実で、フェーズ0の往復テストと同じ保証をそのまま使える。

### 2.4 差分計算の対象範囲（無視リストとスコープ）

差分計算に入る前に、DB 側・既存定義側の**双方**から対象外テーブルを除去する。ここを間違えると「手動で定義したテーブルが毎回削除候補として出る」「マイグレーション履歴テーブルが ER図 に混ざる」といった、日々の運用を摩耗させる問題になる。

```
対象テーブル(DB側)   = 内省結果
                       − 無視リストにマッチするもの        ← K-15 / config.js（恒久）
                       − 接続設定の除外パターンにマッチするもの ← K-06（今回限り）

対象テーブル(既存側) = data/schema/** の全テーブル
                       − 無視リストにマッチするもの        ← K-15（★ここが重要）
                       − 内省スコープ外のネームスペースにあるもの
```

| 集合 | 差分上の扱い |
|---|---|
| DB にあり、既存にある | 通常の比較（added / removed / modified / renamed） |
| DB にあり、既存にない | **追加候補** |
| DB になく、既存にある（対象内） | **削除候補** |
| 無視リストにマッチ | **どちらの集合にも入れない。** 既存定義があってもファイルは残り、削除候補にならない。プレビューには「無視 (N)」として件数のみ表示 |
| 内省スコープ外のネームスペース | 差分の対象外。「対象外 (N)」として件数のみ表示 |

**無視リストのマッチング**（`data/config.js` の `ignoreTables`。設計書 §5.4）:

| 記法 | 例 | 判定 |
|---|---|---|
| 完全一致 | `public.flyway_schema_history` | テーブルID が完全一致 |
| glob | `public.tmp_*` | `*`（0文字以上）/ `?`（1文字）を含む場合に glob として解釈 |
| 正規表現 | `/^staging\..*_bak$/` | 前後が `/` の場合に正規表現として解釈。**不正な正規表現は起動時に検出して警告**し、そのエントリは無視する（黙って全マッチしない） |

マッチ対象は**完全修飾テーブルID（`schema.table`）**。パターンの評価は上から順に行い、1つでもマッチしたら無視する。

> **なぜ「既存定義の側からも」無視する必要があるのか**: DB 側だけを除外すると、既存の `data/schema/**` に定義が残っているテーブルは「DB から取得できなかった」＝削除候補として扱われる。手動定義テーブル（J-01）は DB に存在しないため、これでは**逆生成のたびに削除候補として現れ、毎回チェックを外し続ける運用**になる。無視リストが双方向に効くことで、初めて「このテーブルはツールの逆生成対象外」という意思を1箇所で表明できる。

## 3. K-08 差分プレビュー

### 3.1 表示

ツリー表示。既定では**変更のあるテーブルのみ**を展開可能な形で列挙し、`unchanged` は件数のみ（「84 テーブルに変更なし」）を折りたたんで表示する。

```
▼ 追加 (3)
   ├ ▸ public.invoices            12 カラム / PK: id / FK: 1
   ├ ▸ public.invoice_lines        8 カラム / PK: id / FK: 2
   └ ▸ public.payment_methods      5 カラム
▼ リネーム候補 (2)                          ← K-09
   ├ ▸ public.user  →  public.users        確度: 高（カラム構成が完全一致）   [承認] [訂正] [却下]
   └ ▸ public.odr   →  public.orders       確度: 中（カラム名の 7/9 が一致）  [承認] [訂正] [却下]
▼ 変更 (12)
   ├ ▼ public.products
   │    ├ + カラム  sku            varchar(64) NOT NULL
   │    ├ ~ カラム  price          numeric(10,2) → numeric(12,2)
   │    ├ ~ カラム  name           NULL可 → NOT NULL
   │    ├ − カラム  legacy_code                          ⚠ 論理名「旧コード」と注記が失われます
   │    └ + FK      products_category_id_fkey → public.categories(id)
   └ ▸ …
▼ 削除 (1)                                   ← K-13
   └ ▸ public.temp_import         ⚠ 2ページに配置されています（core, staging）
▷ 対象外 (5)                                 ← 内省スコープ外のネームスペース
▷ 無視 (3)                                   ← 無視リスト（K-15）にマッチ。マッチしたパターンを併記
```

### 3.2 失われるものの事前警告

**プレビューの価値の半分は「何が消えるか」を適用前に見せることにある。** 以下は差分項目に警告アイコンを添えて明示する。

| 状況 | 警告文 |
|---|---|
| 削除されるカラムに論理名・注記・論理制約の参照がある | 「論理名『旧コード』と注記が失われます」 |
| 削除されるテーブルがページに配置されている | 「2ページに配置されています（core, staging）。ノードは孤児として残ります」 |
| 削除されるカラムが `meta.logicalUniques` / `meta.logicalForeignKeys` から参照されている | 「論理外部制約 `lfk_xxx` が参照先を失います」 |
| リネームを**却下**した場合 | 「削除＋追加として扱われ、論理名・注記・ER図上の配置が失われます」 |
| カラムの型が縮小方向に変わる | 情報としての注意喚起のみ（ツールはDDLを発行しないため実害はない） |

## 4. K-09 リネーム候補の提示

### 4.1 なぜ必要か

テーブル / カラムのリネームを「削除 + 追加」として扱うと、**`meta`（論理名・論理制約・注記）と ER図上の配置が失われる**。これは INV-1 / INV-2 の実質的な破壊であり、リネーム検出はそれを防ぐための機構である。

### 4.2 検出アルゴリズム（テーブル）

削除候補集合 `D` と追加候補集合 `A` の間で 1:1 マッチングを推定する。

**ステップ1: シグネチャによる完全一致**

```
strictSignature(table) = sha1( join("\n", [ col.name + ":" + col.logicalType for col in table.columns ]) )
```

`D` と `A` で `strictSignature` が一致するペアは**確度: 高**とする（カラム構成が完全に同じテーブルが同時に消えて現れることは、実際上リネーム以外にありえない）。

**ステップ2: スコアリングによる部分一致**

残りの組み合わせについてスコアを計算する。

| 要素 | 重み | 内容 |
|---|---|---|
| カラム名集合の Jaccard 係数 | 0.45 | `|共通| / |和集合|` |
| 型シーケンスの一致率 | 0.25 | 順序を保った `logicalType` 列の LCS / max(len) |
| 主キー構成の一致 | 0.15 | カラム名まで一致で 1.0、カラム数だけ一致で 0.5 |
| 外部キーの参照先集合の一致 | 0.10 | 参照先テーブルID集合の Jaccard |
| テーブル名の類似度 | 0.05 | 正規化編集距離（`user` → `users` のような語尾変化を拾う） |

- **閾値 0.60 以上**を候補として提示する（それ未満は素直に削除＋追加として扱う）。
- 0.60〜0.80 を**確度: 中**、0.80 以上を**確度: 高**として UI に表示する。
- マッチングは**スコア降順の貪欲法**で 1:1 に確定させる（1つの削除候補が2つの追加候補に割り当たることを防ぐ）。
- 上位2件のスコア差が 0.05 未満の場合は**曖昧**とし、「候補が複数あります」として両方を提示し、ユーザーに選ばせる（自動で片方に決めない）。

### 4.3 検出アルゴリズム（カラム）

**同一テーブル内**の削除カラムと追加カラムの間でも同じことを行う。これがないと、カラム1つのリネームで `meta.columns.<name>` の論理名・注記が消える。

| 要素 | 重み |
|---|---|
| `logicalType` の一致 | 0.40 |
| `ORDINAL_POSITION` の近さ（±1 以内で高得点） | 0.25 |
| NULL可否・デフォルト値・autoIncrement の一致 | 0.20 |
| カラム名の編集距離 | 0.15 |

閾値 0.70。テーブルリネームより閾値を上げる（カラムは同型のものが多く、誤検出しやすいため）。**同一テーブル内で削除1件・追加1件かつ型が一致する場合は、確度: 高**として提示する。

### 4.4 ユーザーの判断とその効果

| 操作 | 効果 |
|---|---|
| **承認** | リネームとして適用（§4.5） |
| **訂正** | 対応先を手動で選び直す（ドロップダウンで追加候補の一覧から選択）。ツールが見逃したリネームを人が指定することもできる |
| **却下** | 削除 + 追加として適用。`meta` と配置は失われる（警告を表示のうえ実行） |

**既定は「未決定」であり、勝手に承認済みにしない。** 未決定のリネーム候補が残っている状態では、適用ボタンを押した際に「N 件のリネーム候補が未決定です」と確認する。

### 4.5 リネーム承認時に書き換わるもの

**これが本機能でもっとも影響範囲が広い処理である。** テーブル `public.user` → `public.users` を承認した場合、以下を**すべてアトミックに**書き換える。

| 対象 | 変更内容 |
|---|---|
| `data/schema/public/user.js` | ファイルを `users.js` に**リネーム**（内容の `id` / `name` も更新）。`meta` はそのまま引き継ぐ |
| `data/manifest.js` | `tables` のキー `"public.user"` → `"public.users"`、パスも更新 |
| `data/index.js` | 再生成（`tables[].id`、`relations[].from` / `to`） |
| **他テーブルの `foreignKeys[].ref.table`** | `"public.user"` を参照している全テーブルを書き換える |
| **他テーブルの `meta.logicalForeignKeys[].ref.table`** | 同上（人が定義した論理外部制約も追随させる） |
| **`data/diagrams/*.js` の全ページ** | `nodes` のキーと `edges` のキー（`public.user#fk:<制約名>` 形式）を書き換える。**座標は変えない**（INV-2） |

カラムリネーム（`public.users.mail` → `email`）の場合:

| 対象 | 変更内容 |
|---|---|
| 当該テーブルの `meta.columns.mail` | キーを `email` に付け替え（論理名・注記を保持） |
| 当該テーブルの `meta.logicalUniques[].columns` / `meta.logicalForeignKeys[].columns` | カラム名を書き換え |
| 他テーブルの `foreignKeys[].ref.columns` / `meta.logicalForeignKeys[].ref.columns` | 参照している場合は書き換え |
| `data/dictionary.js` | **書き換えない**（辞書は物理名 → 論理名の対応であり、旧名のエントリはそのまま残す。孤立エントリは P-03 の画面で「出現テーブル数: 0」として可視化され、人が消す） |

## 5. K-10 適用範囲の選択

### 5.1 UI

差分ツリーの各ノードにチェックボックス（三状態: チェック / 未チェック / 部分選択）を置く。既定は**全選択**。

- 「すべて選択」「すべて解除」「追加のみ」「削除を除く」のクイックフィルタを用意する
- 選択件数と、選択によって書き換わるファイル数をフッタに常時表示する

### 5.2 依存関係（selection の整合性）

チェックを外せない項目、外すと連動する項目がある。**UI 側で自動的に整合させ、サーバー側でも再検証する**（クライアントを信用しない）。

| ルール | 内容 |
|---|---|
| R-1 | テーブル追加を選択しない場合、その配下のカラム・制約は選択できない（自動で解除） |
| R-2 | カラム追加を選択する場合、それを含む PK / UK / FK の追加も選択が必要（自動でチェック） |
| R-3 | FK の追加を選択する場合、**参照先テーブルが既存であるか、同時に追加が選択されている**必要がある。満たさない場合はその FK を選択不可にし、理由を表示する |
| R-4 | テーブル削除を選択する場合、そのテーブルを参照している FK の削除も同時に選択される（`selectable: false` で強制） |
| R-5 | リネームの承認は table 単位で1項目。承認したリネームの配下カラム差分は個別に選択できる |
| R-6 | カラム削除を選択する場合、そのカラムを含む制約の削除も強制される（`selectable: false`） |

### 5.3 部分適用の帰結（ユーザーに明示すること）

**部分適用は「DB と data/** が意図的に食い違った状態」を作る。** これを黙って作らせない。

- 適用しなかった差分は**次回の逆生成で再び差分として現れる**（消えるわけではない）
- 適用ダイアログの確認画面に「N 件の差分を適用せずに残します」と明記する

## 6. K-11 差分の適用

### 6.1 前提条件のチェック（適用を始める前）

| # | チェック | 失敗時 |
|---|---|---|
| 1 | `sessionId` が有効（TTL 30分以内、サーバー再起動を跨いでいない） | `410 Gone` → 「プレビューの有効期限が切れました。再実行してください」 |
| 2 | `baseFingerprint` が現在の `data/**` のハッシュと一致 | `409 Conflict` → 「プレビュー後にファイルが変更されました（他の編集 or git pull）。再プレビューしてください」 |
| 3 | 選択の依存性（§5.2）を満たす | `400` → 違反項目を返す |
| 4 | 未決定のリネーム候補がない | `400`（UI 側で先に確認する） |
| 5 | ガード条件（§8.3）に該当する場合、`confirmed: true` が付いている | `400` → 追加確認を促す |

`baseFingerprint` は `data/**` の全ファイルの (パス, 内容ハッシュ) をソートして連結したハッシュ。**SSE によるファイル監視とは別に、適用直前に必ず取り直して照合する**（TOCTOU を防ぐ）。

### 6.2 適用の順序

```
1. バックアップ      data/** の全体を .erd/backup/<timestamp>/ にコピー（Git 管理外）
2. モデルのロード    現在の data/schema/** を全てメモリに読み込む
3. リネームの適用    承認されたリネームで id / 参照 / diagrams のキーを書き換える（§4.5）
4. スキーマの適用    選択された DiffItem を machine-owned フィールドにのみ適用する
                     ├ 追加: 新規 Table（meta は空）
                     ├ 変更: 既存 Table の machine-owned のみ差し替え。meta はそのまま保持
                     └ 削除: Table をモデルから除去（ファイルは 7 で削除される）
5. 論理名の補完      K-14。meta.displayName が未設定のテーブル / カラムにコメントを種まき
6. 派生物の再生成    manifest.js（tables マップ）、index.js（tables + relations）
7. 検証              §6.3
8. 書き出し          一時ディレクトリに全ファイルを決定論的プリンタで生成
9. アトミック差替    ATOMIC_MOVE で置換 → 削除対象ファイルを削除 → revision 発行
```

**手順4で `meta` を「そのまま保持」するのが本機能の核心である。** 変更の適用は「Table オブジェクトを丸ごと差し替える」のではなく、「machine-owned フィールドだけを差し替え、`meta` は既存インスタンスから引き継ぐ」実装にする。丸ごと差し替えの実装は、たった1行の見落としで INV-1 を破壊するため、**モデルの型レベルで分離する**（`TableSchema`（machine）と `TableMeta`（human）を別クラスにし、`Table = TableSchema + TableMeta` の合成にする）。

### 6.3 書き出し前の検証

一時ディレクトリに生成した完成形に対して行う。1つでも失敗したら**何も差し替えずに中止**する（INV-5）。

| # | 検証 |
|---|---|
| V-1 | 全ファイルが決定論的プリンタで生成され、読み戻して同一モデルになる（往復） |
| V-2 | 全 FK の参照先テーブル・カラムが存在する |
| V-3 | 全 `meta.logicalForeignKeys` の参照先が存在する（存在しない場合は**エラーにせず警告**し、M-04 の整合性チェックに送る。人の定義を勝手に消さない） |
| V-4 | `manifest.tables` のキーと `schema/**` のファイルが 1:1 |
| V-5 | `index.js` の内容が `schema/**` から再生成したものと一致 |
| V-6 | `diagrams/**` のノードキーが、存在するテーブル ID か、または削除された孤児（K-13 で許容）である |
| V-7 | ファイルパスが `erd/data/` 配下から出ていない（パストラバーサル） |

### 6.4 アトミック性の担保

- 全ファイルを一時ディレクトリ `data/.tmp-<revision>/` に完成形として生成する
- 検証通過後、`Files.move(..., ATOMIC_MOVE)` で1ファイルずつ置換する
- **置換の途中で失敗した場合**は、`.erd/backup/<timestamp>/` から復元して元の状態に戻す
- 成功時、`.erd/backup/` は直近3世代だけ残してローテーションする
- 完了後に `revision` を発行し、SSE で配信する。自分が起点のリビジョンをブラウザは無視する（設計書 §8.3）

> **なぜファイル単位の move で足りないか**: 変更は複数ファイルに跨る（schema 複数 + manifest + index + diagrams 複数）。1ファイルずつの ATOMIC_MOVE では「manifest だけ新しく、schema が古い」中間状態が一瞬生まれる。ファイル監視 → SSE → 再読込がこの隙間に走ると、ビューアが壊れた状態を読む。これを避けるため、**差し替え中は SSE の配信を抑止し、完了後に1つの revision としてまとめて通知する**。

### 6.5 レスポンス

```jsonc
{
  "revision": "r-20260711-093012-a91f",
  "applied":  { "added": 3, "removed": 1, "modified": 12, "renamed": 2 },
  "skipped":  { "count": 4, "itemIds": ["table:public.products/column:legacy_code", "..."] },
  "logicalNamesSeeded": { "tables": 3, "columns": 47 },   // K-14
  "unplacedTables": ["public.invoices", "public.invoice_lines", "public.payment_methods"], // K-12
  "orphanNodes": [                                          // K-13
    { "tableId": "public.temp_import", "diagrams": ["core", "staging"] }
  ],
  "warnings": [
    { "code": "LOGICAL_FK_DANGLING", "message": "public.orders の論理外部制約 lfk_orders_user が参照する public.user が存在しません" }
  ]
}
```

## 7. K-12 新規テーブルの受け皿（未配置トレイ）

### 7.1 「未配置」は状態ではなく導出

**未配置フラグをファイルに持たない。** 未配置とは「`index.tables[].diagrams` が空である」という導出結果にすぎない。フラグを持つと、ページから除去したときに更新し忘れて実態とズレる。

```
未配置テーブル = index.tables.filter(t => t.diagrams.length === 0)
```

これにより、逆生成で追加されたテーブルも、人がページから除去したテーブルも、同じ「未配置」として同じトレイに現れる。特別扱いが不要になる。

### 7.2 「今回の新規」の強調

適用レスポンスの `unplacedTables` は**セッション限定のメモリ状態**として保持し、トレイ上で「NEW」バッジを付けて先頭に寄せる。リロードすると消える（ファイルには残らない）。永続的に必要な情報ではなく、「今やるべきこと」の提示にすぎないため。

### 7.3 配置操作

| 操作 | 挙動 |
|---|---|
| トレイからキャンバスへドラッグ | ドロップ位置に 8px スナップで配置（H-01） |
| 選択して「このページに追加」 | ページ内の空き領域に自動配置 |
| 「関連テーブルと一緒に追加」（I-05） | 選択テーブルから N ホップ以内の未配置テーブルもまとめて追加 |
| 「自動配置」（H-08） | **ELK で未配置テーブルのみを配置し、既存ノードの座標は一切動かさない**。既存ノードのバウンディングボックスを固定領域として ELK に渡し、その外側または空き領域に新規ノードを置く |

**配置するまで `data/diagrams/**` は一切変わらない。** 逆生成しただけでは ER図の Git 差分はゼロである（INV-2）。これは「逆生成の適用」と「ER図の配置変更」を別コミットに分けるという運用規約（設計書 §10）を、ツール側から自然に成立させるための設計である。

## 8. K-13 削除テーブルの扱い（孤児ノード）

### 8.1 何が起きるか

適用によって `data/schema/public/temp_import.js` は**削除される**。しかし `data/diagrams/core.js` にはまだ `"public.temp_import": { pos: [...] }` というノードが残っている。この、**参照先スキーマを失ったノードを「孤児ノード」と呼ぶ**。

**孤児ノードを自動削除しない。** 理由は2つある。

1. **意図しない削除の可能性**: 内省スコープの設定ミス（フィルタの書き間違い、接続先 DB の間違い）で「削除」に見えているだけかもしれない。この状態で ER図の配置を消してしまうと、正しい設定で再実行しても配置は戻らない（配置は DB から復元できない human-owned な情報である）。
2. **レビュー可能性**: 孤児ノードとして残っていれば、Git 差分には schema ファイルの削除だけが現れ、ER図の差分は出ない。「本当に消してよいか」を人が判断してから、別コミットで配置を消せる。

### 8.2 ビューア上の表現

| 対象 | 表現 |
|---|---|
| 孤児ノード | 警告色（D-05 のエラーノード）で描画し、「このテーブルはスキーマに存在しません」と表示 |
| 孤児ノードに接続していたエッジ | 描画しない（`index.relations` から消えているため自然にそうなる） |
| ページ一覧・テーブル一覧 | 孤児を含むページに警告アイコン |
| 整合性チェック（M-04） | 孤児ノードを一覧表示し、**一括除去**の操作を提供する |

### 8.3 除去の操作

- ノードを選択して `Delete`（N-04）、または右クリック →「ページから除去」
- M-04 の整合性チェック画面から「孤児ノードをすべて除去」（対象ページを列挙して確認のうえ実行）
- いずれも Undo 可能（H-05）で、`data/diagrams/**` の変更として Git 差分に現れる

### 8.4 削除を「適用しない」という選択

K-10 でテーブル削除のチェックを外すと、スキーマファイルは残る。この場合:

- そのテーブルは以後 **DB に存在しないが data には存在する**状態になる
- **次回の逆生成でも再び削除候補として現れる**
- 「DB からは消したが、設計としては ER図 に残したい」ケースでは、**そのテーブルを無視リスト（K-15）に追加する**ことで削除候補から恒久的に外せる。差分プレビューの削除項目に「無視リストに追加」のショートカットを置き、この導線をその場で提供する

### 8.5 危険な差分に対するガード

**フィルタや接続先の設定ミスを、適用前に止める。** 以下に該当する場合、適用ボタンに追加確認（`confirmed: true` の明示）を要求する。

| ガード | 条件 | メッセージ |
|---|---|---|
| G-1 | 削除対象が既存テーブルの **50% 以上** | 「既存 120 件のうち 87 件が削除対象です。接続先とフィルタ設定を確認してください」 |
| G-2 | 内省結果のテーブル数が **0 件** | 「テーブルが1件も見つかりませんでした。ネームスペースの指定を確認してください」 |
| G-3 | 削除対象がページに配置されている | 「削除対象の 3 テーブルは合計 5 ページに配置されています。ノードは孤児として残ります」 |
| G-4 | 前回と**接続先 DB が異なる**（JDBC URL の host / database 部分が変化） | 「前回とは異なる DB に接続しています（前回: prod / 今回: local）」 |

G-1・G-2 は実務でもっとも高くつく事故（フィルタの書き間違いでスキーマ定義を全消しする）を防ぐためのもので、**MVP に含める**。

## 11. テスト観点

| # | 観点 | 期待 |
|---|---|---|
| T-1 | **同一 DB を2回内省** | 2回目の差分が**ゼロ件**（正規化の検証。§2.3） |
| T-2 | `meta` を書き込んだテーブルに対してカラム追加を適用 | `meta`（論理名・論理制約・注記）が**1文字も変わらない**（INV-1） |
| T-3 | 逆生成を適用 | `data/diagrams/**` の**ファイル mtime とハッシュが不変**（INV-2。リネーム承認がない場合） |
| T-4 | テーブルリネームを承認 | schema のファイル名 / id、他テーブルの FK 参照、**全ページの nodes / edges キー**が書き換わり、**座標は不変** |
| T-5 | テーブルリネームを却下 | 削除 + 追加として適用され、`meta` が消える（警告が出ていること） |
| T-6 | カラムリネームを承認 | `meta.columns.<name>` のキーが付け替わり、論理名・注記が保持される |
| T-7 | 適用の途中で書き込みが失敗（ディスクフル・権限） | `data/**` が**適用前と完全に同一**（INV-5。バックアップからの復元） |
| T-8 | プレビュー後に `data/**` を外部から変更（git pull 相当）して適用 | `409` で拒否され、書き込みが発生しない |
| T-9 | FK の追加のみを選択し、参照先テーブルの追加を選択しない | 選択不可（R-3）。サーバー側でも `400` |
| T-10 | 削除対象が既存の 50% 以上 | ガード G-1 が発火し、`confirmed` なしでは `400` |
| T-11 | 無視リストにマッチする既存定義（手動定義テーブル・管理テーブル）がある状態で逆生成 | 削除候補に**現れず**、スキーマファイルも**削除されない**（INV-6）。DB 側にマッチするテーブルがあっても追加候補に現れない |
| T-11b | 無視リストに不正な正規表現を登録 | 起動時に警告し、そのエントリを無視する（全テーブルがマッチする等の暴走をしない） |
| T-12 | 削除テーブルがページに配置されている状態で適用 | 孤児ノードとして警告表示され、`diagrams` は自動変更されない（K-13） |
| T-13 | 論理名が未設定 + DB コメントあり のテーブルを適用 | `meta.displayName` にコメント1行目が入る（K-14） |
| T-14 | 論理名が**設定済み** + DB コメントあり のテーブルを適用 | `meta.displayName` が**上書きされない**（K-14 / INV-1） |
| T-15 | プレビューのみ実行して破棄 | `data/**` に**一切の書き込みが発生しない**（INV-4） |

T-1 / T-2 / T-3 / T-7 / T-15 は**このツールの信頼性そのもの**であり、CI の必須ゲートとする。実 DB に対する検証は Testcontainers（PostgreSQL / MySQL）で行う。
