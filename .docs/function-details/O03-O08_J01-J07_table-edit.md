# 詳細設計: O-03・O-08・J-01〜J-06（テーブル編集画面の保存モデル）

対象機能: **O-03 テーブル編集画面 / O-08 編集の保存とバリデーション / O-09 未保存変更の警告 / J-01 テーブルの追加 / J-02 テーブルの削除 / J-03 カラムの編集 / J-04 制約の編集 / J-05 `meta` の編集 / J-06 バリデーション**
関連: [H-01〜H-13（書き込みの共通規約）](H01-H13_layout-edit-sync-undo.md)、[K-08〜K-13（逆生成とリネーム）](K08-K13_introspect-diff-apply.md)、P-01〜P-09（論理名・論理制約）、K-15（テーブル無視リスト）
設計書: [1_architecture.md](../1_architecture.md) §5.7（`schema/*.js`）/ §8.3・§8.4（書き込みの共通規約・競合検出）/ §8.6（アトミック性）/ §8.7（別タブ・外部変更の検知）

## 0. この設計が解く問題

機能一覧の J-03 は「カラムの追加 / 編集 / 削除 / 並び替え」としか書いていないが、**この画面で物理名を書き換えることの波及が、機能一覧のどこにも現れていない**。

テーブル名を `users` から `accounts` に変えるという1つの操作は、実際には以下を巻き込む。

- スキーマファイルのリネーム（`schema/public/users.js` → `accounts.js`）と `id` の変更
- `manifest.js` / `index.js` の再生成
- **他テーブルの `foreignKeys[].ref.table`**（このテーブルを参照している全 FK）
- **他テーブルの `meta.logicalForeignKeys[].ref.table`**（人が定義した論理外部制約）
- **全 ER図ページの `nodes` / `edges` のキー**

**これは K-09（逆生成でのリネーム承認）とまったく同じ波及である。** そこで必死に守った「ER図の配置と論理名を失わない」という性質が、編集画面から手でリネームしただけで壊れてはならない。

### 0.1 不変条件

| # | 不変条件 | 破られたときに起きること |
|---|---|---|
| INV-1 | **リネームはリネームとして扱う。** 物理名の変更で、ER図の配置・論理名・注記・論理制約が失われない | K-09 で防いだ事故が、編集画面という別の入口から再発する |
| INV-2 | **リネームの実処理は K-09 と同一のコードを使う**（`RenameService`）。2つの実装を持たない | 片方だけ直され、もう片方に不具合が残る |
| INV-3 | **保存は「全ファイルが成功するか、1ファイルも変わらないか」**（§8.6 のアトミック書き込み） | リネームの途中で失敗し、参照が壊れたリポジトリが残る |
| INV-4 | **保存はすべて明示的（[保存] / `Cmd/Ctrl + S`）。自動保存は存在しない** | フォームの途中状態（カラム名が空、FK の参照先が未選択）がファイルに書かれる |
| INV-5 | **`dialect` は編集できない**（読み取り専用表示） | DB 固有情報を人が書き換えても DB には反映されず、嘘のメタデータが残るだけ |

### 0.2 保存はすべて明示的（INV-4）

**自動保存は廃止した（H-03）。** ER図のレイアウト編集も含め、どの画面も明示的な [保存] / `Cmd/Ctrl + S` でのみ書き込む。

編集画面では特にこれが重要になる。レイアウトの変更（座標）は常に有効な値だが、**フォームの途中状態は不正である**（カラム名が空、型が未選択、FK の参照先が未指定）。仮にデバウンスで書き込めば、不正なスキーマがファイルに書かれ、SSE で他の画面が壊れた状態を読む。**保存後は閲覧（詳細画面）へ戻る**（ER図が保存後も編集を続けるのと異なり、テーブル編集・カラム論理名は保存＝一区切りとして扱う。§4.4）。

## 1. 画面と状態

### 1.1 遷移

```
#/tables/<id>            テーブル詳細（閲覧）  ──[編集]──►  #/tables/<id>/edit
#/tables/new             テーブルの手動追加（J-01）
```

- **編集画面が唯一の編集入口である**（ER図の詳細ダイアログは閲覧専用。G-01）。
- 詳細画面（`#/tables/<id>`）は閲覧ルート、編集画面（`#/tables/<id>/edit`）は編集ルート。[編集] を押して編集ルートへ遷移して初めて編集モードになる（**ロックは取得しない**。H-11 は廃止）。編集中は別ルートへ遷移しようとすると未保存を確認する（O-09）。**別タブでの並行編集は妨げないが、一方の保存はもう一方にバナーで届く**（H-09）。
- 静的モードでは編集画面に入れない（詳細画面へリダイレクトし、「閲覧モードです」と表示する）。ER図の配置と違い、**スキーマ編集には持ち出し手段（エクスポート）を用意しない**（貼り付け先が複数ファイルに跨り、人手での復元が現実的でないため）。

### 1.2 状態

```
committed : サーバーから読んだテーブル定義 + そのファイルの baseHash
draft     : フォームの編集中の値（committed のディープコピーから開始）
dirty     : draft ≠ committed
```

- **Undo はフォーム内のブラウザ標準の取り消しに委ねる。** ER図の Undo スタック（H-05）には載せない（画面を跨ぐ Undo は予測不能になる）。
- 「変更を破棄」ボタンで `draft` を `committed` に戻す。
- **未保存変更の警告（O-09）**: `dirty` の状態で画面遷移（ハッシュルート変更）またはタブを閉じようとしたら確認する（`beforeunload`）。

### 1.3 行の安定キー（リネーム検出の土台）

**フォーム上のカラム・制約の各行に、画面内でのみ有効な内部キー（`uid`）を振る。** これがリネーム検出を「推定」ではなく「確定」にする。

```
読み込み時:  columns.map(c => ({ uid: newUid(), ...c }))   // uid はファイルに保存しない
```

- ユーザーが `mail` を `email` に書き換えても、`uid` は変わらない → **「同じ行の名前が変わった」＝リネーム**と確定できる。
- 行を削除して新しい行を追加した場合は `uid` が異なる → **削除 + 追加**として扱う。
- K-09（逆生成）ではカラム構成のシグネチャからリネームを**推定**するしかないが、**編集画面では推定が不要である**（ユーザーの操作そのものが答えを持っている）。この差を利用する。

## 2. 編集できるもの / できないもの

| 区分 | フィールド | 編集 | 備考 |
|---|---|---|---|
| machine-owned | `name`（物理名） | ✓ | **リネームとして扱う**（§3） |
| machine-owned | `schema`（ネームスペース） | **✗** | **画面に表示しない**（§2.1） |
| machine-owned | `columns[*]`（`name` `type` `logicalType` `nullable` `default` `autoIncrement` `comment`） | ✓ | J-03 |
| machine-owned | `primaryKey` `uniques` `indexes` `foreignKeys` | ✓ | J-04 |
| machine-owned | `comment` | ✓ | **次回の逆生成で DB の値に上書きされる**旨を画面に明示する |
| machine-owned | `dialect` | **✗** | 読み取り専用表示（INV-5） |
| human-owned | `meta.displayName`（テーブル論理名） | ✓ | J-05 / P-01 |
| human-owned | `meta.columns.<name>.displayName` / `.tags` / `.color` / `.notes` | ✓ | J-05 / P-04 / P-12 / P-13 |
| human-owned | `meta.tags` / `meta.color` / `meta.notes` | ✓ | J-05 / P-12 / P-13 |
| human-owned | `meta.logicalUniques` / `meta.logicalForeignKeys` | ✓ | J-05 / P-06 / P-07 |

> **カラム辞書（P-03）の共通設定はこの画面からは書き換えない。** 共通の論理名は薄いプレースホルダとして、共通の色は色見本として見せ（どちらも個別の値を入れれば上書きされる）、**共通タグは読み取り専用のチップ**として出す（個別からは取り消せない。P-12）。共通タグを個別の入力欄に混ぜて出すと、保存の瞬間に個別へ焼き付き、辞書から外しても消えない「幽霊タグ」になる。

> `comment`（DB のコメント）を編集可能にするのは、DB にコメントを入れられない現場のためである。ただし machine-owned であり**逆生成で上書きされる**。「DB のコメントに依存しない注記は `meta.notes` へ」という導線を UI に置く。

### 2.1 スキーマ（ネームスペース）は単一とし、画面に出さない

**1つのプロジェクトが扱うスキーマは1つとする。** 対象スキーマは**逆生成の設定で指定する**運用であり、GUI のテーブル編集画面・一覧・詳細・ER図ノードのいずれにも**スキーマ名を表示しない**（全テーブルが同じ値であり、画面上のノイズにしかならない）。

- データ形式上、テーブルID は `public.users` のまま（`schema.table`）とする。将来の複数スキーマ対応の余地を残し、ID の衝突も防げるため、**データからは削除しない**。
- したがって編集画面でスキーマを変更する手段はなく、「スキーマ変更によるリネーム」も存在しない（§3 の対象外）。

## 3. リネームの波及（この設計の中心）

### 3.1 リネームの種類と影響範囲

| リネーム | 書き換わるもの |
|---|---|
| **テーブル物理名** | ①スキーマファイルのファイル名と `id`<br>②`manifest.tables` のキーとパス<br>③`index.js`（再生成）<br>④**他テーブルの `foreignKeys[].ref.table`**<br>⑤**他テーブルの `meta.logicalForeignKeys[].ref.table`**<br>⑥**全 ER図ページの `nodes` キー、`edges` キー**（座標・waypoints は保持） |
| **カラム物理名** | ①自テーブルの `primaryKey` / `uniques[].columns` / `indexes[].columns` / `foreignKeys[].columns`<br>②**`meta.columns` のキー**（論理名・注記を引き継ぐ）<br>③**`meta.logicalUniques[].columns` / `meta.logicalForeignKeys[].columns`**<br>④**他テーブルの `foreignKeys[].ref.columns`**（このカラムを参照している FK）<br>⑤**他テーブルの `meta.logicalForeignKeys[].ref.columns`** |
| **FK 制約名** | **全 ER図ページの `edges` キー**（`<tableId>#fk:<name>` 形式のため。waypoints を失わないよう書き換える） |
| **論理外部制約の名前** | 同上（`<tableId>#lfk:<name>`） |

> スキーマ（ネームスペース）の変更は存在しない（§2.1）。

### 3.2 K-09 と同一の実装を使う（INV-2）

**サーバー側に `RenameService` を1つ置き、逆生成（K-09 の承認）と編集画面（この機能）の両方がそれを呼ぶ。**

```java
interface RenameService {
    // 波及先をすべて計算し、書き換え後のファイル群を返す（書き込みはしない）
    RenamePlan planTableRename(ProjectModel model, String fromId, String toId);
    RenamePlan planColumnRename(ProjectModel model, String tableId, String fromCol, String toCol);
    RenamePlan planConstraintRename(ProjectModel model, String tableId, String fromName, String toName);
}
```

入口が2つあるだけで、**やることは完全に同じ**である。片方だけ実装すると、必ずもう片方にバグが残る。

### 3.3 保存時の確認（リネームか、削除+追加か）

物理名が変更されている状態で [保存] を押したら、**保存前に確認する**。

```
名前の変更を検出しました。

  テーブル  users  →  accounts
  カラム    mail   →  email

● リネームとして保存する（推奨）
    論理名・注記・論理制約・ER図上の配置（3ページ）を引き継ぎます。
    このテーブルを参照している 4 件の外部キーも書き換えます。

○ 削除して新規作成する
    ⚠ 論理名「ユーザー」、注記、論理制約 2 件、ER図の配置が失われます。

              [ キャンセル ]  [ 保存 ]
```

- **既定はリネーム。** 「削除 + 追加」は、ユーザーが意図的に選んだ場合のみ。
- **影響範囲（引き継がれるもの・書き換わる他テーブル・配置ページ数）を必ず数字で示す。**
- 名前の変更がない場合、この確認は出さない（そのまま保存する）。

## 4. 保存モデル

### 4.1 全文置換（部分更新にしない）

`PUT /__erd/tables/:id` は**テーブル1件の完全な定義**を送る。理由:

- フォームはテーブル全体を保持しており、部分差分を作る意味がない
- テーブル1件は数十行であり、転送量は問題にならない
- 部分更新にすると「送らなかったキーは維持」という暗黙のルールが必要になり、`meta` の消失事故を招く（K の INV-1 と同じ罠）

### 4.2 リクエスト

```jsonc
PUT /__erd/tables/public.users
{
  "baseHash": "sha256:9f1a…",          // 対象スキーマファイルの、読み込み時点の内容ハッシュ
  "baseFingerprint": "sha1:3e8b…",     // リネームを伴う場合のみ必須（波及先が複数ファイルに及ぶため）

  "renames": {                          // ★ サーバーは推測しない。クライアントが uid の追跡結果を明示する
    "table":       { "from": "public.users", "to": "public.accounts" },
    "columns":     [ { "from": "mail", "to": "email" } ],
    "constraints": [ { "from": "users_org_fk", "to": "accounts_org_fk" } ]
  },
  "mode": "rename",                     // "rename" | "recreate"（§3.3 でユーザーが選んだ結果）

  "table": { /* 変更後の完全なテーブル定義（machine-owned + meta） */ }
}
```

- **`renames` はクライアントが送る。** 編集画面では `uid` によってリネームが確定しているため、サーバー側で推定する必要がない（推定を入れると、K-09 と違って誤検出の余地が生まれるだけ）。
- **`baseFingerprint`**（`data/**` 全体のハッシュ。K-08 と同じもの）は、リネーム時のみ必須とする。リネームは他テーブルと全 ER図ページを書き換えるため、対象ファイル1つのハッシュでは不十分である。
- リネームを伴わない通常の編集は `baseHash`（対象ファイルのみ）で足りる。**競合検出の粒度を2段に分ける**ことで、単純な編集が「他のファイルが変わっただけ」で弾かれるのを防ぐ。

### 4.3 サーバー側の処理順序

```
1. 競合検証（baseHash / baseFingerprint）           → 失敗: 409 STALE
2. バリデーション（§5）                             → 失敗: 422 + フィールド単位のエラー
3. mode = "rename" なら RenameService で波及を計算（§3.2）
4. machine-owned を差し替え、meta は draft の値で更新（＊）
5. 派生物の再生成（manifest.js / index.js）
6. 一時ディレクトリに完成形を生成 → 検証 → ATOMIC_MOVE（§8.6）
7. revision を発行し SSE 配信（複数ファイルでも単一リビジョン）
```

> ＊ **逆生成（K-11）とは `meta` の扱いが逆である。** 逆生成は `meta` を触らない（machine-owned だけ差し替える）。編集画面は**人が `meta` を編集している**のだから、`meta` も送られた値で更新する。この非対称性を実装で取り違えないよう、**`PUT /tables/:id` は「machine + meta の両方を置換」、逆生成の適用は「machine のみ置換」**と明示的に分ける。

### 4.4 レスポンス

```jsonc
{
  "revision": "r-…",
  "newId": "public.accounts",           // リネームした場合。クライアントは #/tables/public.accounts へ遷移する
  "affected": {
    "tables":   ["public.orders", "public.sessions"],   // FK 参照を書き換えたテーブル
    "diagrams": ["core", "billing"]                     // ノード/エッジのキーを書き換えたページ
  },
  "warnings": [ /* 保存はできたが注意すべきこと（§5.3） */ ]
}
```

保存後は**詳細画面（`#/tables/<newId>`）へ遷移**し、「保存しました（3ページの ER図 と 2テーブルの参照を更新しました）」と通知する。

## 5. バリデーション（O-08 / J-06 / P-08）

### 5.1 エラー（保存を中断する）

| # | 検証 | メッセージ例 |
|---|---|---|
| E-1 | テーブル名・カラム名が空 / 使用不可文字 | 「カラム名を入力してください」 |
| E-2 | 同一テーブル内でカラム名が重複 | 「`email` が重複しています」 |
| E-3 | テーブルID（`schema.table`）が既存と重複 | 「`public.accounts` は既に存在します」 |
| E-4 | カラムが 0 件 | 「カラムが必要です」 |
| E-5 | PK / UK / INDEX / FK が存在しないカラムを参照 | 「主キーのカラム `id` が定義されていません」 |
| E-6 | FK の参照先テーブルが存在しない | 「参照先 `public.orgs` が存在しません」 |
| E-7 | FK の参照元と参照先でカラム数が不一致 | 「カラム数が一致しません（2 → 1）」 |
| E-8 | FK の参照先カラムに PK / ユニーク制約がない | 「参照先 `public.orgs.code` が一意ではありません」 |
| E-9 | 制約名がプロジェクト内（ER図のエッジID の名前空間）で重複 | 「制約名 `fk_org` が既に使われています」 |
| E-10 | 論理制約（P-06 / P-07）が上記 E-5〜E-8 に相当する違反 | 同上（詳細は [P 詳細設計](P01-P09_logical-names-constraints.md) §5.1） |

- エラーは**該当フィールドの直下に表示**し、最初のエラー行へスクロールする。フォーム全体を1つのトーストで片付けない。

### 5.2 型の妥当性

- `type`（DB 生の型文字列）は**自由入力**とする（DB ごとに無限にあるため、ホワイトリスト検証はしない）。
- `logicalType` は列挙（`string` / `int` / … / `other`）から選ぶ。`type` から推定した既定値を提示する。
- FK の参照元と参照先で `logicalType` が異なる場合は**警告**（エラーにしない。`int` ↔ `bigint` のような実用上問題ないケースがあるため）。

### 5.3 警告（保存はできる）

| 警告 | 内容 |
|---|---|
| W-1 | 論理制約が既存の物理制約と同一のカラム構成 → 「物理制約 `users_email_key` と重複しています」 |
| W-2 | FK の型が参照先と異なる（§5.2） |
| W-3 | `comment` を編集した → 「次回の逆生成で DB の値に上書きされます」 |
| W-4 | 手動追加テーブル（J-01）が無視リストに入っていない → §6.1 |

## 6. J-01 テーブルの追加 / J-02 削除

### 6.1 J-01 追加（`#/tables/new`）

DB に存在しないテーブルを手で定義する（未反映の設計案、外部システムのテーブルなど）。

**保存時に、無視リスト（K-15）への追加を提案する。**

```
このテーブルは DB に存在しません。
次回の逆生成で「削除候補」として毎回表示されるのを防ぐため、
テーブル無視リストに追加することを推奨します。

  ☑ public.design_draft を無視リストに追加する

              [ 追加せずに保存 ]  [ 保存 ]
```

- チェックは**既定で ON**。
- これを飛ばすと、逆生成のたびに削除候補として現れ、毎回チェックを外す羽目になる（K 詳細設計 §2.4 の INV-6）。**手動テーブルの保護は、追加した瞬間に済ませるのが最も確実である。**

### 6.2 J-02 削除

削除の前に**影響を提示する**。

```
public.temp_import を削除します。

  ⚠ ER図 2ページに配置されています（core, staging）
     → ノードは孤児として残ります（自動削除しません。K-13 と同じ扱い）
  ⚠ 3件の外部キーがこのテーブルを参照しています
     → public.orders.users_fk / …（これらは参照先を失います）
  ⚠ 論理名「一時取込」、注記、論理制約 1 件が失われます

              [ キャンセル ]  [ 削除する ]
```

- スキーマファイルを削除する。**ER図のノードは削除しない**（孤児ノードとして警告表示。K-13）。
- 参照していた FK は**自動削除しない**（他テーブルを勝手に書き換えない）。整合性チェック（M-04）で検出させる。

## 7. API 仕様

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/__erd/tables/:id` | 編集画面の初期値。**`baseHash` を含めて返す** |
| POST | `/__erd/tables` | 新規作成（J-01）。`ignoreListAdd: true` で無視リストへの追加も同時に行う |
| PUT | `/__erd/tables/:id` | 保存（§4.2）。`200` / `409 STALE` / `422 VALIDATION` |
| DELETE | `/__erd/tables/:id` | 削除（J-02）。`{ affected }` を返す |
| POST | `/__erd/tables/:id/validate` | **保存せずに検証のみ**（フォーム上でのリアルタイム検証に使う。デバウンス 500ms） |

`403`（トークン不一致。設計書 §8.5）は**「見つかりません」と分けて扱う**。専用の画面で次の手順（サーバーが表示した `?t=…` 付き URL を開き直す / 分からなければサーバーを再起動する / dev では `ERD_TOKEN=erd-dev` で起動する）を出す。保存時の `403` も同様に、HTTP コードだけでなく次の手順を含むトーストにする。

トークンはデータ配信にも要求するため、**ふつうはこの画面より先に起動時の 403 案内に着地する**（データが1つも読めない）。編集画面の 403 は、起動後にサーバーが再起動されてトークンが変わった場合などの受け皿である。

`422` のレスポンス:
```jsonc
{
  "code": "VALIDATION",
  "errors": [
    { "path": "columns[3].name",              "code": "DUPLICATE", "message": "email が重複しています" },
    { "path": "foreignKeys[0].ref.table",     "code": "NOT_FOUND", "message": "public.orgs が存在しません" }
  ],
  "warnings": [ … ]
}
```

## 9. テスト観点

| # | 観点 | 期待 |
|---|---|---|
| T-1 | 論理名・注記・論理制約を設定したテーブルの**カラム名**を変更して保存 | `meta.columns` の論理名・注記が**新しいカラム名のキーで引き継がれる**。論理制約のカラム参照も追随する |
| T-2 | 3ページに配置されたテーブルの**テーブル名**を変更して保存 | 全3ページの `nodes` / `edges` のキーが書き換わり、**座標と waypoints は不変** |
| T-3 | T-2 と同時に、他テーブルの FK / 論理外部制約の参照 | すべて新しいテーブルIDに書き換わる |
| T-4 | リネームで「削除して新規作成」を選ぶ | `meta` と配置が失われる（**警告が出ていること**） |
| T-5 | カラムを削除して同名のカラムを新規追加（`uid` が異なる） | リネームとして扱われ**ない**（削除 + 追加。§1.3） |
| T-6 | 保存の途中でディスク書き込みが失敗 | `data/**` が**保存前と完全に同一**（INV-3） |
| T-7 | 編集画面を開いたまま、外部で同じテーブルのファイルを変更して保存 | `409 STALE`。書き込まれない |
| T-8 | 編集画面を開いたまま、**別の**テーブルのファイルを外部変更して保存（リネームなし） | **保存できる**（`baseHash` は対象ファイルのみを見るため。§4.2） |
| T-9 | 同上で、**リネームを伴う**保存 | `409 STALE`（`baseFingerprint` が変わっているため。波及先の安全を優先する） |
| T-10 | 手動追加（J-01）で無視リストへの追加を承諾 → 逆生成 | そのテーブルが**削除候補に現れない** |
| T-11 | 手動追加で無視リストへの追加を**拒否** → 逆生成 | 削除候補に現れる（仕様どおり。警告 W-4 が出ていたこと） |
| T-12 | フォームでカラム名を空にして保存 | `422`。該当フィールドにエラーが表示され、書き込まれない |
| T-13 | 編集中にタブを閉じる | 離脱警告が出る（O-09） |
| T-14 | 編集画面を開いている間、別タブで同じテーブルの編集を開始 → 一方が保存 | **ロックで妨げられない**（並行編集可。H-11 廃止）。他方の保存時に `409 STALE`、またはバナー[再読込]/[無視]が出る（H-09） |

T-1 / T-2 / T-3 は **K-09 と同じ保証を、別の入口に対しても課すもの**であり、CI の必須ゲートとする。
